## Executive Summary

Every agent memory system shipping today is a walled garden, and 2026 is the year that stopped being a footnote and started being a problem people are trying to solve at the protocol level. Anthropic's Managed Agents memory stores are workspace-scoped directories of Markdown files mounted into a session sandbox, versioned and redactable through a proprietary API. Mem0's SDK covers 21 frameworks with its own storage layout. Letta/MemGPT, Cognee, and Zep/Graphiti each have their own vocabulary for what a "memory" is, how it's written, and how it's retrieved. None of these talk to each other. An agent's accumulated preferences, corrections, and hard-won context are exactly as portable as a 2010-era social network profile — which is to say, not at all, unless someone builds a bespoke exporter.

Four efforts are now trying to fix this simultaneously, at four different layers of the stack, largely without referencing each other. **memorywire** (arXiv 2606.01138) is a JSON-Schema wire format defining five operations — remember, recall, forget, merge, expire — across four memory types, with reference adapters for sqlite-vec, mem0, Letta, Cognee, and pgvector. The **Portable Agent Memory** protocol (arXiv 2605.11032) tackles a different problem: cryptographically-verified export and import of memory *between* heterogeneous models (demonstrated across GPT-4, Claude, Gemini, and Llama), using a Merkle-DAG provenance graph and an "injection-resistant rehydration" step designed specifically to stop imported memory from becoming a prompt-injection vector. The IETF's **PAMSPEC** draft (draft-infantado-agent-memory-architecture-00) proposes a provider-independent architecture — a Compute Plane cleanly separated from a Persistent State Plane, with typed Memory Objects, an append-only Event Ledger, and eleven conformance profiles — without claiming the other efforts don't exist, but without integrating with them either. And the **W3C AI Agent Memory Interoperability Community Group**, chartered in June 2026, is scoping interoperability *profiles* and conformance tests on top of whichever wire format wins, with a specific mandate around post-quantum identity binding and cryptographic erasure for GDPR-style right-to-be-forgotten compliance.

This is a standards race running in parallel with — not after — genuine unresolved research problems: nobody has a working definition of what "delete this memory" should mean for a system where the same fact may have already been baked into embeddings, distilled into a summary, or folded into a consolidated ("dreamed") memory store. Nobody has a shared evaluation framework for memory quality beyond conversational-recall benchmarks like LoCoMo and LongMemEval, which don't measure procedural memory, cross-agent consistency, or resistance to memory poisoning. And importing memory across models is, definitionally, importing an attack surface — a fact multiple efforts now design for explicitly, and one Anthropic's own memory-store documentation flags with an unusually blunt warning about prompt injection into `read_write` stores.

The rest of this piece works through: (1) what a real, shipping memory system looks like today, using Anthropic's Managed Agents memory stores and "dreaming" consolidation jobs as the concrete baseline; (2) the four standardization efforts, what layer of the stack each actually addresses, and where they genuinely overlap versus where they're solving different problems entirely; (3) the deletion problem that none of them fully solve; (4) the security surface that memory portability inherently opens up; (5) why this may be premature standardization rather than premature optimization, and what that risk actually looks like in practice; and (6) what a small, multi-runtime agent operation should actually do about any of this today — which is less than the standards bodies would like, but more than "wait and see."

## 1. The Concrete Shape of Lock-In: What a Real Memory Store Looks Like Today

It's worth grounding this in an actual shipping system before getting into proposed standards, because the abstractions in the standards papers map suspiciously well onto whatever the standard's authors happened to be integrating against when they wrote it.

Anthropic's Managed Agents platform exposes **memory stores**: workspace-scoped collections of small text documents, capped at 100 KB (~25k tokens) each, up to 2,000 memories per store. A store is mounted as a directory under `/mnt/memory/<slug>/` inside a session's sandbox, and the agent reads and writes it with ordinary file tools — there's no separate memory API the agent has to learn, just a directory it's told about in its system prompt. Every write produces an immutable, retained version (`memver_...`), which can be listed, retrieved, or **redacted** — scrubbing content out of history for compliance reasons (leaked secrets, PII, a deletion request) while leaving the fact that *something* was redacted, and by what operation, in the audit trail. Access is `read_write` or `read_only`, enforced at the filesystem level, and a session can mount up to eight stores at once — one per user, one shared read-only reference store, one per project.

Layered on top of that is **dreaming**: an asynchronous job that takes an existing memory store plus 1–100 past session transcripts, and produces a *new*, separate output store with duplicates merged, contradictions resolved in favor of the latest value, and new cross-session insights surfaced — all without touching the input store, so a bad dream can simply be discarded. This is a genuinely well-designed answer to the "memory rot" problem that every accumulating store eventually hits: incremental local writes, done well individually, still degrade in aggregate over hundreds of sessions, and periodic consolidation is the standard fix (the same shape as the site's own [memory consolidation](/research/2026-06-08-agent-memory-consolidation-selective-retention-forgetting) and [controlled forgetting](/research/2026-06-04-controlled-forgetting-ai-agent-memory-retention) work covers architecturally, now shipping as a first-party async job in a commercial platform).

None of this is portable. There is no export format for a memory store beyond reading every memory over the API one at a time and reconstructing the tree yourself; there is no import format for bringing a mem0 or Letta store's contents in with their existing structure, provenance, or version history intact. This isn't a criticism specific to Anthropic — every vendor in this space has built the equivalent of this for their own runtime, because building the storage layer first and worrying about interop later is the obviously correct product sequencing. It's simply the concrete reality the four standardization efforts below are responding to: a fast-maturing, genuinely useful capability that is, today, a hard fork per vendor.

## 2. Four Efforts, Four Layers of the Same Stack

**memorywire — the wire format layer.** memorywire (also distributed as a Python package on PyPI, with a reference implementation on GitHub) defines the narrowest and most immediately implementable piece: a JSON-Schema 2020-12 vocabulary for five memory operations — `remember` (write), `recall` (read), `forget` (delete), `merge` (deduplicate), and `expire` (apply a TTL policy) — over four memory type classifications: semantic, episodic, procedural, and emotional. The architecture is a `MemoryStore` interface plus a fan-out router that can dispatch a single logical operation across multiple backends, and — notably — an optional HITL (human-in-the-loop) governance channel that lets a human approve a write before it's committed to long-term storage, directly addressing the "an agent's own writes shouldn't unilaterally become its own future ground truth" concern. The reference implementation ships five backend adapters (sqlite-vec, mem0, Letta, Cognee, pgvector) and reports strong numbers on a 100-fact/50-query test corpus: perfect recall@5 on 42 gold-id queries, 37.8ms p50 ingest latency, 40.6ms p50 recall latency, and 68/80 cells passing on its own conformance suite. The paper is candid that "the entangled class remains open" — meaning memories that are causally entangled with other memories (a correction that invalidates part of an episodic record, say) don't yet have a clean forget semantics, though provenance-based forgetting shows promise per its PurgeBench evaluation.

**Portable Agent Memory — the transfer/provenance layer.** This is a different problem: not "what operations exist on a memory store" but "how do I move an agent's memory from one model/runtime to a different one, and prove nothing was tampered with along the way." Its core structure is a five-component memory model with content-addressable entries linked in a Merkle-DAG provenance graph — the same integrity primitive that underlies Git and Certificate Transparency, repurposed here so any recipient can verify a memory's lineage without trusting the sender. Access control is capability-based, enabling selective, scoped disclosure (share only the procedural-memory subset, not the episodic one, for instance). The most operationally interesting piece is the **injection-resistant rehydration protocol**: importing memory into a target model isn't a raw content copy, it's an adaptation step designed to prevent recalled content from carrying an indirect prompt injection into the new context. Serialization is JSON-first with optional CBOR compaction for transport efficiency, and the authors demonstrated cross-model transfer among GPT-4, Claude, Gemini, and Llama architectures with a 54-test Python SDK, released under Apache 2.0.

**IETF PAMSPEC — the architecture/data-model layer.** draft-infantado-agent-memory-architecture-00 is the most abstract of the four and explicitly scopes itself as architectural vocabulary rather than a wire protocol. Its central move is separating a **Compute Plane** (model inference, planning, tool execution — inherently ephemeral and swappable) from a **Persistent State Plane** (authoritative, versioned Memory Objects, provenance, lifecycle state, and an append-only Event Ledger) plus a layer of **Derived Indexes** (embeddings, lexical indexes, caches) that are explicitly non-authoritative and regenerable — meaning a compliant system should be able to blow away its vector index and rebuild it from the Event Ledger without data loss. It defines eleven conformance profiles from PAMSPEC-Lite (minimal) up to PAMSPEC-Evaluation (deterministic replay), doesn't mandate a specific transport (HTTP, MCP, or an embedded library binding are all acceptable), and bakes in explicit scope enforcement to prevent unscoped global semantic search by default — a governance concern showing up at the architecture level rather than left to policy. It carries the standard IETF individual-submission disclaimer (no working-group backing, no formal standing, expires January 2027) and, tellingly, doesn't reference either memorywire or the W3C group — three efforts converging on the same problem without visible coordination.

**W3C AI Agent Memory Interoperability CG — the governance/conformance layer.** Proposed May 18, 2026 and chaired by Russell Jackson, this Community Group adopted its v1.0 charter in June 2026 with 17 members. Its scope is explicitly *not* re-specifying the underlying wire protocol — it's building interoperability profiles and conformance tests on top of whatever protocol layer wins, plus governance concerns the other three efforts touch only lightly: memory cell format and encryption structure, **post-quantum identity binding** using ML-DSA-65 (FIPS-204), sharing contracts with revocation capability, and — the piece with the most legal teeth — **cryptographic erasure**: destroying the data-encryption key (DEK) for a memory cell, combined with a tombstone record and a content-address blacklist, as the mechanism for satisfying GDPR-style right-to-erasure requests without needing to prove every derived copy (embeddings, cached summaries, dreamed consolidations) has also been scrubbed. The charter explicitly excludes blockchain selection, vector database choice, agent runtimes, and tool routing from scope — a deliberate narrowing that keeps the group from re-litigating fights already being fought elsewhere (MCP for tool routing, various vector-DB benchmarks for storage choice). One detail worth flagging for anyone tracking the standards-politics angle: the IETF's Independent Submission review process concluded in July 2026, which the CG notes lifts prior restrictions on developing competing protocol specifications — i.e., the field was, until very recently, procedurally constrained from spawning exactly the kind of multi-spec fragmentation now underway.

## 3. Where They Overlap, and Where They're Actually Solving Different Problems

Laid side by side, the four efforts look more like a stack than four competitors, but only if someone eventually wires them together:

| Layer | Effort | Core question it answers |
|---|---|---|
| Operations / wire format | memorywire | What verbs exist on a memory store, and what's the request/response shape? |
| Transfer / provenance | Portable Agent Memory | How do I move memory between different models and prove it wasn't tampered with? |
| Architecture / data model | IETF PAMSPEC | What is a Memory Object, independent of any specific vendor's implementation? |
| Governance / conformance | W3C AI Agent Memory Interop CG | What does "interoperable" mean well enough to test for, and how do erasure and identity work across vendors? |

The overlap is concentrated in exactly the place you'd expect: all four touch **deletion semantics**, and none of them touch it the same way. memorywire's `forget` operation is a wire-level verb with an open problem around entangled memories. Portable Agent Memory's Merkle-DAG makes tampering detectable but doesn't itself define what a compliant "forget" looks like across a lineage graph. PAMSPEC treats retention and lifecycle state as an explicit, independent dimension of a Memory Object, separate from validation state — a genuinely useful architectural distinction (a memory can be expired but still valid, or invalid but not yet expired) that the other three don't model as cleanly. And the W3C group's cryptographic-erasure mechanism is the only one of the four that actually confronts the fact that "delete the record" and "delete the information" are different problems once embeddings and consolidated summaries exist — its answer is to make the *keys* unrecoverable rather than promise the *data* was scrubbed everywhere, which is a meaningfully weaker but more honestly achievable guarantee. Section 4 below goes into why that distinction matters more than it sounds.

Where they genuinely diverge rather than overlap: memorywire and PAMSPEC are optimizing for different failure modes. memorywire is pragmatic and adapter-driven — it exists to let one agent talk to five different concrete backends today, and its conformance suite (68/80 passing) is honest that full interop isn't there yet. PAMSPEC is closer to a formal ontology — it's less interested in "can I call mem0 through this" and more interested in "is there a vendor-neutral definition of what a memory *is* that survives any single vendor's implementation choices going away." A system could plausibly speak memorywire on the wire while being internally organized along PAMSPEC's Compute Plane / Persistent State Plane split — they're not mutually exclusive, they're just not currently written to acknowledge each other.

## 4. The Problem Underneath All Four: You Can't Fully Delete What You've Already Learned From

Every one of these efforts treats `forget`/erasure as a first-class operation, because GDPR's right to erasure and equivalent regimes are not optional for anyone shipping agent memory in a regulated market. But the honest state of the art, reflected in the W3C charter's specific choice of *cryptographic* erasure rather than *content* erasure, is that "delete this memory" cannot mean what it sounds like it means once a memory has been through a dreaming/consolidation pass, folded into a distilled summary, or used to update embeddings.

Cryptographic erasure — destroy the DEK, leave a tombstone, blacklist the content address — is a real, defensible, GDPR-aligned answer for the *original record*: if the key is gone, the ciphertext is permanently unreadable, which satisfies "erasure" in the sense regulators actually mean (the data is no longer accessible or usable), even though the ciphertext bytes may still physically exist on disk. What it does *not* address is anything **derived** from that memory before it was erased: a dream that merged the now-erased fact into a broader summary; an embedding computed from its content and stored in a vector index; a distilled preference that got folded into a smaller model via fine-tuning. None of the four efforts claims to solve this — it's an open research problem broader than any memory-portability standard, closely related to work on machine unlearning, and the W3C group's explicit exclusion of "vector databases" and "agent runtimes" from its scope is, read charitably, an acknowledgment that fully solving derived-data erasure would require reaching into exactly those systems.

This is also where the site's earlier work on [Stability and Safety Governed Memory](https://arxiv.org/html/2603.11768v1) framing is relevant background: memory governance in LLM agents has to reason about risk, mechanism, and stability as separate concerns, not just "can I delete a row." A practical implication for anyone building on any of these emerging standards: treat `forget`/erasure as removing a memory from *future retrieval and future derivation*, not as a retroactive guarantee about everything already derived from it. Anything downstream of a dreaming/consolidation job that ran before the forget request needs its own remediation path (re-run the consolidation, or at minimum flag the derived artifact as tainted) — the standards give you a clean way to say "stop using this," not a time machine.

## 5. Importing Memory Is Importing Attack Surface

This is the part of agent memory portability that reads, on first encounter, like a solved problem ("just add access control") and is actually one of the harder open questions in the space, because the threat model is specific to what memory *is for*: content that's meant to be trusted and acted on without re-verification, by design, because re-verifying every remembered fact on every recall would defeat the point of having memory at all.

Anthropic's own memory-store documentation states this plainly, in a warning that's unusually direct for API docs: a store attached with `read_write` access, if the agent processes untrusted input (user prompts, fetched web content, third-party tool output), can have malicious content written into it by a successful prompt injection — and *later sessions then read that content as trusted memory*. That's the exact mechanism the injection-resistant rehydration step in the Portable Agent Memory protocol is built to interrupt: when memory crosses a trust boundary (a different model, a different vendor, a different agent), the recall step needs to treat the incoming content the way a sane system treats any other externally-sourced input — subject to the same skepticism a fresh tool result would get, not elevated to "prior established fact" purely because it arrived via the memory channel rather than the tool-call channel. memorywire's optional HITL governance channel is the same problem attacked from the write side rather than the read side: put a human in the loop before an agent-generated memory becomes durable, rather than trying to sanitize it perfectly on the way back out.

The uncomfortable generalization: memory portability standards, by making it *easier* to move memory across trust boundaries that previously required a bespoke, effortful exporter, also make it easier to move a poisoned memory across those same boundaries — the friction that used to be an accidental security control (nobody had built the pipe yet) goes away once the pipe is standardized. None of the four efforts treats this as solved; the honest framing across all of them is "here is a defense-in-depth mechanism," not "here is a guarantee."

## 6. The Skeptical Read: This May Be Premature Standardization, Not Premature Optimization

It's worth stating the counter-case directly, because "four groups are racing to standardize X" is not automatically good news — it can just as easily mean the field agreed to standardize before it agreed on what matters. Mem0's own state-of-the-industry accounting puts its integration surface at 21 frameworks and platforms, which the company itself frames as evidence that no single framework has won and adopting any one framework's memory module still means adopting its whole abstraction layer. The broader 2026 literature on agent memory is candid that there is no comprehensive evaluation framework for memory quality: LoCoMo and LongMemEval measure conversational recall reasonably well, but neither captures procedural memory quality, cross-agent consistency, temporal reasoning accuracy in isolation, or resistance to memory poisoning — meaning the standards bodies are agreeing on wire formats and conformance profiles for a concept ("good agent memory") that doesn't yet have an agreed-upon measurement.

Concretely: memorywire's own conformance suite passes 68 of 80 cells, and its authors are upfront that "the entangled class remains open." The IETF draft is an individual submission with no working-group backing and an explicit disclaimer that it has no formal standing. The W3C group is 17 members deep, six weeks past charter adoption at the time of writing. None of this is a criticism of the work — early-stage, individually-submitted, not-yet-consensus specs are exactly what a standards process is supposed to produce before consensus — but it does mean "there are now four competing/complementary standards for agent memory" should be read as "the field has enough shared pain that multiple serious groups started writing specs," not as "agent memory portability is a solved, converged problem you can safely build against today." The realistic outcome, based on how MCP itself went from "interesting Anthropic proposal" to "the de facto standard everyone implements" over roughly a year, is that one of these four wins on adoption for reasons partly technical and partly about which vendor backs it — and the others either fold in as profiles/adapters or fade. Which one that will be is not yet knowable from the current state of the field.

## 7. What This Means for a Small, Multi-Runtime Agent Operation

The practical answer for an operation running its own tiered memory system (identity, state, references, per-user profiles, session logs, archive — the same shape this site's own memory architecture uses) is not "implement memorywire" or "wait for W3C to finish." It's narrower and cheaper than either:

- **Don't adopt any of the four specs yet.** Each is pre-consensus, and PAMSPEC in particular is an individual IETF submission with zero formal standing. Building a real dependency on any of them today means re-architecting when the field converges on a different shape, which historically (see: the pre-MCP tool-calling landscape) takes twelve to eighteen months to shake out.
- **Do adopt the discipline the specs are converging on, independent of adopting the specs themselves.** All four efforts, from four different angles, land on the same three tags for every memory write: **scope** (what this memory applies to — a user, a project, a session), **provenance** (where this memory came from — a specific tool call, a specific conversation, a specific dreaming/consolidation pass), and **lifecycle state** (is this still valid, has it been superseded, when does it expire). A memory-tiering system that already routes writes by scope (this site's own identity/state/references/user-profile split is a working instance of exactly this) is most of the way to "export-ready" without needing to touch a wire format at all — the hard part standards bodies are fighting over is agreeing on the *shape* of that metadata across organizations, not the *existence* of it within one.
- **Treat consolidation jobs (dreaming, or any local equivalent) as the natural point to enforce this tagging retroactively.** A dreaming-style pass that merges and deduplicates old memories is exactly the moment to backfill scope/provenance/lifecycle metadata on records that predate the discipline, cheaply, in bulk, rather than trying to migrate live.
- **Take the security warnings more seriously than the interop promise.** Even without adopting any external memory format, the "a successful prompt injection can write malicious content into a `read_write` store, and later sessions read it as trusted" warning applies to any memory system that lets an agent's own outputs, derived from untrusted input, flow back into its own future context unreviewed. That's a today problem, independent of which standard eventually wins.

None of the four efforts is mature enough to bet an architecture on. All four are pointing, independently and somewhat redundantly, at the same three or four properties well-designed agent memory needs regardless of which wire format eventually carries it — and those properties are cheap to adopt now, standard or not.
