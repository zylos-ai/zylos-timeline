## Executive Summary

A terminology rename looks like the safest change you can make. Nothing in the behavior of the system changes; you are only replacing one word with another, everywhere it appears. That appearance of safety is exactly what makes renames dangerous. A word in a design spec or a codebase is rarely a single, unambiguous token — it is a position in a network of meaning, shared across prose, code identifiers, database schemas, CLI flags, and diagrams, and the same spelling is frequently reused for more than one concept. Treating a rename as mechanical text substitution, rather than as a change to the domain model itself, is how a "pure rename" commit quietly changes what a sentence means, collides a new name with an existing one, or leaves old terminology stranded in exactly the document most readers see first.

This piece works through why renames are semantic changes rather than mechanical ones (via Domain-Driven Design's idea of a ubiquitous language and bounded contexts), how several large, well-documented engineering efforts have actually executed terminology migrations at scale, the compatibility mechanics that make a rename safe to roll out gradually, the tooling available for both code-level and prose-level renaming, a concrete review discipline for rename diffs, and what changes when the renaming is being done — or reviewed — by an AI agent. It closes with a practical checklist.

## The failure modes

Consider a recent case from our own design work, generalized here: an AI-agent system's design specs used a term — call it the "channel key" — as the central identifier for a logical grouping of related work. The team decided the name was misleading and renamed the concept to "session group" across roughly six long-lived specification documents, including the identifiers, schema names, and CLI flags those specs define. The rename was deliberately isolated into its own commit, separate from any semantic edits, specifically so it could be reviewed on its own. An independent review of that pure-rename commit still surfaced three distinct problems, each instructive in its own way:

**1. The mis-rename from polysemy.** The old word, "channel," turned out to have two unrelated meanings in the same document set: it was both the name of the concept being renamed and, separately, the name of an unrelated system component (a communication channel). A mechanical find-and-replace that matched the string "channel" without regard to which sense was intended rewrote a sentence that was actually about the component, not the concept — silently changing that sentence's meaning while leaving it grammatically fluent and easy to skim past. This is the textbook risk of homonyms: the same token, two referents, and a substitution tool that cannot tell them apart because it operates on text, not meaning.

**2. The collision with an existing symbol.** The new name introduced a short variable or field letter that happened to already be in use elsewhere in the document for a different quantity. The rename didn't just introduce a new term; it introduced a new *symbol*, and nobody checked that symbol against the existing namespace before adopting it. This is a problem a naming change shares with picking any new identifier: the search space you need to check is "everything already in scope," not just "everywhere the old name appeared."

**3. The residue in the overview.** After the rename propagated through the detailed specs, a top-level overview document — the one most readers would open first — still contained the old term. Partial propagation is an almost universal property of manual or semi-manual renames across multiple documents: the detailed, frequently-edited files get caught, and the summary document that's "basically stable" and rarely opened for editing is exactly the one that gets missed.

Beyond these three, the same class of system tends to produce a few other recurring mismatches worth naming explicitly:

- **Code identifier vs. prose term drift.** The prose settles on "session group," but the code cannot simply use `sessionGroup` as the variable name, because `sessionGroup` (or an equivalent camelCase form) was already claimed elsewhere in the code for the fully-qualified identifier of that same entity (e.g., a composite id string). The result is a deliberate, documented mismatch — code says `groupName`, prose says "session group" — which is a legitimate outcome of a rename, but only if someone decided it on purpose and wrote it down, rather than it emerging as an accident that confuses the next reader.
- **Schema- and interface-level names.** Database columns and indexes, environment variables, CLI flags, and public API field names all encode the old term too, and each has a different blast radius and a different safe-migration mechanic (covered below) — a prose rename and a column rename are not the same operation even though they start from the same decision.
- **Stale derived artifacts.** Diagrams, generated reference tables, and other artifacts derived from the source material don't get re-derived automatically; if they were hand-edited to begin with, a rename in the source leaves them silently out of date until someone remembers to regenerate or re-draw them.

## Why a rename is a semantic change, not a mechanical one

The underlying reason all of the above happens is that a name is not decoration on top of a concept — in a well-run project, the name *is* the interface to the concept, and changing it changes the interface. This is the core insight behind Eric Evans' idea of a **ubiquitous language** in Domain-Driven Design: a common, rigorous language shared between developers and domain experts, built around the domain model, in which "rigor is essential because software requires precision and cannot tolerate ambiguity" [1]. Evans frames the vocabulary itself as something to be actively maintained and tested in conversation — "domain experts should object to terms or structures that are awkward or inadequate to convey domain understanding; developers should watch for ambiguity or inconsistency that will trip up design" [1]. A glossary, under this view, isn't documentation written *about* the system after the fact; it is closer to the source of truth the system's vocabulary is supposed to conform to, and a rename is an edit to that source of truth, which then has to be propagated — correctly — to every place that currently reflects the old version of it.

DDD's companion idea, the **bounded context**, explains why the same word can legitimately mean two different things in two different parts of a system without that being a bug: each bounded context has its own model and its own local ubiquitous language, and a term's meaning is only guaranteed to be consistent *within* a context, not across all of them. That is precisely the shape of failure mode #1 above — "channel" as a component name and "channel" as the renamed concept were, in effect, two different local meanings sharing one spelling, and a pure find-and-replace has no notion of context boundaries at all. It treats the whole document set as one giant string, when the people who wrote it were implicitly treating it as several.

This is also why residue and collisions are not edge cases but the default outcome of naive renaming. A text substitution tool matches *spelling*; a vocabulary consists of *references*. Every occurrence of the old spelling needs to be classified — is this occurrence a reference to the renamed concept, a reference to something else that happens to share the spelling, or a reference to the renamed concept that for some reason should legitimately keep the old word (a quotation, a historical record, an external name you don't control)? A rename review is really a classification exercise wearing the clothes of a text diff.

## How large projects have done terminology migrations

Several widely documented efforts show how this plays out at real scale, and the mechanics they converged on are strikingly consistent.

**Kubernetes: "master" to "control-plane."** Kubernetes replaced the `node-role.kubernetes.io/master` node label and its associated taint with `node-role.kubernetes.io/control-plane`, tracked as KEP-2067 [2]. The project did not do a single cutover; it ran a staged migration across multiple releases. The `control-plane` label was introduced *alongside* the existing `master` label well before `master` was touched, so that both labels and taints coexisted and any workload relying on either selector kept working. Only in a later release did `kubeadm upgrade apply` stop adding the `master` label to new nodes and begin actively removing it from existing control-plane nodes on upgrade; the taint followed a similar staged removal, and consumers like CoreDNS had their tolerations for the old taint updated in a still-later release [2]. The project's own reasoning for the rename was that a dedicated working group had flagged "master" as needing replacement, but the *execution* is the interesting part: dual-labeling first, removal only after an announced grace period, communicated through release notes and community channels, with explicit sequencing, rather than a single atomic rename commit.

**git / GitHub: "master" to "main" as the default branch.** GitHub's own guidance repository for this migration documents a transition designed specifically to avoid breaking existing workflows or rewriting history [4]. When a repository's default branch is renamed, GitHub redirects web requests for the old branch name to the new one, returns a "Moved Permanently" response for API requests against the old name, retargets open pull requests, moves branch protection rules, and updates GitHub Pages build sources — all while leaving existing commit history untouched; past commits and their history "remain intact," and contributors pushing to the old name simply get a notice to update their local remote [4]. GitHub's own write-up explains the choice of "main" itself partly on practical grounds — it's short, keeps muscle memory intact, and translates reasonably across languages — but the operational lesson is the redirect-and-retarget machinery, not the specific word chosen.

**Rust: renaming standard-library collection types.** RFC 0580 proposed renaming several `std::collections` types for naming consistency — `Bitv` to `BitVec`, `BitvSet` to `BitSet`, `DList` to `LinkedList`, and `RingBuf` to `VecDeque` — while explicitly leaving well-established names like `Vec`, `HashMap`, and `BTreeMap` untouched [5]. The compatibility mechanism the RFC specifies is now the standard pattern across the Rust ecosystem for any rename: "redefine the original names as aliases of the new names, and mark them as deprecated. After a transition period, remove the original names completely" [5]. The alias is load-bearing: it means every caller using the old name keeps compiling, gets a compiler warning pointing at the replacement, and only breaks once the maintainers deliberately remove the alias — a decision made on its own schedule, independent of when the rename itself landed.

**Linux kernel: inclusive terminology for new code.** The kernel's own coding-style documentation contains a section recommending that new code avoid "master/slave" and "blacklist/whitelist," with concrete suggested replacements (primary/secondary, leader/follower, controller/device, denylist/allowlist, blocklist/passlist, among others) [3]. What's notable is the explicit, narrow scope: the policy applies to *new* code, with stated exceptions for maintaining existing userspace APIs or ABIs, and for code that has to track a hardware or protocol specification that itself mandates the old terms as of 2020 [3]. The kernel project deliberately chose not to retrofit historical code wholesale — a recognition that renaming inside a live interface contract is a different (and much higher-risk) action than renaming inside code you're actively writing.

**IETF: terminology guidance for protocol documents.** A long-running Internet-Draft, "Terminology, Power, and Inclusive Language in Internet-Drafts and RFCs," argues that authors *should* replace exclusionary pairings like master-slave and blacklist-whitelist with more precise, non-metaphorical alternatives — primary/secondary, primary/replica, active/standby, writer/reader for the first pair; various accept/deny framings for the second [7]. Critically, the draft explicitly does not propose retroactively changing already-published RFCs; it recommends the RFC Editor maintain a living style sheet of guidance for future documents, and that authors referencing older specifications that use the old terms may substitute the new terms in their own prose while noting the substitution, rather than editing the historical document itself [7]. This is the same "don't rewrite history" instinct seen in the GitHub branch rename: the rename applies going forward, and old artifacts are annotated or superseded, not silently altered.

Across all five cases, the pattern is remarkably uniform: introduce the new name alongside the old one, give the old name a bounded but real grace period (sometimes release-numbered, sometimes just "a transition period"), communicate the timeline explicitly, and only remove the old name once you've verified — not assumed — that nothing still depends on it.

## Compatibility mechanics

The mechanism underneath nearly every large rename above has a name: **Parallel Change**, also called **expand-contract**, formalized by Martin Fowler as a three-phase pattern for making a backward-incompatible change safely [6]. The phases are:

- **Expand** — add the new name/interface/column alongside the old one, purely additively. Nothing is removed and no existing caller breaks.
- **Migrate** — move callers, readers, and writers over to the new name incrementally, at whatever pace is safe for each consumer, while both old and new remain live and (if it's data) kept consistent with each other.
- **Contract** — once nothing depends on the old name anymore, remove it.

Fowler is explicit that the pattern's main cost is having to maintain two versions simultaneously during the migration window, and that the discipline required is finishing the contract phase — skipping it leaves a codebase "in a worse state than you started," carrying two names for one concept indefinitely [6]. This maps directly onto the kinds of artifacts a terminology rename touches:

- **Config keys and environment variables**: read the new name first, fall back to the old name if unset (dual-read), and optionally write both during a transition (dual-write), logging a deprecation warning whenever the old name is actually used so you know when it's safe to drop.
- **Database columns and indexes**: add the new column, backfill it from the old one, switch application code to read/write the new column (optionally still writing the old one for safety), and only drop the old column once telemetry shows nothing is reading it — the classic expand/migrate/contract sequence applied to schema.
- **CLI flags**: accept both `--channel-key` and `--session-group` for a release or two, with the old flag's help text pointing at the new one and a startup warning when it's used, before removing it.
- **Code identifiers**: Rust's `#[deprecated]` attribute is a clean example of this at the language level — an old name is redefined as an alias for the new one and annotated so that using it produces a compiler warning naming the replacement, until the alias is deleted in a later release [5].
- **Historical records**: changelogs, old release notes, and closed tickets that use the old term should generally stay exactly as they were written. They're a record of what was true at the time, not living documentation; rewriting them to use the new term retroactively erases the historical trail and can make old discussions harder to follow, not easier. This is consistent with both the IETF draft's position on not editing published RFCs [7] and GitHub's choice to preserve commit history untouched across the branch rename [4].

## Tooling

Different layers of a rename call for different tools, and conflating them is itself a source of error.

**Code-aware renaming.** The Language Server Protocol defines a `textDocument/rename` request specifically so editors can ask a language server to compute a workspace-wide rename as a *set of edits*, not a text search — the server resolves the symbol through scope, imports, and type information first, so "find references" means "the places that actually resolve to this symbol," not "the places containing this string." For renames that need to run outside an IDE, across many files, in CI, or language-agnostically, structural tools fill the gap: **ast-grep** matches and rewrites code based on the actual abstract syntax tree (via tree-sitter), so a pattern is written as ordinary-looking code but matched structurally rather than textually, which is precisely what prevents matching a string occurrence inside a comment, a different symbol, or an unrelated field [9]. **Comby** takes a more language-agnostic approach — structural rather than purely textual, but without deep syntax or type awareness — which trades precision for the ability to operate uniformly across many languages and even non-code formats like JSON or Markdown [9]. **Coccinelle**, used heavily in the Linux kernel, goes further still with a dedicated semantic patch language for expressing C-specific structural transformations that understand control flow; the kernel tree ships a collection of such semantic patches for exactly this kind of large mechanical change.

**Prose-aware renaming.** For specification documents and other prose, the equivalent of a structural code tool is a terminology linter. **Vale** implements a `substitution` rule type specifically for this: a rule defines a table mapping a banned or outdated term to its preferred replacement, and the linter flags every occurrence of the old term along with the preferred form, so a reviewer can check each hit rather than trusting a blind replace [8]. The same rule is a natural home for the **do-not-change allowlist**: Vale's substitution checks accept an `exceptions` list of strings to ignore, so the known-good occurrences (a quoted historical document, a different sense of the same word, an external product name you don't control) are recorded once instead of being rediscovered by a human re-reading the whole diff.

```yaml
# styles/Project/Terms.yml
extends: substitution
message: "Use '%s' instead of '%s'."
level: error
ignorecase: true
swap:
  channel key: session group
exceptions:
  - Channel Key API   # hypothetical third-party product name we do not control
```

**Residue checking.** The simplest and most durable check of all is a grep for the old term across the entire tree *after* the rename commit, compared against an explicit exception list of occurrences that are intentionally unchanged (the historical-record case, the genuinely different sense of the word, an external name). Anything that shows up in the grep but isn't on the exception list is residue — exactly the class of bug that stranded the old term in the overview document in the motivating example above. This check is nearly free to run and should be run on every rename, not just the risky-looking ones, because the overview-document failure mode specifically strikes documents that look too stable to need checking.

**Derived artifacts.** Diagrams, generated reference tables, and other artifacts that summarize the spec rather than define it should, where practical, be generated *from* the renamed source rather than hand-edited to match it — the UK Government Digital Service's internal standard on "diagrams as code" makes this argument directly: a hand-drawn diagram in a graphic editor lives in a different system from the text that describes it, nothing forces the two to stay in sync, and the fix is to keep the diagram's source as text (e.g., Mermaid) alongside the document it illustrates so it can be regenerated and reviewed like any other change [10]. A rename that updates the prose but leaves a hand-drawn diagram with the old label is functionally the same bug as the residue case, just in a format grep can't reach.

## Reviewing a rename

In the motivating example, an independent reviewer reading the rename commit on its own caught all three failure modes. That review generalizes into a small number of concrete practices, each of which targets at least one of them:

1. **Separate the rename from any semantic change.** A commit (or PR) that does nothing but rename should contain nothing but renaming. If a rename is bundled with a behavior change, a reviewer has to simultaneously verify two different kinds of correctness, and mistakes in either one hide behind the other.
2. **Write the mapping table down before touching anything.** Old term → new term, explicitly, plus a second list of "occurrences that look like the old term but must not change" — the component named "channel" that isn't the concept being renamed is exactly this second list's reason for existing. The mapping table is also the right place to record deliberate code/prose mismatches (like `groupName` in code vs. "session group" in prose) so a later reader finds the decision instead of re-discovering the confusion.
3. **Classify every hit, don't just replace every hit.** Each occurrence of the old term found by a search needs to be bucketed: rename it, leave it (on the do-not-change list), or flag it for a human decision because it's ambiguous. A tool that auto-applies without this classification step reproduces the mis-rename failure mode by construction.
4. **Check the new name against the existing namespace before adopting it.** The collision failure mode — a new short symbol landing on top of an existing one — is caught by one specific, cheap step: grep the proposed new identifier (and any short forms/abbreviations derived from it) against the current codebase and spec set *before* the rename lands, not after.
5. **Read the diff as a word-diff, not a line-diff.** A line-level diff on a document-wide rename shows mostly-unchanged lines as fully rewritten, which buries the one line where the replacement was wrong inside dozens of lines where it was fine. A word-level diff isolates exactly the changed tokens, making an incorrect substitution visually distinct from a correct one.
6. **Run a positive control.** Before trusting a review process (human or automated) to catch rename errors, deliberately plant one known bad substitution — a mis-rename on a homonym, or a collision with an existing name — and confirm the review step actually flags it. This is the same logic as mutation testing, where a code change is deliberately seeded into a program specifically to check whether the test suite notices; a "surviving mutant" means the suite has a blind spot exactly where the seeded bug was placed. Applied to review, a planted mis-rename that survives review tells you the review process — not just this particular rename — has a gap.

## Agent-specific considerations

Bulk mechanical renames are, on paper, exactly the kind of task an LLM agent should be good at: deterministic, high-volume, low-creativity. In practice, agents performing free-form renames tend to drift toward two specific failure patterns beyond the ones already described. First, **over-replacement**: an agent asked to rename a term will sometimes also "helpfully" rewrite nearby prose for clarity or consistency, which reintroduces exactly the semantic-change-bundled-with-rename problem the review discipline above is designed to prevent, except now it's distributed across many small, easy-to-miss edits instead of one obvious one. Second, **paraphrase instead of substitution**: rather than using the exact new term, a model will sometimes produce a near-synonym or a slightly reworded phrase that preserves the local meaning but breaks the project's ability to grep for the new canonical term later, which quietly reintroduces inconsistent terminology in the very documents meant to fix it.

A recent study of a multi-agent framework for coordinated renaming reports, in its ablation study, that disabling human feedback cut precision from 47% to 11% — roughly a 4x degradation — because the agents went on to rename many identifiers that should have been left alone [11]. The result reinforces that developer (or reviewer) oversight is not a redundant formality for this task but catches a real, recurring class of error that fully autonomous rename agents miss. The practical implication is not that agents shouldn't do renames, but that the review techniques above apply with extra force when the renamer is an agent:

- **Give the agent the mapping table and the do-not-change list explicitly, as input, not as something it infers.** An agent asked to "rename channel key to session group" without being told that "channel" has a second, unrelated meaning in the same documents has no way to discover that ambiguity reliably; an agent given the explicit do-not-change list for that second meaning can be checked against it mechanically.
- **Have an independent reviewer — ideally a separate agent invocation or a separate model from the one that performed the rename — check for meaning changes specifically**, not just for whether the new term appears. A reviewer prompted narrowly ("did any sentence's meaning change as a side effect of this substitution?") is doing exactly the classification work described above, and doing it as a dedicated pass catches what a single combined generate-and-check pass tends to miss.
- **Regenerate derived artifacts from source rather than asking the agent to hand-edit them.** If a diagram or summary table is derived from the spec, the safe move after a rename is to regenerate it from the renamed source, not to have the agent edit the diagram's own representation to match — the latter reintroduces the same sync risk diagrams-as-code is meant to eliminate [10], and an agent editing a diagram file is doing unreviewable work in a format a word-diff can't illuminate.
- **Apply the positive-control check to the agent's own output before trusting it on a real rename.** Plant a known ambiguous term or an identifier collision in a test document, run the agent's rename process against it, and confirm the agent (or its reviewer pass) actually catches it — the same discipline recommended for human review processes applies without modification to agent pipelines, and arguably matters more, since an agent has no instinct that something "feels off" the way a human skimming a familiar document sometimes does.

## Checklist

- Write the old→new mapping table and a separate do-not-change list *before* making any edits.
- Check the new name/symbol against every existing identifier and short form already in scope.
- Keep the rename in its own commit, with zero semantic changes bundled in.
- Classify every hit from a search for the old term — rename, leave, or flag — rather than blanket-replacing.
- Review the diff as a word-diff, and specifically re-read every sentence containing a homonym of the old term.
- Explicitly check the overview/summary document, not just the detailed specs — it's the one most likely to be skipped.
- For code/schema/config/CLI renames, use expand → migrate → contract: add the new name, dual-read/dual-write during migration, remove the old name only once nothing depends on it.
- Use deprecation aliases with warnings (e.g., a `#[deprecated]`-style annotation or equivalent) rather than a hard break, wherever the rename crosses a public interface.
- Leave historical records — changelogs, closed tickets, old release notes — untouched; annotate new documents instead of editing old ones.
- Prefer structural tools (LSP rename, ast-grep, Coccinelle) over text search-and-replace for code, and a terminology linter (e.g., Vale substitution rules) with an exception list for prose.
- Regenerate diagrams and other derived artifacts from the renamed source rather than hand-editing them.
- Run a residue grep for the old term after the rename lands, reconciled against the do-not-change list.
- Plant a positive control — a deliberate mis-rename or collision — and confirm your review process (human or agent) actually catches it before relying on that process for the real thing.
- If an AI agent performs the rename, give it the mapping table and do-not-change list as explicit input, and route the result through an independent reviewer pass focused specifically on meaning changes, not just term coverage.
