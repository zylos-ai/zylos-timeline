## Executive Summary

As AI coding agents move from suggesting diffs to autonomously cloning repositories, writing commits, and opening pull requests, the question of *how an agent authenticates to GitHub* has become a first-class security and governance decision, not an implementation afterthought. GitHub offers five distinct identity primitives for machine-driven git activity — personal access tokens (classic and fine-grained), dedicated "machine user" accounts, deploy keys, GitHub App installations, and OIDC federation — and each carries different guarantees around scoping granularity, credential lifetime, attribution, rate limits, licensing, and auditability.

The trajectory across the industry is converging on one answer for agents that write code across many repositories on an ongoing basis: **GitHub App installations, minting short-lived (1-hour) installation access tokens server-side, with the agent's commits attributed to a distinct `<slug>[bot]` identity.** This is what GitHub's own Copilot coding agent does, what Renovate recommends over its legacy PAT mode, what Dependabot's underlying architecture resembles, and what a growing number of third-party agent platforms (Devin, Cursor's background agents, and various in-house "agent identity" systems) have converged on or are actively migrating toward. Personal access tokens remain useful for individual developer tooling and quick prototypes but are increasingly discouraged for any unattended or multi-repo agent, because a leaked classic PAT hands an attacker everything the underlying human account can see — with no expiry. OIDC federation, meanwhile, has become the default answer for the adjacent problem of an agent (or its CI job) needing to reach *other* systems — clouds, package registries, secrets managers — without storing a static credential at all.

This report surveys the identity landscape, the mechanics of GitHub App token minting and commit attribution, how today's major AI coding agents implement (or fail to implement) clean machine identities, the security failure modes specific to bot-driven git workflows, and the nascent — and contested — conventions emerging for marking AI-authored commits (`Co-Authored-By`, `Assisted-by`, and proposals for dedicated provenance trailers).

## Identity Models on GitHub: A Comparative Landscape

GitHub recognizes several distinct ways for a non-interactive actor to authenticate and take action, and they are not interchangeable — each was designed for a different trust relationship.

**Personal access tokens (classic).** Classic PATs (prefix `ghp_`) are bearer credentials scoped to a fixed set of broad OAuth-style scopes (`repo`, `workflow`, `admin:org`, etc.) and inherit the *entire* visibility of the issuing human account — every organization and repository that account can see, public or private. They have no forced expiration unless the user sets one manually. GitHub's own guidance is now that classic PATs should be reserved for legacy integrations, Gists, and Packages access, and phased out elsewhere.

**Personal access tokens (fine-grained).** Introduced to address the blast-radius problem, fine-grained PATs let the issuer pick a specific set of repositories ("only select repositories") and assign each of roughly 50+ permission categories (Contents, Pull requests, Issues, Actions, etc.) an independent no-access/read/read-write level. They cap out at a 366-day maximum lifetime, and up to 50 tokens per user. This is a real improvement, but the token is still tied to a human account's identity for attribution and review purposes, and it still requires manual rotation.

**Deploy keys.** An SSH key pair registered against a single repository, optionally read-only. Deploy keys have no API surface at all — they only grant `git clone`/`push` over SSH to that one repo — which makes them a narrow, low-blast-radius option for single-repo pull/push automation, but unsuitable for anything that also needs to open PRs, comment, or manage checks via the REST/GraphQL API, since a deploy key carries no API scope. They also don't expire and must be manually revoked.

**Machine user accounts ("bot accounts").** A regular GitHub account, but one that GitHub's Terms of Service specifically permit to exist for automation, provided a real human accepts the ToS on its behalf and remains responsible for its actions. Historically this was the default way to give a CI system or bot "its own identity" distinct from any engineer's personal account — teams create `myorg-bot`, generate a PAT or SSH key under that account, and grant it collaborator access. The approach is now explicitly discouraged in most modern guidance: it consumes a paid per-seat license on GitHub Enterprise plans (a "User" is defined to include machine accounts), requires manual credential rotation exactly like a PAT, and produces commits attributed to what looks like — and functionally is — a regular user account rather than a clearly-marked integration.

**GitHub App installations.** A GitHub App is registered independently of any user, with its own declared permission manifest (e.g., Contents: read-write, Pull requests: read-write, Issues: read) and its own webhook/event subscriptions. An organization or repository owner *installs* the app, at which point GitHub mints a dedicated `<slug>[bot]` machine identity (a real user ID, just suffixed `[bot]`) that owns all activity the app performs. Crucially, the app itself authenticates as its long-lived identity only via a JWT signed with its private key; every actual git/API operation uses an **installation access token that GitHub mints on demand and that expires in one hour.** Because the app's permission manifest, its per-installation repository selection, and (since GitHub's May 2026 "per-request override header" change) even further per-request permission narrowing all apply *before* a token is minted, GitHub Apps give the tightest and most automatable scoping of any identity type, without a human account or manual PAT rotation in the loop.

**OIDC federation.** Not a GitHub-side identity for authenticating *to* GitHub, but the now-standard way for a GitHub Actions job (or increasingly, other CI/agent runtimes) to authenticate *outward* to a cloud provider, package registry, or secrets manager without storing any long-lived secret at all. GitHub issues a short-lived, workflow-scoped OIDC JWT (requires `id-token: write` permission) that the remote party's trust policy verifies against claims like repository, ref, and workflow name, then exchanges for temporary cloud credentials. Since February 2026, even Dependabot itself supports OIDC to reach package registries. OIDC is the complementary half of the identity story: GitHub Apps solve "how does the agent authenticate *into* GitHub," OIDC solves "how does the agent (or its CI shell) authenticate *out* to everything else."

## How GitHub Apps Attribute Commits and Pull Requests

When a GitHub App installation performs an action, GitHub does not attribute it to the app's own developer account or to whichever human clicked "Install" — it attributes it to a synthetic **bot user**, named `<app-slug>[bot]`, that GitHub provisions automatically the first time the app is installed anywhere. This identity has its own numeric GitHub user ID, separate from the App ID found in the app's settings page — a distinction that trips up almost everyone building this for the first time.

**The noreply email format.** To make a commit authored by the app show the `[bot]` badge and link back to the bot's profile, the commit's author/committer email must be:

```
<BOT-USER-ID>+<app-slug>[bot]@users.noreply.github.com
```

For example, GitHub's own Actions runner commits use `41898282+github-actions[bot]@users.noreply.github.com`. The `41898282` is *not* the app's registration ID — it's the bot account's user ID, retrievable via `GET /users/<app-slug>[bot]` (i.e. `curl https://api.github.com/users/<app-slug>%5Bbot%5D`). Using the wrong ID (or the app's own App ID) still produces a valid, pushable commit — it just renders as an ordinary unverified commit with no bot badge, silently defeating the point of using an App identity in the first place.

**Verified/signed commits.** There are two distinct paths to a green "Verified" badge:
1. *Git-level GPG/SSH signing*, where the pusher generates a key, registers the public half on the bot or app's account, and signs each commit locally before `git push` — this is what dedicated machine-user setups (e.g., Devin's `devin@company.com` account) typically do, and it requires ongoing key custody.
2. *API-authored commits via the GraphQL `createCommitOnBranch` mutation* (or the REST Contents API), where GitHub itself authors the commit server-side from the supplied file changes and **automatically GPG-signs it as verified**, extracting authorship information from the authenticating credential — no client-side signing key required at all. This is the practical reason many GitHub App–based bots (Renovate, Copilot coding agent, various in-house systems) prefer creating commits through the API rather than `git push`-ing locally staged commits: verification comes for free, and there's no GPG key to provision or rotate.

**Co-authorship conventions layered on top.** Independent of *who* the commit is attributed to at the git-author level, tools also append trailers to the commit message body to disclose AI involvement. GitHub, GitLab, and most git UIs render a recognized `Co-authored-by: Name <email>` trailer as an additional avatar next to the primary author — a convention that predates AI and was designed for human pair-programming. Claude Code, by default, appends `Co-Authored-By: Claude <noreply@anthropic.com>` to commits it creates on a user's behalf (configurable/removable), and OpenAI's Codex CLI shipped an equivalent `commit_attribution` feature (merged February 17, 2026) that adds a comparable trailer. This is a *convention layered on top of* — not a substitute for — the git author identity: the app/bot identity establishes who technically has push authority and produced the artifact; the trailer discloses AI assistance to human reviewers reading the log.

## Installation Token Mechanics

The concrete flow that turns "an app is installed" into "an agent can `git push`" has four steps:

1. **Generate a JWT for the App itself.** Using the app's RS256 private key, construct a JWT with `iat` (issued-at, recommended to be set ~60 seconds in the past to tolerate clock drift), `exp` (expiry, must be ≤10 minutes from `iat`), and `iss` (the App ID). This JWT proves "I am App #X," not "I may act on repo Y" — it has no repository or permission scope of its own.
2. **Exchange the JWT for an installation access token.** `POST /app/installations/{installation_id}/access_tokens`, authenticated with `Authorization: Bearer <JWT>`. The request body can optionally pass a `repositories`/`repository_ids` array to scope the resulting token to a *subset* of the repos the installation covers, and a `permissions` object to request a *subset* of the app's declared permissions — both narrower-than-installed, never broader. This is the key scoping lever: a server minting tokens for many agent workspaces can hand each workspace a token that only covers the one repo it's working in, even though the underlying installation may span an entire org.
3. **Receive a token good for exactly one hour.** The response includes the token string and an `expires_at` timestamp; using it past expiry returns `401 Unauthorized`, and there's no refresh call — the caller just repeats step 2. Well-behaved clients (Octokit, and the widely used `actions/create-github-app-token` Action) handle this transparently; hand-rolled integrations typically build a small caching layer that re-mints ~5 minutes before expiry.
4. **Use the token for git and the API.** For the REST/GraphQL API, it's a standard `Authorization: token <token>` (or `Bearer`) header. For `git` itself over HTTPS, GitHub App installation tokens work as the password half of basic auth with the literal username `x-access-token`:
   ```
   git clone https://x-access-token:<INSTALLATION_TOKEN>@github.com/owner/repo.git
   git -C repo push https://x-access-token:<INSTALLATION_TOKEN>@github.com/owner/repo.git HEAD:main
   ```
   Community credential-helper implementations (e.g. `bdellegrazie/git-credential-github-app`) wrap this into a standard git credential helper, often combined with `useHttpPath = true` and `git-credential-cache`, so that per-repo remotes automatically resolve to the right installation without embedding a token in the remote URL at all — useful when an agent's workspace touches several repos under different installations.

Because minting happens server-side against a private key that the agent process itself never needs to see, this flow cleanly separates "the thing with long-term custody of a secret" (a token-minting service) from "the thing running arbitrary, possibly-compromised agent code" (the agent's sandbox) — the agent only ever holds a token that is worthless again within the hour and scoped to (at most) one repository.

## Industry Practice: How AI Coding Agents Actually Do This Today

**Dependabot** doesn't push with a conventional credential at all in the way a third-party bot does — dependency-update commits happen through GitHub's own backend on the `dependabot[bot]` identity, and its GitHub Actions integration (for private registry access, custom compute, etc.) runs with a default *read-only* `GITHUB_TOKEN` and, as of February 2026, can additionally use OIDC to reach external package registries without static registry credentials.

**GitHub Copilot coding agent** is the clearest large-scale example of the GitHub-App-first pattern: it operates under its own bot identity, commits are automatically signed and show as "Verified," and — notably — each agent-authored commit message includes a link back to the full agent session log, giving reviewers permanent provenance from a diff to the reasoning that produced it. Scoping is aggressive by default: the agent can only access the single repository it was invoked on, can only push to a new `copilot/…`-prefixed branch or the existing PR branch it was invited into, cannot push to protected/ruleset-enforced branches, and only receives secrets explicitly added to a dedicated `copilot` Actions environment rather than the repo or org's general secret store.

**Renovate** historically ran on a maintainer's PAT but now documents and increasingly recommends a GitHub App–based deployment for exactly the reasons above: permissions "tune" more precisely than a user-tied PAT, PRs are attributed to the app rather than an individual, and the bot keeps functioning if the human who originally set it up leaves the org. Renovate's docs also show the git-author-identity pattern directly — configuring `gitAuthor` to the `<bot-id>+<username>@users.noreply.github.com` form described above.

**Devin** takes a different path: it provisions a genuine dedicated machine-user account (e.g. `devin@company.com`) rather than a `[bot]`-suffixed App identity, and achieves "Verified" commits the git-native way — generating a GPG key locally, uploading the public key to that machine account, and ensuring the committer email matches a verified email on the account. This is functionally closer to the traditional "machine user" model than to the GitHub App model, trading some of the automatic scoping/expiry benefits of App tokens for simplicity of setup and a persistent, human-legible identity that behaves like a regular collaborator (useful, e.g., where org policy or third-party tool integrations still expect a "real user" rather than a bot).

**Cursor's background/cloud agents** connect via a GitHub App installed on the target org, following least-privilege principles for the requested permission set; commits and PRs the agent creates can carry an automatic "Made with Cursor" attribution trailer. Community reports note some rough edges typical of a maturing integration — e.g., agents spawned via API sometimes getting git push/pull access without matching PR-comment/review API permissions, and confusion in personal-account installations (which grant API permissions but not full collaborator-equivalent PR rights the way an organization installation does).

**Claude Code's GitHub integration** (`claude-code-action`) supports GitHub App installation as its primary connection mode for the `@claude` GitHub Actions workflow (alongside PAT-based setups for simpler cases), requests only the permissions the workflow declares (typically `contents: write`, `pull-requests: write`, `issues: write`), signs the commits it creates, and — as noted above — appends a `Co-Authored-By: Claude` trailer to the commit body by default, separate from and in addition to the git-level author/committer identity used to push.

**OpenAI's Codex** has been actively building out a dedicated "agent identity" concept in its own codebase (feature-flagged as `use_agent_identity`, with ChatGPT-derived runtime auth provisioning), suggesting the ecosystem is converging on treating the *agent itself* — not just the human operating it, and not a generic bot account — as a first-class identity to be authenticated and audited independently.

## Security Considerations

**Blast radius of a leaked credential** is the dominant axis separating these identity types in practice. A leaked classic PAT is catastrophic and silent — full read/write on every organization and repository the issuing human can see, with no expiry, until someone notices and manually revokes it. A leaked fine-grained PAT is contained to its declared repos but can still live on disk for up to a year. A leaked GitHub App installation token is, by construction, worthless within an hour and was never broader than the one installation (and often the one repo) it was minted for — the meaningful secret to protect is the App's *private key*, held only by the server that mints tokens, not by any individual agent workspace.

**Confused-deputy risk** shows up specifically around token minting: a service that mints installation tokens on behalf of many callers/tenants must make sure it hands out a token scoped to *that caller's* authorized repo(s), not the full breadth of what the installation is permitted to touch — otherwise workspace A's agent can be tricked (or can simply err) into acting on workspace B's repository through a token that was technically valid but never should have been minted that broad. This is the direct analog of over-broad OAuth scope requests, and GitHub's own guidance stresses minting the narrowest `repositories`/`permissions` subset per request rather than reusing one org-wide token everywhere.

**Private-key custody** is the App's single point of failure: GitHub allows up to 25 concurrently valid private keys per App specifically so operators can rotate without downtime (generate the new key, redeploy consumers, then revoke the old one — GitHub won't let you revoke the last remaining key), and best practice is to keep the key in a proper secrets manager (Vault, cloud KMS, etc.) rather than in repo secrets or environment files baked into an agent's own sandbox image.

**Branch protection and rulesets** need explicit interplay design: GitHub's newer repository rulesets support a "bypass list" that can name specific GitHub Apps (in addition to roles/teams), letting a bot skip required-status-check enforcement while still being blocked from destructive actions like force-push or branch deletion if those are layered into a *second*, empty-bypass-list ruleset. The safer default emerging across Copilot's coding agent and most serious internal deployments is to *not* put the agent on any bypass list at all — require it to open a PR like any other contributor and let normal required reviews/checks gate the merge, reserving direct-push bypass only for narrowly scoped, non-default branches (e.g., the agent's own `agent/*` working branches).

**Audit-log visibility** is materially better with GitHub Apps: GitHub Enterprise's audit log records the `token_id` and a `hashed_token` (never the raw token) alongside each action, so if a token is suspected compromised, every action it performed can be enumerated precisely — and because App tokens are short-lived and narrowly scoped by construction, the compromise window and blast radius visible in that log are both naturally small compared to a long-lived PAT or machine-user credential doing the same volume of work.

## Emerging Standards and Discussion

Attribution conventions for AI-authored commits are actively contested, not settled. `Co-Authored-By` — a trailer designed for human pair-programming — has become the de facto default (used by Claude Code, and adopted by OpenAI's Codex CLI via a February 2026 PR) largely because it was already universally rendered by GitHub/GitLab UIs. But a visible backlash has formed: several open-source projects (Mesa, Kubernetes, pip, Requests, attrs) now explicitly forbid using `Co-Authored-By` for AI tools, reserving it for genuine human collaborators, and a number of practitioners argue the trailer is semantically wrong for a non-deterministic, unaccountable tool and are proposing dedicated alternatives — e.g. separate `Coding-Agent:`/`Model:` trailers that identify the specific tool and model version rather than borrowing the co-author slot, or a generic `Assisted-by:` trailer (the convention Artsy's community RFC converged on in mid-2026) that discloses "significant LLM assistance" without implying joint authorship. None of this is standardized at the git or GitHub-platform level yet — it remains project-by-project convention enforced through CONTRIBUTING.md and CI linting rather than tooling.

At the supply-chain-security layer, the more rigorous alternative to a commit-message trailer is cryptographic: **Sigstore's `gitsign`** enables keyless commit signing using ephemeral certificates issued by Fulcio based on an OIDC identity (GitHub Actions' own OIDC token, in CI) and logged tamper-evidently in Rekor, so that a commit's "verified" status is backed by a transparency-log entry tied to a specific CI identity and run rather than a long-lived GPG key an operator must protect forever. This composes naturally with GitHub Apps and OIDC-federated CI: the workflow identity that already exists for cloud-credential exchange doubles as the signing identity, with no additional key management. Separately, **SLSA provenance / GitHub artifact attestations** are moving from opt-in to default for build artifacts on public repos, tying an artifact's hash to the exact workflow run, commit, and OIDC claims that produced it — the same primitive that, extended to *commits* rather than *build artifacts*, is what several of the trailer proposals above are informally reaching for without yet having the cryptographic backing SLSA/Sigstore already provide for builds. As of September 2026 there is no single ratified standard for "AI agent commit provenance," but the direction of travel — distinct bot identity for push authority, disclosure trailer for human legibility, and (increasingly) keyless cryptographic signing for verifiability — is visible across nearly every serious implementation surveyed here.

## Key Takeaways for Agent Builders

- **Default to a GitHub App per agent product/tenant, not a shared PAT or machine-user account.** It is the only model that gives short-lived tokens, per-request repo/permission narrowing, automatic rotation, a distinct `[bot]` identity, and no per-seat licensing cost — and it is what GitHub's own Copilot coding agent, Renovate's recommended deployment, and most maturing third-party agents are converging on.
- **Mint installation tokens server-side, never inside the agent's own sandbox.** Keep the App's private key in a secrets manager behind a minting service that hands each agent workspace a token scoped (via the `repositories`/`permissions` fields on the token-mint call) to only what that workspace needs — this is the concrete defense against confused-deputy leakage between tenants/workspaces and caps leaked-token blast radius to one hour and one repo.
- **Get the bot user ID right, not the App ID, for commit email.** Use `<bot-user-id>+<app-slug>[bot]@users.noreply.github.com`, fetched once via `GET /users/<app-slug>[bot]`, or commits will still push successfully but silently lose the `[bot]` badge and attribution.
- **Prefer API-authored commits (`createCommitOnBranch`/Contents API) over locally `git`-signed commits when verification matters** — GitHub signs and verifies these automatically from the authenticating installation token, eliminating GPG key custody entirely; reserve local commit + `git push` for cases needing full local control over the working tree.
- **Require PRs, don't bypass-list the agent.** Keep agent identities off branch-protection/ruleset bypass lists for default branches; let normal required reviews and checks gate merges, and scope any bypass privileges narrowly (agent-owned working branches only) if granted at all.
- **Layer a disclosure trailer on top of the identity, and expect it to be contested.** `Co-Authored-By` is the path of least resistance but is explicitly rejected by a growing list of major projects; consider a dedicated `Assisted-by:`/`Coding-Agent:`-style trailer instead, and make it configurable — the convention is still being fought over in public as of this writing, not settled.
- **Treat OIDC as the answer to the adjacent problem, not a substitute.** GitHub Apps authenticate the agent *into* GitHub; OIDC federation is how the agent's CI/runtime authenticates *out* to clouds, registries, and secrets managers without a second static credential to leak.
- **Use the enterprise audit log's `token_id`/`hashed_token` fields as your incident-response hook** — design the minting service to log which token (by ID, not value) was issued to which workspace/request, so a suspected-compromised token can be traced to exactly what it did and revoked without guesswork.
