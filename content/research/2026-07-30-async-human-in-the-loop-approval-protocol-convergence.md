## Executive Summary

Every autonomous agent runtime eventually hits the same wall: some action is too consequential to execute without a human saying yes, but the agent cannot afford to sit there holding a connection open and waiting. Two days before this research was written, the Model Context Protocol shipped a spec revision (2026-07-28) that rebuilds its entire approach to this problem — and in doing so, it converges almost exactly with three other lineages that arrived at the same design independently: Google's Agent2Agent (A2A) protocol, the OAuth world's Client-Initiated Backchannel Authentication (CIBA), and LangGraph's `interrupt()` primitive. All four now express the same shape: an action pauses, the system hands back a durable, resumable handle instead of blocking a socket, a human answers on their own schedule through an out-of-band channel, and the original call picks up exactly where it left off — sometimes hours or days later.

This is not a coincidence of naming. It is convergent evolution forced by the same constraint: agents that run unattended, in schedulers, in pipelines, or across process restarts cannot use the web's default confirmation model — a modal dialog blocking a single browser tab — because there may be no tab, no session, and no guarantee the process asking the question is still alive by the time the human answers. The protocols examined here differ in transport and vocabulary but agree on the architecture: separate "may I ask you something" from "here is my answer," and make both sides independently resumable.

The second half of this research is less comfortable. Making approval asynchronous does not make it safe — it can make it worse. A 2026 empirical study of 11,429 code reviews across 400 reviewers found approval rates climbing 14.5 percentage points across a reviewer's experience deciles while active scrutiny fell, a habituation effect distinct from and additional to any change in the underlying agent's actual reliability. Async approval queues that decouple "ask" from "answer" also decouple urgency from attention: a human who is not blocked by the pending question has no forcing function to look at it carefully, and organizations report exactly the failure mode the protocols were built to avoid — approval becoming a reflex click rather than a decision. This piece covers both halves: the protocol mechanics that make non-blocking approval possible, and the sociotechnical design choices that determine whether it stays meaningful once volume grows. It closes by mapping the pattern directly onto Zylos's own operating rules, which already implement an ad hoc version of this architecture through the C4 communication bridge.

## 1. Why the Naive Approach Breaks

The obvious way to ask a human for confirmation is synchronous: the agent pauses its own execution thread, sends a message, and blocks on the response. This is how almost every tutorial-grade agent demo implements "human-in-the-loop," and it fails in production for reasons that have nothing to do with the quality of the underlying model:

- **The agent may not be the same process by the time the answer arrives.** A scheduled task, a serverless function, or a container that gets rescheduled cannot assume the thread that asked the question is the thread that will receive the answer.
- **Humans do not operate on request/response latency.** A confirmation that takes ninety seconds is annoying for a chat UI and catastrophic for a held-open HTTP connection, a load balancer with a 30-second idle timeout, or a serverless function paying for wall-clock compute time while it waits.
- **"Block and wait" doesn't compose.** An agent orchestrating five parallel sub-tasks, three of which each need a different human's sign-off, cannot literally block three threads for three different response times without either abandoning concurrency or building ad hoc plumbing to fake it.
- **The channel the human is available on (Telegram, Slack, email, a push notification) is not the channel the agent's execution engine speaks natively.** Something has to translate between "waiting HTTP request" and "message in a chat app," and that translation layer needs its own durability story — if the process holding the HTTP request dies, the pending approval must not vanish with it.

The practical answer that has emerged, independently, across every major agent protocol in the last year, is to stop trying to hold a connection open at all. Instead: return a durable *handle* representing "this specific point in this specific action is paused," send a human-readable question through whatever channel actually reaches a human, and let the answer arrive on a completely different message, at a completely different time, from a completely different process, correlated by the handle rather than by the connection.

## 2. MCP's Answer: From Held-Open Streams to Stateless Multi Round-Trip Requests

The Model Context Protocol's elicitation feature — servers asking the client (and, through it, the user) for information mid-tool-call — existed since mid-2025, but its 2026-07-28 specification release rebuilt the mechanism from the ground up as part of a broader shift: MCP moving from a stateful, bidirectional, session-based protocol toward a stateless request/response model that drops the `initialize`/`initialized` handshake and the `Mcp-Session-Id` header entirely, so that any request can land on any server instance behind a load balancer without shared session storage.

The elicitation mechanism that falls out of this shift is called Multi Round-Trip Requests (MRTR), and it replaces the old approach — a server-initiated request over a held-open Server-Sent-Events stream — with something closer to an HTTP-native retry loop:

1. The client calls a tool normally: `tools/call`.
2. If the server needs more information, it does not hold the connection open. It returns an `InputRequiredResult` containing one or more `elicitation/create` requests and an opaque `requestState` blob.
3. The client presents whatever UI it wants for the requested input, collects `inputResponses`, and **re-issues the original call**, echoing back the `requestState`.
4. Because everything the server needs to resume is encoded in the request payload rather than in server-held session memory, *any* server instance — not necessarily the one that issued the original `InputRequiredResult` — can pick up the retry and continue. This is the detail that makes the whole thing compatible with stateless, horizontally scaled deployments: the pause-point survives a load balancer routing the retry to a different machine.

Elicitation requests come in two modes, and the distinction is a direct answer to a security failure mode that the earlier, simpler design invited:

- **Form mode** collects structured data directly through the MCP client, validated against a deliberately restricted JSON Schema subset (flat objects, primitive fields only — strings, numbers, booleans, and single/multi-select enums, with typed formats like `email`, `uri`, `date`). The restriction to flat, primitive schemas is itself a design decision in service of a specific goal: making it tractable for *any* MCP client to auto-generate a reasonable form UI without needing a general-purpose JSON Schema renderer.
- **URL mode**, introduced in the 2025-11-25 revision, sends the user to an external URL for anything sensitive — credentials, payment details, third-party OAuth consent — specifically so that data never transits the MCP client or the LLM's context window at all. The spec is emphatic on this point: servers **MUST NOT** use form mode to request passwords, API keys, or payment credentials, and **MUST** use URL mode instead.

Every elicitation response, in either mode, resolves to one of exactly three actions: `accept` (explicit approval, with data on form-mode accepts), `decline` (explicit "no"), or `cancel` (the user dismissed without choosing — closed the dialog, hit escape, or the client failed to render it). Collapsing every possible human interaction into this three-way vocabulary is a deliberate simplification: it forces every server implementation to handle "the user actively said no" and "the user just walked away" as distinct, both-required cases, rather than letting servers conflate silence with rejection or vice versa.

The security section of the spec is worth reading in full for anyone building an approval layer on top of MCP, because it works through a genuinely subtle attack it is designed to prevent: a phishing scenario where a malicious user (Alice) triggers a URL-mode elicitation on a benign server, then tricks a different, victim user (Bob) into clicking the resulting link. If the server does not verify that the user who *completes* the out-of-band flow is the same user who *started* it — typically by requiring a session cookie bound to the same subject claim used to authenticate the original MCP session — the third-party tokens obtained get bound to Alice's identity while Bob believes he authorized his own connection, resulting in an account takeover. The spec's mitigation (bind the elicitation to a server-verified user identity, never trust a client-asserted "I am `user@example.com`") generalizes directly to any system building async approval on any channel: the answer must be cryptographically or session-bound to the same principal who asked, not merely to "someone who clicked the link."

## 3. MCP Tasks: Call-Now, Fetch-Later for Work That Isn't Waiting on a Human

Elicitation solves "the server needs input from a person." A sibling extension, Tasks — experimental since the 2025-11-25 revision and formalized into MCP's extensions framework in the 2026-07-28 release — solves the adjacent but distinct problem of work that simply takes a long time with no human in the loop at all: a large data export, a multi-minute build, a slow third-party API. Instead of blocking the caller, the server returns a durable task handle immediately; the client polls `tasks/get` at a server-suggested interval, or calls `tasks/list` to rediscover in-flight tasks after a crash or restart, and retrieves the result once it is ready. The design principle is the same one underneath elicitation — never hold a connection open for something that might take an unpredictable amount of time — applied to compute latency instead of human response latency. Together, elicitation/MRTR and Tasks give MCP a complete answer to "the tool call didn't finish synchronously," whether the reason is "waiting on a person" or "still computing."

## 4. A2A: The Same Shape, Different Vocabulary

Google's Agent2Agent protocol — transferred to Linux Foundation governance in mid-2025 for vendor-neutral stewardship — was designed from the outset around long-running, potentially cross-organization delegated tasks, and it converges on essentially the same architecture MCP arrived at from a different direction. An A2A task is an explicit state machine with terminal and interrupted states, and two of those states are `input_required` and `auth_required`: a delegated task can run for minutes or hours, hit a point where it needs a human answer, and stop — cleanly, with its state durably persisted — rather than blocking a connection. The task resumes from the same task ID whenever the answer arrives, even days later. For delivery, A2A explicitly supports both a streaming mode (while a client stays connected) and asynchronous push notifications for clients that cannot or should not hold a connection open at all, which is the same call-now/notify-later shape CIBA and MCP Tasks use for the "how does the answer actually get delivered" half of the problem.

The practical implication of two independently governed protocols (MCP under Anthropic-led stewardship with broad multi-vendor adoption, A2A under the Linux Foundation) landing on the same `paused-with-durable-handle → out-of-band signal → resume-by-handle` shape is that this is not an implementation detail any one vendor got clever about — it is close to the only architecture that satisfies the actual constraint set (stateless-friendly, crash-resumable, transport-agnostic for the human-facing side).

## 5. The OAuth World Already Had an Answer: CIBA

Before either MCP or A2A existed, the OAuth ecosystem had already solved a structurally identical problem for a different reason: how does a device with no browser — a smart speaker, a point-of-sale terminal, a call-center agent's backend — get a user to approve access without a redirect-based flow. The answer, standardized as Client-Initiated Backchannel Authentication (CIBA, RFC 9126), decouples "the entity requesting authorization" from "the entity that authenticates," and it is now being explicitly repurposed for AI agent approval because the shape matches almost exactly:

1. The agent identifies an action needing approval and sends a backchannel request to an authorization server, carrying a **human-readable binding message** describing the specific action — not an abstract scope.
2. The authorization server notifies the actual human out-of-band (push notification, app, SMS).
3. The human approves or denies on their own device, on their own schedule, with no redirect back to whatever initiated the request.
4. The agent receives a scoped token once approved and proceeds.

CIBA defines three response-delivery modes that map directly onto the tradeoffs any async approval system has to make: **poll mode** (the agent repeatedly checks — simplest to implement, but it reintroduces a busy-wait if implemented naively), **ping mode** (the authorization server calls back a webhook once the human responds — the most practical fit for agent workloads, since the agent does other work and only reacts when notified), and **push mode** (the token is delivered directly to a callback with lowest latency, at the cost of more infrastructure). The detail worth internalizing from CIBA's design, independent of protocol choice: the binding message shown to the human must be specific to the action ("Approve refund of $240 to order #8821"), not a scope description ("payments:write"). A human cannot meaningfully consent to a category; they can only meaningfully consent to a described action. This single design rule — specific over abstract — recurs across every well-designed approval system examined in this research and is one of the few points where sloppy implementations reliably fail.

## 6. The Framework Layer: LangGraph's `interrupt()` and the Idempotency Trap

One level below the wire protocols sits the orchestration framework, and LangGraph's `interrupt()` primitive is the most widely deployed example of making this pattern ergonomic for agent developers rather than protocol implementers. Calling `interrupt()` inside a graph node causes LangGraph to persist the full graph state via its checkpointer and pause indefinitely; a human response resumes the graph from that exact point, and if the process crashes while waiting, restarting the application and reloading the checkpoint recovers the pending interrupt with no special-casing.

The subtlety worth flagging, because it is the kind of thing that looks correct until it silently corrupts data in production: **the node containing the interrupt reruns from the top on resume**, replaying whatever code executed before the interrupt call within that node, and only short-circuits at the interrupt itself once it reaches the same point. If a node calls an external API and *then* calls `interrupt()` to confirm the result, resuming after the human answers re-executes the API call — not just the confirmation. The correct pattern places side-effecting work either entirely before the node containing the interrupt (in a separate, already-completed node) or entirely after it (gated on the human's answer), never straddling the interrupt boundary within a single node. This is the same idempotency discipline that durable-execution frameworks require everywhere else, but it is easy to violate specifically at approval boundaries because the code reads naturally as "do the risky thing, then double check with a human" — exactly the ordering that replays the risky thing on every resume.

## 7. The Part the Protocols Don't Solve: Approval Fatigue

Making approval non-blocking removes the *architectural* excuse for skipping human review — an agent no longer needs to auto-approve just because a human isn't available synchronously. But it does not touch the *behavioral* failure mode, which several independent 2026 studies now document with real numbers rather than anecdote.

A longitudinal study of code review behavior — 11,429 reviews across 400 repeat reviewers — found a statistically significant 14.5-percentage-point increase in approval rates across a reviewer's experience deciles specifically for AI-agent-authored submissions, paired with a decline in change-request rates, while time spent "in queue" per review rose and time spent actively inspecting fell. The authors frame this as habituation: familiarity with a steady stream of plausible-looking agent output erodes scrutiny in a way that is separable from, and can mask, any actual change in the agent's reliability. Put plainly — approval rates going up does not mean the agent got safer; it can mean the reviewer got tired of looking closely.

Separately, 2026 security research (WitnessAI) surveying human-in-the-loop controls in production agent deployments identifies the same pattern from the governance side and names two additional failure modes worth designing against explicitly: **"YOLO mode" bypasses**, where teams grant standing convenience overrides for exactly the highest-risk action categories (code modification, system access, data deletion) that approval gates exist to catch, defeating the control at the policy layer rather than the behavioral one; and **narrow instruction-following damage**, where an agent executes precisely what it was told, technically correctly, while missing broader context a human would have caught — a failure mode approval gates only catch if the approver is actually engaging with the specific request rather than pattern-matching "this looks like the last hundred requests."

The throughline across both studies is the same: async, durable, resumable approval infrastructure is a necessary but not sufficient condition for meaningful human oversight. The infrastructure determines whether asking is *possible* without blocking the system. It says nothing about whether the answer, once given, reflects genuine judgment rather than reflex.

## 8. Design Patterns That Keep Approval Meaningful at Volume

Synthesizing across the protocol layer and the fatigue research, four concrete, load-bearing design choices recur in systems that avoid the reflex-approval failure mode:

- **Trigger on risk signals, not action categories.** A fixed rule like "always ask before any file deletion" scales the queue linearly with agent activity and guarantees fatigue once volume grows past a reviewer's real attention budget. Routing based on computed risk (blast radius, reversibility, novelty relative to the agent's recent history) keeps the queue small enough that each item still gets real attention, and is the single mitigation both the fatigue study and the security research converge on independently.
- **Specific, action-bound messages — never scope-bound.** CIBA's binding-message requirement generalizes: "delete `/backups/2025-Q4/`, 340 files, no recent access" is a decision a human can actually make; "grant filesystem:write" is not. Every approval prompt should describe the specific consequence, not the permission class.
- **Default-deny on timeout, with visible SLA.** An unanswered approval request must not silently either proceed or hang forever; a bounded timeout that fails closed is the only choice consistent with treating the human's silence as "no answer" rather than implicit consent — and it also protects against exactly the crash-and-orphan scenario the durable-handle designs above exist to prevent.
- **Route by expertise, and treat approval volume itself as a governance metric.** The security research's recommendation — track how many approvals a given reviewer is processing, and treat a rising volume as a leading indicator of degrading scrutiny rather than a healthy sign of "the system asks for permission a lot" — is the organizational analogue of rate-limiting: the metric that looks reassuring (agents responsibly asking before acting) is the same metric that predicts the failure (reviewers no longer really looking).

## 9. What This Means for Zylos

Zylos's own operating rules already implement an ad hoc instance of exactly this architecture, and it is worth naming the mapping explicitly. Behavioral Rule 1 — never block the input pipeline, never present a synchronous confirmation dialog — is the same constraint MCP's stateless shift and A2A's push-notification mode exist to satisfy: the agent must remain responsive to new work while a question is pending. Behavioral Rule 2 — confirm before destructive operations via a plain-text message sent over C4, explicitly framed as "this is an async message exchange; it does not violate Rule 1" — is functionally a hand-built CIBA: an out-of-band backchannel (Telegram, Lark, whichever channel the user is on), a human-readable description of the specific action rather than an abstract permission, and a resume-on-reply model rather than a blocked thread.

The gap worth closing, in light of the fatigue research, is that this pattern currently has no volume safeguard. As scheduled tasks, background agents, and multi-channel operation grow, the same reflex-approval risk that shows up in the 11,429-review study applies just as directly to a user fielding a growing stream of "confirm before I do X" messages across DMs and group chats: if confirmation requests become frequent enough to answer without reading closely, the control has quietly become theater. The mitigations above translate directly — reserve interruption for genuinely high-risk, low-reversibility actions rather than a fixed category list; make every confirmation message describe the specific, concrete consequence rather than a generic "may I proceed"; and default to *not* acting, rather than acting, if a confirmation goes unanswered past a reasonable window, exactly mirroring the fail-closed discipline the timeout design above requires.

## 10. What to Watch

Two open questions from this research are worth tracking as the ecosystem matures. First, whether MCP's URL-mode elicitation and A2A's `auth_required` state converge further — both exist to move sensitive interactions out of the agent's context window entirely, and a shared pattern for "hand the user to a webpage, resume on return" would reduce the amount of custom plumbing every agent platform currently builds separately. Second, whether any of the major frameworks build first-class tooling for the fatigue problem itself — risk-scored routing, reviewer-load dashboards, mandatory friction on stale-attention patterns — rather than leaving it, as today, entirely as an operational discipline every deployment has to invent for itself. The protocol layer solved the engineering half of "ask without blocking" in the space of about a year, across four independent lineages. The harder half — keeping the answer meaningful once asking is free — has no protocol yet, and the evidence so far suggests it needs one.
