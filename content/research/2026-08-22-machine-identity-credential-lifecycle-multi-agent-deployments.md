## Executive Summary

When a single AI agent connects to a task platform, a communication hub, or an orchestration service, identity is trivial: one account, one credential, one thing to rotate if it leaks. The moment a deployment grows to two, three, or five agent instances -- each running on its own machine, each needing to authenticate independently -- identity stops being trivial. Share one account across machines and you lose the ability to answer basic questions after an incident: which machine made this call, which instance leaked the credential, which one can be revoked without taking the other four down with it. Issue a separate credential per machine and you inherit a lifecycle problem that most non-human-identity tooling was built for humans-adjacent systems (CI/CD runners, Kubernetes pods, cloud workloads), not for long-running autonomous agents that persist state, memory, and behavior independently of the machine they happen to run on.

This is the central architectural distinction the research keeps surfacing under different names: **machine identity is not agent identity.** A machine identity (a per-instance Personal Access Token, a service-account credential, an mTLS certificate) answers "is this specific process/host allowed to open a session with the platform?" An agent identity (the persona, memory, behavioral configuration, and decision authority) answers "what is this agent allowed to decide and do once it's talking to the platform?" Conflating the two -- letting the registration credential itself carry the agent's full authorization -- is the single most common failure mode found across the literature, from a July 2026 analysis showing that LangGraph, AutoGen, and CrewAI all lose identity enforcement the instant a request leaves the process boundary, to the Cloud Security Alliance's May 2026 finding that 78% of organizations have no documented policy for creating or removing AI identities at all.

The infrastructure world has already solved adjacent versions of this problem, repeatedly, in different forms: Kubernetes' bound service account tokens, HashiCorp Vault's AppRole and dynamic secrets, SPIFFE/SPIRE's short-lived SVIDs, and the cloud IAM machine-identity patterns (AWS IRSA, GCP Workload Identity Federation, Azure Managed Identities) all converge on the same shape -- short-lived, narrowly scoped, cryptographically verifiable, auto-rotating credentials issued to a specific workload rather than shared across a fleet. GitHub Actions' and GitLab CI's OIDC federation show the same convergence in the CI/CD world: replace a long-lived static secret with a token minted per run, valid for minutes, that a downstream system exchanges for narrowly scoped temporary access. None of these patterns were designed for autonomous AI agents, but all of them are directly applicable to a fleet of 2-5 agent machines -- and none of the mainstream agent orchestration frameworks currently implement them by default.

This article surveys machine identity theory, issuance and rotation patterns, the trust-boundary problem between registration credentials and agent authorization, five reference architectures from adjacent infrastructure domains, the gaps specific to today's AI agent platforms, and a practical, right-sized playbook for teams running a handful of agent instances -- motivated directly by the PAT-per-machine onboarding model used by Zylos' own Multica task platform.

## Machine Identity vs. Agent Identity: Why They Must Be Separate

Security vendors and standards bodies draw the identity hierarchy in slightly different ways, but the shape is consistent. **Human identity** covers people. **Machine identity** is the umbrella for every non-human entity that authenticates -- devices, applications, automated processes, cloud workloads -- and CyberArk defines it plainly as the set of "digital entities used to identify, authenticate and authorize machines, devices and IT infrastructure as well as the applications, cloud workloads and automated processes within an IT infrastructure" ([CyberArk: What is a Machine Identity?](https://www.cyberark.com/what-is/machine-identity/)). Within that umbrella sits the narrower, more modern concept of **workload identity**: a unique, cryptographically verifiable identity assigned to an ephemeral non-human actor -- a container, a serverless function, a CI job -- that is dynamic and often lives for minutes rather than years, in contrast to the static, long-lived identities associated with, say, an IoT device certificate ([Palo Alto Networks: What Is Workload Identity?](https://www.paloaltonetworks.com/cyberpedia/what-is-workload-identity); [NHI Management Group: Machine Identity vs. Workload Identity](https://nhimg.org/nhi-101/machine-identity-vs-workload-identity)).

NIST's Zero Trust Architecture (SP 800-207) makes the point that matters most for agent deployments: it treats service accounts, workload identities, and API keys under exactly the same zero-trust discipline as human accounts -- owner-assigned, minimally scoped, continuously re-verified, never trusted by virtue of network location alone ([NIST SP 800-207](https://nvlpubs.nist.gov/nistpubs/specialpublications/NIST.SP.800-207.pdf)). Nothing in the zero-trust model exempts a machine credential from least-privilege scoping just because a human isn't sitting behind it.

For a multi-agent deployment, this cashes out into a concrete design rule: **the credential that lets a machine open a session with a platform should not be the same object that determines what the agent running on that machine is allowed to do.** A per-machine PAT (or service-account token, or mTLS cert) is a *registration* credential -- it proves "this specific host/process is a legitimate member of the fleet." The agent's authorization -- what tasks it can claim, what data it can read, what actions it can take -- belongs to a separate layer, evaluated at the application boundary, ideally per-request rather than baked into the registration credential itself.

Skipping this separation produces a documented failure pattern: once a token is issued, it tends to get accepted broadly across an API surface without scope-specific validation, so the principle of least privilege collapses the moment every token in the fleet grants the same breadth of access regardless of what the agent behind it actually needs to do right now ([Decoupling Identity from Access: Credential Broker Patterns for Secure CI/CD, arXiv:2504.14761](https://arxiv.org/pdf/2504.14761)). Okta's 2025-2026 positioning on unifying human and non-human identity makes a related point from the other direction: because human identities are so often the root that provisions non-human ones (a person creates the service account, generates the PAT, deploys the agent), the two layers need consistent governance even while remaining architecturally distinct ([Okta: Human & Non-Human Identities](https://www.okta.com/blog/ai/non-human-and-human-identities-a-unified-approach/)).

## Credential Issuance Patterns

**Personal Access Tokens (PATs).** GitHub's evolution here is instructive because it happened in public and under real operational pressure. GitHub now steers users toward fine-grained PATs over classic ones: fine-grained tokens can be scoped to specific repositories with narrow permissions (e.g., "Contents: read/write" rather than blanket repo access) and, critically, carry a *mandatory* expiration date -- classic PATs could live forever ([GitHub Blog: Introducing fine-grained personal access tokens](https://github.blog/security/application-security/introducing-fine-grained-personal-access-tokens-for-github/)). For anything beyond a handful of tokens, GitHub's own guidance is to move off PATs entirely and onto **GitHub Apps**, which are a first-class identity independent of any human account: installation tokens expire in about an hour instead of living indefinitely, rate limits are roughly 3x higher (15,000 req/hr vs. 5,000), and the app's access survives the departure of whoever created it -- GitHub states plainly that "your app should never use a personal access token or GitHub password to authenticate" ([GitHub Docs: Best practices for creating a GitHub App](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app); [Demystifying GitHub Apps](https://josh-ops.com/posts/github-apps/)).

GitLab runs a parallel three-tier model: Personal Access Tokens (broad, tied to a user), Project Access Tokens (scoped to one project, backed by a bot user that doesn't consume a paid seat), and Group Access Tokens. GitLab's recommendation for cross-project automation mirrors GitHub's Apps advice -- use a dedicated **Service Account**, centrally managed and rotatable, rather than a token tied to a person's lifecycle ([GitLab Docs: Token overview](https://docs.gitlab.com/security/tokens/)).

**OAuth 2.0 Client Credentials flow.** For pure service-to-service authentication with no human or browser in the loop, RFC 6749's client credentials grant is the standard: a client exchanges a `client_id` and `client_secret` for a short-lived access token (typically 15 minutes to an hour) at a token endpoint ([Auth0: Client Credentials Flow](https://auth0.com/docs/get-started/authentication-and-authorization-flow/client-credentials-flow); [Microsoft: OAuth 2.0 client credentials flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-client-creds-grant-flow)). This is the recommended default whenever traffic crosses an organizational trust boundary, because the long-lived secret (the client secret) never itself travels on the wire after the initial exchange -- only the short-lived derived token does.

**mTLS / X.509 certificates.** Where the identity needs to be embedded at the transport layer rather than carried as a bearer token in a header, mutual TLS is the mechanism -- this is the model SPIFFE/SPIRE builds on (below), and it has the useful property that a stolen token replayed from a different host still fails the TLS handshake, whereas a stolen bearer token works from anywhere until it's explicitly revoked.

The throughline across all of these: **the industry's direction of travel is away from long-lived static secrets and toward short-lived, narrowly scoped, auto-expiring credentials issued per machine or per session** -- exactly the pattern a small agent fleet should replicate rather than reinvent.

## Rotation and Revocation

Issuance is the easy half of the lifecycle. Rotation and revocation are where operational discipline actually gets tested, and where most small deployments quietly fail.

**Automated rotation** has two distinct shapes in HashiCorp Vault, both worth borrowing conceptually even without running Vault itself. Vault can generate **dynamic secrets** on demand, per request, with a short TTL -- an AWS IAM key or database credential minted fresh for one job and never persisted anywhere -- so there is no long-lived secret to leak in the first place. Separately, for credentials that must remain static (a root database password, an LDAP bind account), Vault's database and LDAP secrets engines support scheduled **auto-rotation**, immediately rotating a credential the moment it's onboarded and then again on a defined `rotation_schedule` ([HashiCorp: Automated secrets rotation](https://developer.hashicorp.com/hcp/docs/vault-secrets/auto-rotation); [Vault Database secrets engine](https://developer.hashicorp.com/vault/docs/secrets/databases)).

AWS Secrets Manager illustrates the mechanics of rotation-without-downtime clearly: a Lambda function runs a four-step protocol (`createSecret`, `setSecret`, `testSecret`, `finishSecret`), and during the transition two staging labels -- `AWSCURRENT` and `AWSPENDING` -- let both the old and new credential remain simultaneously valid until the new one is confirmed working, at which point the label flips and the old version is retired ([AWS: Rotation by Lambda function](https://docs.aws.amazon.com/secretsmanager/latest/userguide/rotate-secrets_lambda.html)). This overlapping-validity design is the piece small teams most often skip when rotating credentials by hand -- rotating in place with no grace period is how a rotation itself causes an outage.

**Revocation is the harder half, and offboarding is where it most often breaks.** Disabling a person's SSO account does not revoke credentials that were issued independently -- a PAT, an API key, a service-account token continues to work after the human's login is disabled unless it is explicitly, separately revoked, because it "authenticates independently of the user's login session" ([NHI Management Group: How do organisations make SaaS offboarding actually work?](https://nhimg.org/faq/how-do-organisations-make-saas-offboarding-actually-work/)). For a multi-agent deployment this maps directly onto machine decommissioning: turning off a VM or deleting a container does nothing to the platform-side PAT it was using unless that PAT is separately revoked at the platform. A real offboarding runbook has to track every credential to its own retirement, not assume it dies with the machine.

Compliance frameworks put numbers on how fast this should happen: FedRAMP's PS-4 control expects credential revocation within a 4-hour window; SOC 2 CC6.1 and ISO 27001 Annex A 6.5 treat same-day revocation as the floor. These are enterprise benchmarks, but they're a reasonable informal SLA even for a small deployment -- "revoke it today," not "revoke it whenever someone remembers."

## Trust Boundaries: What a PAT Should (and Shouldn't) Authorize

The credential-broker pattern is the cleanest resolution to the machine-identity/agent-identity split described above. Instead of a registration credential (the PAT) being checked once and then trusted for everything downstream, a broker sits between the credential and the resource: it validates the registration credential, evaluates policy for the specific action being requested, and issues an ephemeral, task-scoped credential -- valid for minutes, non-reusable outside its approved scope -- only when policy allows it ([Decoupling Identity from Access: Credential Broker Patterns for Secure CI/CD, arXiv:2504.14761](https://arxiv.org/pdf/2504.14761)). This decouples "who is this machine" from "what may this specific action do right now," and it's the same decoupling OAuth scopes provide at a simpler level: fine-grained scopes are, as Auth0 puts it, "essential for upholding the principle of least privilege and minimizing exposure" in exactly this kind of machine-to-machine exchange ([Auth0: OAuth 2.0 Access Tokens and The Principle of Least Privilege](https://auth0.com/blog/oauth2-access-tokens-and-principle-of-least-privilege/)).

HashiCorp's own validated pattern for AI agent authentication makes this concrete for the agent case specifically: an agent exchanges a human's identity-provider token for an On-Behalf-Of (OBO) token carrying both the agent's own identity claims and the originating user's claims, and Vault's JWT auth method binds acceptance of that token to the specific `preferred_username`, group claims, `bound_audiences` (the calling tool's client ID), and `azp` (authorized party) -- with an `X-Correlation-ID` propagated end-to-end across the whole Web → Agent → MCP Server → Vault chain for audit purposes ([HashiCorp: Secure AI agent authentication using Vault dynamic secrets](https://developer.hashicorp.com/validated-patterns/vault/ai-agent-identity-with-hashicorp-vault)). Note what this buys: the registration credential proves the agent is legitimate; the OBO exchange and the bound claims determine, per request, exactly what it's allowed to touch -- and every hop is attributable after the fact.

The practical takeaway for a small fleet: a PAT should be scoped to the minimum needed to open a session and identify the machine -- nothing more. Any authorization broader than "this is a registered agent instance" belongs at the application layer, evaluated per request, not folded into the PAT's own permission scope.

## Reference Architectures from Adjacent Domains

Five infrastructure ecosystems have already solved versions of this problem at scale. None target AI agents directly, but each pattern maps cleanly onto a multi-machine agent fleet.

**Kubernetes Service Accounts.** Kubernetes moved away from long-lived Secret-mounted tokens toward **bound service account tokens**, issued through the stable `TokenRequest` API: each token is time-bound (default one-hour lifespan), audience-scoped via the JWT `aud` claim, and bound to a specific object -- typically the Pod, whose name and UID are embedded as claims. Tokens are delivered via a `projected` volume and the kubelet refreshes them automatically before expiry; deleting the Pod invalidates its tokens immediately, with no separate revocation call required ([Kubernetes: Managing Service Accounts](https://kubernetes.io/docs/reference/access-authn-authz/service-accounts-admin/); [KEP-1205: Bound Service Account Tokens](https://github.com/kubernetes/enhancements/blob/master/keps/sig-auth/1205-bound-service-account-tokens/README.md)). The lesson: tying credential lifetime to *instance* lifetime, rather than to a separately managed expiry, eliminates an entire class of "forgot to revoke it" incidents.

**HashiCorp Vault -- AppRole and Identity.** The AppRole auth method is designed specifically for machine authentication: a static `role_id` (like a username) plus one or more `secret_id`s (like one-time passwords) together yield a Vault token. Vault's built-in Identity secrets engine -- always mounted, cannot be disabled -- turns each authenticated client into an **Entity** that can carry multiple **Aliases**, so one machine's identity can be unified across several auth backends (e.g., one entity with both a GitHub alias and an LDAP alias) ([HashiCorp: AppRole auth method](https://developer.hashicorp.com/vault/docs/auth/approle); [HashiCorp: Identity secrets engine](https://developer.hashicorp.com/vault/docs/secrets/identity)). This Entity/Alias split is a useful mental model even outside Vault: an agent machine's "identity" can be one stable concept even as the specific credential it authenticates with rotates or varies by backend.

**SPIFFE/SPIRE.** SPIFFE is the specification, SPIRE the reference implementation, and the unit of identity is the **SVID** (SPIFFE Verifiable Identity Document) -- either an X.509-SVID (SPIFFE ID embedded in the certificate's SAN URI field, for mTLS) or a JWT-SVID (for HTTP Authorization headers where mTLS isn't practical). Both are short-lived, typically around an hour and configurable down to minutes, auto-rotated by the SPIRE Agent before expiry ([SPIFFE: Working with SVIDs](https://spiffe.io/docs/latest/deploying/svids/)). Identity issuance is a two-phase attestation: **node attestation** proves the identity of the physical/virtual host to the SPIRE Server, and **workload attestation** inspects the process running on that node and matches it against registered selectors to decide which SVID it receives ([SPIFFE Concepts](https://spiffe.io/docs/latest/spiffe-about/spiffe-concepts/); [SPIRE Concepts](https://spiffe.io/docs/latest/spire-about/spire-concepts/)). This two-phase split -- "which machine is this" then "which workload on that machine is this" -- is precisely the machine-identity/agent-identity separation this article argues for, just implemented at the infrastructure layer. Teleport's commercial Machine & Workload Identity product (via its `tbot` agent) issues SPIFFE-compatible SVIDs specifically to replace static secrets in CI/CD, SSH, Kubernetes, and MCP contexts ([Teleport: Machine & Workload Identity](https://goteleport.com/docs/machine-workload-identity/)).

**Cloud IAM machine credentials.** AWS instance profiles pass an IAM role to an EC2 instance at boot; **IRSA** (IAM Roles for Service Accounts) extends the same idea to Kubernetes by leveraging EKS's built-in OIDC provider, letting a Kubernetes ServiceAccount assume an IAM role narrower than the node's own instance-profile role -- least privilege per workload, not per node ([AWS: IAM roles for service accounts](https://docs.aws.amazon.com/eks/latest/userguide/iam-roles-for-service-accounts.html)). GCP's **Workload Identity Federation** goes a step further, letting external workloads (on-prem servers, CI runners, other clouds) impersonate a GCP service account without ever downloading a service-account key file -- eliminating the single riskiest artifact in the whole model, the long-lived downloadable key ([Google Cloud: Workload Identity Federation](https://docs.cloud.google.com/iam/docs/workload-identity-federation)). Azure's Managed Identities offer both system-assigned (lifecycle tied to one resource) and user-assigned (independently provisioned, shareable, backed by its own Entra ID service principal) variants, with Microsoft recommending user-assigned identities whenever the identity needs to outlive or be shared across a specific piece of compute ([Microsoft: Managed identities overview](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/overview)).

**GitHub Actions / GitLab CI OIDC federation.** Both platforms now let a CI job authenticate to a cloud provider without ever storing a cloud credential as a CI secret at all: the CI platform itself acts as an OIDC identity provider, minting a token per run that carries claims identifying exactly what's running (repo, branch, workflow, environment); the cloud provider validates a pre-configured trust relationship and exchanges that token for a short-lived, narrowly scoped credential that expires automatically at the end of the job ([GitHub Docs: Configuring OpenID Connect in cloud providers](https://docs.github.com/actions/deployment/security-hardening-your-deployments/configuring-openid-connect-in-cloud-providers); [GitLab Docs: OpenID Connect with GCP Workload Identity Federation](https://docs.gitlab.com/ci/cloud_services/google_cloud/)). This "identity federation replaces static secret" pattern is repeatedly cited as the template other machine-to-machine credential systems should converge on, and it is worth naming explicitly as the target shape even for teams too small to build it: minutes-scoped, per-run, claims-bound tokens beat a static key sitting in a `.env` file indefinitely.

## Gaps in Current AI Agent Platforms

Set against those five mature patterns, today's AI agent orchestration frameworks look early. A July 2026 comparative analysis of LangGraph, AutoGen, and CrewAI found that none of them enforce identity-bound policy at the point where it matters most -- the model-call or tool-call boundary. Each framework's internal controls (LangGraph's graph checkpoints, AutoGen's conversational structure, CrewAI's role-based tool scoping) operate only inside the process; the moment a request leaves the process to call an external model API or tool, "the request leaves that process carrying whatever credential is configured, and the framework's controls no longer apply." The article's blunt summary: "the identity that reaches a model API is whatever credential the process holds" ([DeepInspect: Agentic AI Framework Security](https://www.deepinspect.ai/blog/agentic-ai-frameworks-security-comparison)). In other words, credential and identity enforcement has to be built as a layer *above* these frameworks, because none of them provide it natively.

OpenHands (formerly OpenDevin) is a partial counterexample worth noting: its Agent Server supports session-based API-key authentication via an `X-Session-API-Key` header, the server itself holds no LLM API key at all (the client supplies model and key per conversation, encrypted at rest), and multi-tenant isolation runs one container per agent instance with its own filesystem and resource limits. That's a workable machine-per-instance credentialing shape, though it still leaves the actual LLM credential passing through the agent's own runtime context ([The OpenHands Software Agent SDK, arXiv:2511.03690](https://arxiv.org/html/2511.03690v2)). That last point is a structural problem independent of any framework: once a credential enters an LLM's context window, it is just tokens with no privilege bit attached, and it can leak out through logs, commit messages, tool-call arguments, or persisted memory files -- an argument for keeping raw credentials out of agent context entirely wherever a broker or OBO-style exchange can substitute for it instead ([HackerNoon: The Credential Problem Behind Agentic AI](https://hackernoon.com/the-credential-problem-behind-agentic-ai)).

The scale of the resulting exposure is measurable. Over 28.6 million new secrets were exposed on public GitHub in 2025, a 34% year-over-year increase, with AI-service credential leaks specifically surging 81.5%; more tellingly, 64% of credentials confirmed leaked in 2022 were still active and exploitable as of January 2026 -- strong evidence that detection has outpaced revocation discipline, not the other way around ([WorkOS: How to manage API keys, tokens, and secrets for AI agents](https://workos.com/blog/ai-agent-secrets-management)). The Cloud Security Alliance's May 2026 whitepaper quantifies the governance gap behind those numbers: non-human identities now outnumber human ones by roughly 45:1 on average (144:1 in cloud-native environments), yet 78% of organizations have no documented policy for creating or removing AI identities, 51% report no clear ownership of AI identities, and only 20% have a formal offboarding process for API keys ([CSA: The Non-Human Identity Governance Vacuum](https://labs.cloudsecurityalliance.org/research/csa-whitepaper-nonhuman-identity-agentic-ai-governance-v1-cs/)).

This gap has not gone unnoticed at the standards and vendor level. A dedicated **non-human identity (NHI)** security category has consolidated rapidly through 2025-2026: Astrix Security and Oasis Security both built discovery-and-lifecycle platforms for NHIs specifically (Astrix is being acquired by Cisco, announced May 2026; Oasis has a pending ~$1B acquisition by Cyera announced July 2026); Aembit built a policy-based workload identity broker that replaces static secrets outright rather than just managing them; Teleport productized SPIFFE-compatible SVID issuance; and the broader security-platform market shifted decisively toward machine identity as a category, reflected in Palo Alto Networks' roughly $25B acquisition of CyberArk in February 2026 ([Aembit: IAM for Agentic AI](https://aembit.io/blog/iam-agentic-ai/); [Cremit: NHI Security Platform Comparison 2026](https://www.cremit.io/reports/rsac-2026-nhi)). Government guidance has followed: on May 1, 2026, CISA, the NSA, and cyber agencies from Australia, Canada, New Zealand, and the UK jointly published "Careful Adoption of Agentic AI Services," the first coordinated multinational guidance on agentic AI security -- it explicitly requires each agent to carry a verified, cryptographically anchored identity with short-lived credentials, encrypted communication, and continuous runtime authentication, and recommends human approval gates for high-impact actions ([CISA: Careful Adoption of Agentic AI Services, official PDF](https://media.defense.gov/2026/Apr/30/2003922823/-1/-1/0/CAREFUL%20ADOPTION%20OF%20AGENTIC%20AI%20SERVICES_FINAL.PDF)). NIST's Center for AI Standards and Innovation opened an AI Agent Standards Initiative in February 2026 with agent identity as one of three founding pillars, alongside security and interoperability.

None of this tooling yet targets the specific case this article is about: a small team running a handful of self-hosted agent instances against an internal platform, rather than an enterprise managing thousands of cloud workloads. The patterns are transferable, but nobody has packaged them for a 2-5-machine deployment yet.

## Practical Recommendations for Small Teams (2-5 Agent Instances)

Translating the enterprise patterns above down to a small fleet, without requiring a Vault cluster or a SPIRE deployment:

1. **One credential per machine, never shared.** Each agent instance gets its own PAT (or equivalent registration credential) at every platform it connects to. This is non-negotiable even at small scale -- it is the only way to answer "which machine did this" after an incident, and it is the only way to revoke one compromised or decommissioned instance without disrupting the rest of the fleet.

2. **Scope the registration credential to registration, not to everything.** The PAT should prove machine legitimacy and open a session; it should not itself carry the agent's full authorization. Where the platform supports finer scopes (repo-level, project-level, permission-level, as GitHub and GitLab both do), use the narrowest scope that lets the machine register and communicate -- push broader authorization decisions to the application layer, evaluated per action rather than baked into the token.

3. **Treat rotation as calendared, not reactive.** Even without automation, put rotation on a schedule: quarterly for platform PATs and third-party API keys is a reasonable default, informed by common practice around 30-90 day cycles for higher-sensitivity credentials. The specific interval matters less than it being scheduled rather than "whenever we remember."

4. **Rotate immediately on any personnel or machine change** -- a laptop reimaged, a VM decommissioned, someone leaving the team. Disabling SSO access does not revoke independently issued tokens; they have to be revoked explicitly, at the platform, as their own step.

5. **Write down a one-page decommissioning runbook and actually use it.** When retiring a machine: revoke its registration credential at every platform it touched, remove it from any group/permission bindings, and check for credentials it may have minted downstream (cached SSH keys, tokens it issued to other services on its behalf). Do this at decommission time, not as a later cleanup task -- "later" is where the 64%-still-active-two-years-later statistic comes from.

6. **Get secrets out of `.env` files as soon as the fleet crosses "one machine."** A `.env` file is fine for solo local development; it stops being adequate the moment credential attribution matters across multiple machines. Move the highest-risk secrets first (platform PATs, anything with write access) into a dedicated secrets manager -- self-hosted Vault, a cloud secrets manager, or a lighter SaaS option -- rather than attempting a big-bang migration of everything at once.

7. **Prefer per-task or per-session scoping over per-agent static credentials wherever the platform allows it.** The same logic that pushed GitHub toward Apps with hour-long installation tokens and pushed CI/CD toward OIDC federation applies here: if a platform supports issuing a short-lived, task-scoped token from a longer-lived registration credential, use it instead of handing the agent one static token that lives forever.

8. **Log every issuance, rotation, and revocation event, and watch post-authentication activity, not just login events.** Machine identities typically authenticate once and then make many downstream calls; a compromised credential usually shows up first as unusual API activity after a normal-looking login, not as a failed login attempt. Even a simple append-only log of "which machine, which credential, which action" pays for itself the first time something needs to be traced.

9. **Adopt an informal revocation SLA.** "We revoke a known-bad credential within 4 hours" (mirroring FedRAMP's PS-4 benchmark) or "same day" (mirroring SOC 2 CC6.1) is a useful discipline to hold even informally -- the specific number matters less than having one, and holding to it.

10. **Keep raw credentials out of agent context wherever practical.** If an agent's LLM context window never contains the actual PAT or API key value -- because a broker injects it at the tool-call boundary, or because the platform issues a short-lived derived token instead -- an entire class of leak vector (logs, commit messages, memory files, accidental disclosure in output) simply doesn't exist for that credential.

None of this requires enterprise infrastructure. It requires treating each agent machine as its own principal from day one, and treating credential lifecycle as an explicit, scheduled practice rather than something that happens only when a credential is discovered leaked.

## Closing Note

The pattern underlying a PAT-per-machine onboarding model -- separate registration credential, separate agent-layer authorization, explicit rotation and revocation discipline -- is not a novel idea. It is the same idea Kubernetes, Vault, SPIFFE/SPIRE, and every major cloud IAM system converged on independently, for the same reason: shared, long-lived, broadly scoped credentials are the default failure mode of any system that starts small and grows, and the fix is always the same shape -- narrow the scope, shorten the lifetime, separate "who is this machine" from "what can this agent do," and make revocation a first-class, scheduled operation rather than an afterthought. What's missing today is not the pattern; it's tooling and defaults in the AI agent ecosystem that make the pattern the path of least resistance instead of the path requiring deliberate extra work.
