## Executive Summary

A recurring failure pattern is showing up across multi-agent task platforms: Agent A calls Agent B, B replies by calling A back, and the reply vanishes. Nothing errors. No comment appears. From the outside it looks exactly like message loss, dropped webhooks, or a flaky queue. The actual cause is almost always a permission check: the platform distinguishes calls that trace back to a human from calls that originate purely inside the agent mesh, and by default it refuses the latter.

This is not a bug in any one product — it is a deliberate, convergent design choice showing up in Slack's bot-to-bot messaging conventions, GitHub Actions' `GITHUB_TOKEN` recursion guard, and — concretely, in the platform this article uses as its motivating case — Multica's `authorType == "member"` / `actorType == "member"` trigger gates. Each of these systems independently arrived at the same rule: **an event caused by a bot must not, by itself, cause another bot to act**, because otherwise you get infinite loops, runaway cost, unattributable actions, and a laundering path for prompt injection to hop from agent to agent with no human ever having approved the chain.

The cost of that safety property is that peer-to-peer agent collaboration — coordinator asks reviewer, reviewer reports back, coordinator asks a third agent, and so on — breaks by default the moment no human is present in the call chain. Platforms that get this right expose the gate as a configurable, observable permission (an allowlist, a scope, a visible refusal); platforms that get it wrong leave it as an invisible default that produces silent drops indistinguishable from infrastructure failure.

This article surveys how seven ecosystems (Slack, GitHub Copilot, Google's A2A protocol, Microsoft Agent 365/Copilot Studio, OpenAI Agents SDK, Anthropic Claude Code, Discord, and the Multica task-platform pattern) gate agent-to-agent invocation, extracts the shared design vocabulary, and closes with concrete recommendations for a small self-hosted platform in the Zylos style. Where a specific platform behavior could not be verified from primary sources, this is stated explicitly rather than guessed.

## The Motivating Pattern

The incident that frames this piece: a coordinator agent (running on a Claude runtime) created a reviewer agent (running on a Codex runtime) on a Multica-style task platform and dispatched a review via an issue comment. The reviewer did its job and @-mentioned the coordinator back to report results. That mention never woke the coordinator — no error, no visible refusal, just silence. Root cause: the coordinator's agent record had `permission_mode=private`, a setting under which the agent only accepts invocations whose call chain contains a human originator. The reviewer's callback had no human in its chain, so it was refused, and the refusal was not surfaced anywhere a human would see it. The fix was to move the coordinator to `permission_mode=public_to` with an explicit `invocation_targets` allowlist scoped to the workspace.

`permission_mode`, `public_to`, and `invocation_targets` could not be verified as literal, publicly documented field names in Multica's current API — its public docs (`multica.ai/docs/agents`) describe a conceptually similar but differently named control: an **Access** setting per agent with three values, "Only me," "Entire workspace," and "Specific people," where new agents default to "Only me." That default-private-to-owner posture is the same shape of problem described in the incident, and the incident's exact field names are treated here as an internal/implementation-level description of that same mechanism rather than as verified public API. What *is* independently verifiable, and turns out to be the more important evidence, is that Multica's own issue tracker documents this exact failure class as a known, named problem in its trigger-gating code — covered below.

## How Current Platforms Gate Agent-to-Agent Invocation

### Multica-style task platforms (issues, comments, @-mentions)

Multica's documented model: @-mentioning an agent in an issue comment starts a new run from that comment while leaving the issue's assignee and status unchanged; assignment, by contrast, makes the agent the issue owner. Access restrictions apply regardless of mention: "An @-mention cannot bypass an agent's Access." When a mention can't fire — wrong access level, agent offline — "the trigger preview explains that it won't start; the comment itself still posts normally." Agents can @-mention other agents in replies, and the platform notes a real gap here: "When A @-mentions B and B @-mentions A back, the system merges duplicate runs at the same moment, but it does not decide when the collaboration should end — write the stop condition into the agent instructions." (Source: [Multica Docs — Agents](https://multica.ai/docs/agents), [Multica Docs — @-mention agents in comments](https://multica.ai/docs/mentioning-agents), undated, accessed 2026-08-30.)

More revealing is Multica's public GitHub issue tracker, which documents the exact origin-gating mechanism at the code level, independent of the incident this article is built around. Three findings:

- **Issue #2120** ("Subtask-completion trigger to unblock Coordinator-pattern multi-agent workflows"): the codebase gates comment-triggered runs on `authorType == "member"` and status-triggered runs on `actorType == "member"`. These "correctly prevent infinite loops but inadvertently block legitimate coordinator notifications." The only working workaround as of that issue is for sub-agents to remember to @-mention the coordinator in their final comment — "a discipline that depends entirely on LLM memory," and when an agent forgets, "the Coordinator is never woken up and the workflow silently dies" with no error signal. (Source: [multica-ai/multica issue #2120](https://github.com/multica-ai/multica/issues/2120), accessed 2026-08-30.)
- **Issue #1290** ("Agent-initiated comments and backlog→todo transitions should trigger task pickup"): pinpoints the same `authorType`/`actorType == "member"` checks at specific code locations (`comment.go:263`, `issue.go:1127`, `issue.go:1433`) and proposes replacing the blanket member-only check with "anti-self-loop" logic that allows agent-to-agent triggers while still blocking an agent from re-triggering itself. (Source: [multica-ai/multica issue #1290](https://github.com/multica-ai/multica/issues/1290), accessed 2026-08-30.)
- **Issue #3353**: a related but distinct failure — agent runs can be marked complete without posting any user-visible comment, because the runtime doesn't enforce that task completion requires an explicit `multica issue comment add` call. This is a different bug (missing output, not a gated invocation) but compounds the same symptom for an observer: things look like they silently failed. (Source: [multica-ai/multica issue #3353](https://github.com/multica-ai/multica/issues/3353), accessed 2026-08-30.)

Taken together, this is strong independent corroboration that the "silent drop on agent-originated callback" failure mode described in the motivating incident is not specific to one platform's private beta behavior — it is a structural consequence of any system that gates triggers on an originator-type check without also building an agent-to-agent-aware allow path and a visible refusal signal.

### Slack

Slack has invested heavily in agent-native surfaces in 2025–2026 — dedicated agent containers, app threads, streaming, and an "agentic OS" framing under Agentforce 360 with Slack as the interaction layer for third-party models. (Source: [Slack — Announcing agents and AI innovations in Slack](https://slack.com/blog/news/ai-innovations-in-slack), [Slack — Work with AI agents and assistants in Slack](https://slack.com/help/articles/33076000248851-Understand-AI-apps-in-Slack), accessed 2026-08-30.) A precisely worded bot-to-bot messaging restriction with the specificity claimed in some secondary sources (e.g., a rule that "a peer-bot message is accepted only when the message itself contains a current @-mention of this bot") could not be verified from Slack's own developer documentation. That is flagged as an unverified secondary-source claim rather than a confirmed Slack platform rule. What is well established practically (and consistent with widespread bot-development convention across Slack, Discord, and similar platforms) is that most bots explicitly check the `bot_id`/`is_bot` field on incoming events and self-suppress on messages from other bots, precisely to avoid the reply-loop problem — a convention enforced by app authors, not by the platform, on classic Slack bots. Whether Slack's newer first-class "Agent" app type enforces this at the platform level rather than leaving it to app code was not confirmable from primary sources in this pass.

### GitHub Copilot coding agent / GitHub Actions

This is the best-documented instance of origin-gating in the survey, and it maps almost exactly onto the private/public_to distinction. GitHub's own docs state the mechanism plainly: when a workflow uses the default `GITHUB_TOKEN` to push a commit or open/update a PR, "events triggered by the `GITHUB_TOKEN` will not create a new workflow run," with `workflow_dispatch` and `repository_dispatch` as the only exceptions. This exists specifically "to prevent you from accidentally creating recursive workflow runs." For the `pull_request` event triggered by a bot-authored PR, GitHub does allow a workflow run, but forces it into an "approval-required" state — a human with write access must click "Approve and run workflows" before it executes. (Source: [GitHub Docs — GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/github_token), [GitHub Docs — Triggering a workflow](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow), accessed 2026-08-30.) Community discussion confirms there is deliberately no way to bypass this human-approval gate for bot/app-triggered workflow runs — it is treated as a security boundary, not a bug. (Source: [GitHub community discussion #167493](https://github.com/orgs/community/discussions/167493), [#162826](https://github.com/orgs/community/discussions/162826), accessed 2026-08-30.) Microsoft's own Copilot-coding-agent training material frames this the same way, under "Security, risks, and limitations of the Copilot coding agent." (Source: [Microsoft Learn](https://learn.microsoft.com/en-us/training/modules/github-copilot-code-agent/2-security-risks-limitations-copilot-code-agent), accessed 2026-08-30.) This is functionally identical to `permission_mode=private`: the default posture refuses to let a bot-caused event cause further automated action, and the escape hatch (an explicit PAT or GitHub App token instead of the ambient `GITHUB_TOKEN`, or human approval) is exactly the `public_to`/allowlist idea, just implemented as "use a different, more privileged credential" rather than a workspace-scoped invocation list.

### Google Agent2Agent (A2A) protocol

A2A is an open interoperability protocol (originated at Google, now under the Linux Foundation-adjacent `a2aproject`) for communication between independent agent systems built on different stacks. Each A2A-compliant agent publishes an **Agent Card** — a JSON document at the well-known URI `/.well-known/agent.json` — describing its identity, skills, endpoint, and required authentication (OAuth 2.0, API keys, OIDC, or bearer tokens); credentials themselves are obtained out-of-band and must never appear in the card. Work is modeled as a **Task** with a defined lifecycle (submitted → working → input-required → completed/failed/canceled), and the protocol has an explicit `TASK_STATE_AUTH_REQUIRED` state for cases where an agent needs the human client to step in and authorize an action mid-task — a built-in human-in-the-loop checkpoint rather than an implicit rule. As of 2026, the specification has moved toward signed Agent Cards for verifiable identity, and the protocol has broadened beyond a single-vendor announcement toward wider industry participation. (Sources: [A2A Protocol Specification](https://a2a-protocol.org/latest/specification/), [a2aproject/A2A on GitHub](https://github.com/a2aproject/A2A), [Google Developers Blog — Announcing A2A](https://developers.googleblog.com/en/a2a-a-new-era-of-agent-interoperability/), [Rost Glukhov — A2A in 2026](https://www.glukhov.org/ai-systems/comparisons/a2a-protocol-2026-adoption/), accessed 2026-08-30.) A2A's model is notably different from Multica's or GitHub's: it does not gate on "was a human in the chain" as a binary; it gates on standard authn/authz per-hop (the server authorizes each request based on authenticated client identity and its own policy), and pushes the human-approval decision into the task state machine as an explicit, visible step rather than a silent refusal.

### Microsoft Copilot Studio / Agent 365

Copilot Studio governs who may *chat with* or *author* an agent via sharing settings (owner, collaborator/"can edit," chat-only/"can chat," or revoked), enforced through tenant policy and Entra-based access control; agents "do not get unrestricted or implicit access to tenant data" purely by virtue of being agents. (Source: [Microsoft Learn — Share agents with other users](https://learn.microsoft.com/en-us/microsoft-copilot-studio/admin-share-bots), accessed 2026-08-30.) The larger and more relevant 2025–2026 development is **Agent 365**, Microsoft's enterprise control plane for AI agents (announced at Ignite 2025, GA to commercial customers reported as of May 1, 2026), built on **Entra Agent ID** — extending Microsoft's human-identity plane to non-human actors so that agents can be authenticated, authorized, audited, and governed with the same machinery as employee accounts. Its five stated capabilities are Registry (a single inventory of every agent, with ownership/deployment/permissions/policy metadata), Access Control (policy-based, conditional access via Entra), Visualization, Interoperability, and Security/compliance integration with Defender and Purview. (Sources: [Microsoft 365 Blog — Agent 365](https://www.microsoft.com/en-us/microsoft-365/blog/2025/11/18/microsoft-agent-365-the-control-plane-for-ai-agents/), [Microsoft Learn — Agent Registry convergence](https://learn.microsoft.com/en-us/entra/agent-id/agent-registry-convergence), accessed 2026-08-30.) Specific documentation describing an *agent-to-agent invocation* permission model distinct from this general identity/access-control framing could not be found — Agent 365's public materials describe governance of agents as first-class identities, not a specific "who may @-mention whom" primitive comparable to Multica's or Slack's.

### OpenAI Agents SDK

The Agents SDK's primary multi-agent pattern is the **handoff**: one agent transfers an in-progress conversation to another agent via the `handoff()` function, and the receiving agent inherits the conversation history and takes over. The SDK documents two collaboration patterns — handoff (full transfer of control) and "agent-as-tool" (one agent calls another as a callable tool without transferring the conversation). (Source: [OpenAI Agents SDK — Handoffs](https://openai.github.io/openai-agents-python/handoffs/), [OpenAI Agents SDK — Agents](https://openai.github.io/openai-agents-python/agents/), accessed 2026-08-30.) This is architecturally distinct from the platforms above: handoffs and agent-as-tool calls happen *within a single orchestrated run that a human or top-level caller initiated*, so origin-gating in the Multica/GitHub sense (is there a human anywhere in this specific call's ancestry) is less of a live problem — the human origin is structurally guaranteed by how a run starts. The SDK does not appear to define a public/private permission mode for one independently-deployed agent calling another arbitrary agent it doesn't share a runtime with — that's closer to A2A's problem space than the Agents SDK's.

### Anthropic Claude Code — subagents and Agent Teams

Claude Code has two built-in multi-agent primitives. **Subagents** are specialized assistants with their own context window, system prompt, and tool permissions, invoked within a single session — again, a human-initiated session by construction. **Agent Teams** (experimental, opt-in via `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`) let multiple Claude Code instances coordinate as teammates, with one session acting as team lead, assigning tasks and synthesizing results from parallel members. (Source: [Claude Code Docs — Agent Teams](https://code.claude.com/docs/en/agent-teams), [Claude Platform Docs — Multiagent orchestration](https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration), accessed 2026-08-30.) As with the OpenAI SDK, both mechanisms nest inside a human-originated top-level session; there is no publicly documented cross-deployment "agent calls a stranger agent" permission surface comparable to Multica's Access settings or A2A's agent cards. Anthropic's own applied multi-agent work (the Research feature's orchestrator-worker system, where a lead agent decomposes a query and dispatches parallel subagents, achieving a reported 90.2% improvement over single-agent baselines on internal evals, at roughly 15x the token cost of a single chat) is a useful data point on *why* platforms want tight control over agent-initiated fan-out — the cost and coordination overhead of letting agents freely spawn more agent work is real and measured, not hypothetical. (Source, via secondary summary of Anthropic's engineering writeup: [ZenML LLMOps Database — Building a Multi-Agent Research System](https://www.zenml.io/llmops-database/building-a-multi-agent-research-system-for-complex-information-tasks), [ByteByteGo — How Anthropic Built a Multi-Agent Research System](https://blog.bytebytego.com/p/how-anthropic-built-a-multi-agent), accessed 2026-08-30 — the original engineering.anthropic.com post was not independently fetched in this pass, so treat the specific 90.2%/15x figures as reported-by-secondary-source rather than primary-verified here.)

### Discord

Discord bots by convention check the `bot`/`is_bot` flag on incoming messages and ignore other bots to avoid loops, but this is application-level discipline, not a platform-enforced rule — Discord's own community forum has an open, unresolved feature request asking Discord to let bots deliberately trigger other bots' commands, confirming there is no first-class platform primitive for sanctioned bot-to-bot command dispatch as of the request. (Source: [Discord Support Community — "bots can trigger other bots with commands"](https://support.discord.com/hc/en-us/community/posts/360066185652--suggestion-bots-can-trigger-other-bots-with-commands), accessed 2026-08-30.) Discord does enforce mention-suppression at the API level via the `allowed_mentions` field, which lets a bot's message avoid pinging `@everyone`, roles, or users it quotes — a related but distinct control (suppressing *notification*, not gating *invocation*). (Source: [Discord API docs discussion on allowed mentions](https://github.com/discord/discord-api-docs/pull/1396), accessed 2026-08-30.)

## Why the "No Human Originator" Rule Exists

Across every platform surveyed, the justification clusters around four concerns, each independently sufficient to motivate the rule:

**Loop and ping-pong prevention.** This is the most explicitly documented reason (GitHub's recursion guard, Multica's anti-loop gate). Two agents that can freely trigger each other with no circuit breaker will, under fairly ordinary conditions (a coordinator asking for confirmation, a reviewer asking a clarifying question), produce an unbounded exchange. GitHub's fix is structural (bot-sourced events don't retrigger by default); Multica's is currently a blunt member-only filter that over-blocks legitimate one-shot callbacks along with genuine loops, which is precisely the tension its own issue tracker is trying to resolve.

**Cost blow-up.** Anthropic's own multi-agent research system reportedly runs at roughly 15x the token cost of single-agent chat for legitimate parallel fan-out (per secondary source above); an uncontrolled agent-to-agent loop compounds that multiplicatively per round-trip. A platform that lets any agent silently spawn or re-trigger any other agent has effectively removed the human cost-approval checkpoint from its billing loop.

**Accountability and attribution — who is the principal?** This is the theme underlying the OAuth/identity research: RFC 8693 token exchange, Microsoft's On-Behalf-Of flow, and Entra Agent ID all exist to answer "who authorized this action" in delegation chains that cross from a human into one or more agents. WorkOS and ScrambleID's writeups both describe the target pattern as Human → Agent A → Agent B → Tool C → Resource D, with the original delegator's identity preserved at every hop via `act`/`obo` claims so the chain stays auditable end to end. (Sources: [WorkOS — AI agents and the multi-hop delegation problem](https://workos.com/blog/oauth-multi-hop-delegation-ai-agents), [ScrambleID — Multi-Hop Agent Delegation Chains](https://www.scrambleid.com/learn/multi-hop-agent-delegation-chains), [Microsoft Learn — Agent OAuth on-behalf-of flow](https://learn.microsoft.com/en-us/entra/agent-id/agent-on-behalf-of-oauth-flow), accessed 2026-08-30.) An agent-to-agent call with no human anywhere in its ancestry is, in this framework, an action with no clear principal — nobody to bill, nobody who consented, nobody accountable if it goes wrong.

**Prompt-injection laundering through agent chains.** This is the security-research framing: the Cloud Security Alliance's applied research on "confused deputy" attacks against autonomous agents, and OWASP's 2026 Top 10 for Agentic Applications, both treat unchecked inter-agent delegation as an attack surface — a malicious instruction embedded in content one agent processes can propagate to a second agent that trusts the first as a peer, executing with the second agent's privileges rather than the injector's. OWASP's stated mitigations are strikingly close to the design patterns below: short-lived, task-scoped tokens per agent/workflow, enforced usage budgets, immutable logs of suspicious tool/agent chains, and re-checking authorization at each privileged hop via a centralized policy engine. (Sources: [CSA — Confused Deputy Attacks on Autonomous AI Agents](https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-agent-confused-deputy-prompt-injection/), [OWASP Top 10 for Agentic Applications 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/), [Auth0 — Lessons from OWASP Top 10 for Agentic Applications](https://auth0.com/blog/owasp-top-10-agentic-applications-lessons/), accessed 2026-08-30.) A "no human in the chain" default is a blunt but effective way to cut off this laundering path entirely, at the cost of also cutting off legitimate peer collaboration.

## Design Patterns Observed

Synthesizing across the verified sources, a consistent vocabulary of controls emerges, even though no single platform implements all of them:

- **Permission modes on the receiving agent.** Multica's Access (Only me / workspace / specific people) and the incident's described `private`/`public_to` are the same idea at different granularity: a receiver-side setting for who may invoke, independent of what the invocation is *about*.
- **Explicit invocation-target allowlists**, scoped narrowly (e.g., to a workspace or a named set of peer agents) rather than a blanket "public" — this is the `invocation_targets` concept in the incident, and structurally similar to Copilot Studio's agent-sharing roles and A2A's per-server authorization policy.
- **Hop-count / TTL on call chains** to bound worst-case loop damage even when direct invocation is permitted — not found explicitly documented as a shipped feature on any surveyed platform, but a natural complement to GitHub's "don't retrigger from a bot-sourced event" rule and repeatedly recommended in the OAuth delegation-chain literature (bounding depth, not just presence, of delegation).
- **Originator/principal propagation as metadata on the call itself** — RFC 8693's `act` and on-behalf-of `obo` claims, Entra Agent ID's dual-identity tokens (binding both the human `upn` and the agent `appid`) are the clearest verified instances of this pattern; it lets a receiving agent (or platform) answer "was a human ever involved, and who" without relying on a coarse binary member/agent flag.
- **Budget caps per chain** — implied strongly by OWASP's "usage budgets" mitigation and by the cost concerns above, though no platform was found documenting a shipped per-chain token/dollar budget enforced automatically across an agent-to-agent call graph.
- **Dedup of mention loops** — Multica explicitly does this for the simplest case ("when A @-mentions B and B @-mentions A back, the system merges duplicate runs at the same moment") but, by its own docs, does not decide when the collaboration should end; that is left to agent instructions.
- **Silent-drop vs. visible-refusal.** This is the single largest quality-of-implementation gap across the survey. GitHub's approval-required state is fully visible in the Actions UI. A2A's `AUTH_REQUIRED` task state is a first-class, visible state in the task lifecycle. Multica's documented behavior for a blocked @-mention is a middle ground — the comment posts, but the trigger preview (visible at authoring time) explains why the run won't start; the harder case, an *agent*-originated mention hitting the same gate with nobody watching the trigger preview in real time, is exactly the failure mode issue #2120 documents as "the Coordinator is never woken up... without any error signal." The incident this article is built around is a sharper version of the same thing: the refusal happened server-side with no comment, no log entry visible to the operator, and no distinguishing signal from ordinary message loss.

## Failure Modes and Debugging

**Silent drops that look like infrastructure failure.** The defining symptom: an operator sees a coordinator that stopped progressing and reasonably suspects a dead queue, a crashed runtime, or a webhook delivery failure — because a permission refusal and a lost message produce identical externally-visible symptoms (nothing happened). Debugging this class of failure requires checking, in order: (1) did the callback actually fire on the sender's side — check the reviewer/sender's own run logs, not just the receiver; (2) does the receiver's permission/access record explicitly allow the sender, by identity, not just by role; (3) is there a platform-level audit log of *refused* invocations, separate from the log of accepted ones — most platforms surveyed here do not clearly document one.

**Asymmetric permissions.** A can call B does not imply B can call A. This is easy to overlook because it is invisible in the happy path — the first leg of a coordinator → reviewer → coordinator round trip works fine, so the pattern looks correct until the second leg silently fails. It is exactly what happened in the motivating incident: dispatch worked, callback didn't, and the asymmetry was the coordinator's own default-private setting, not anything the reviewer did wrong.

**Default-private agents created by other agents.** When an agent (not a human) creates a new peer agent — as the coordinator did when it created the reviewer in the motivating incident — the new agent typically inherits whatever the platform's default Access/permission setting is (Multica: owner-only / "Only me"). If the creating agent doesn't explicitly widen that default at creation time, every subsequent peer that isn't the literal owner will hit the same silent-drop wall. This is a structural trap: the agent best positioned to know it will need peer callbacks (the creator, mid-orchestration) is also the one most likely to accept the platform default without thinking about it, because agents don't reliably reason about their own future inbound permission needs unless explicitly instructed to.

## Recommendations for a Small Self-Hosted Platform (Zylos-style)

These are analysis and recommendation, not verified facts about any shipping product — offered as design guidance grounded in the patterns above.

1. **Default new agents to workspace-scoped, not fully private, but require explicit peer allowlisting for cross-agent callbacks.** Full "Only me" defaults are safe against strangers but actively break the coordinator/reviewer pattern that is the entire point of a multi-agent task platform. A better default: an agent accepts invocations from any human in its owning workspace by default (matching Multica's least-surprising path), but agent-originated invocations require the *receiving* agent to have the *calling* agent's identity on an explicit allowlist — never a blanket "accept all agent-originated calls," which reopens the injection-laundering risk.

2. **Make the creating agent set peer permissions at creation time, not as an afterthought.** If Agent A creates Agent B specifically to hand off work and expects a callback, the creation step should require (or strongly prompt for) an explicit `invocation_targets`-style entry naming A on B's record, in the same operation that creates B. Leaving it as a separate, optional, later step is exactly how the motivating incident happened — the coordinator had no reason to think about its own inbound permissions while focused on dispatching the review.

3. **Log every refused invocation, not just accepted ones, and make that log queryable by the caller, not only the receiver.** The single biggest debugging cost in the motivating incident was that the refusal was invisible to both agents involved — the reviewer had no signal its callback was rejected, and the coordinator had no signal it had refused anything. A minimal audit record (timestamp, caller identity, callee identity, chain/originator metadata, permission mode evaluated, allow/deny) resolves this class of failure from "looks like infra is broken" to "looks like a one-line permission fix" in a single log query.

4. **Post a visible refusal, not a silent one, when a permission check fails an agent-to-agent mention.** Following GitHub's and A2A's pattern of surfacing state rather than swallowing it: when B refuses A's callback, post a system comment on the relevant issue/thread — "Invocation from agent-x refused: permission_mode=private, no human originator in chain" — so a human watching the thread (or the calling agent itself, if it's instructed to check) sees the refusal in the same place they'd see a normal reply. This alone would have turned the motivating incident from an hours-long "why did my coordinator go quiet" investigation into an immediately visible one-line diagnosis.

5. **Carry originator/chain metadata on every inter-agent call, not just a binary human/agent flag.** Borrowing from RFC 8693 and Entra Agent ID's dual-claim pattern: propagate a lightweight chain record (originating human, if any; ordered list of agent hops; depth) with each invocation rather than collapsing the decision to a single `actorType == member` check. This gives future policy more to work with than Multica's current binary gate — e.g., "allow agent-originated calls only if a human appears somewhere in the last N hops" is expressible with chain metadata and is not expressible with a flat member/agent flag.

6. **Bound chains with hop count or TTL even where invocation is otherwise permitted.** A permission allowlist stops *unauthorized* loops; it does not stop *authorized* agents from producing a long or runaway exchange once they're allowed to talk to each other at all (the exact gap Multica's own docs flag: merging duplicate simultaneous runs, but not deciding when collaboration ends). A hop-count or TTL ceiling, enforced by the platform rather than left to agent instructions, is a cheap backstop against exactly the ping-pong scenario the human-originator rule was designed to prevent in the first place — but applied at the mesh level instead of only at the outer human/agent boundary.
