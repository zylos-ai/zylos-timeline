## Executive Summary

Every autonomous agent built on a transformer eventually hits a hard wall: the context window. Production systems now treat this not as an edge case but as a routine operational event — something to detect, checkpoint, and recover from, the same way distributed systems treat node failure. Three broad strategies have converged across the industry in 2025–2026: **server/client-side compaction** (summarize the transcript, keep working), **externalized memory files** (write durable state to disk/DB, re-read on resume), and **durable-execution replay** (treat each step as a checkpointed, idempotent unit of work). No framework relies on a single one of these — Anthropic explicitly recommends combining compaction with the memory tool, and Anthropic's own "harness engineering" guidance for long-running coding agents leans almost entirely on git commits and structured progress files rather than context tricks at all. The hardest unsolved problems are not mechanical (how to serialize state) but epistemic: agents that survive a rotation can carry forward **stale or confabulated beliefs** about what they already did, and side-effecting tool calls made near a rotation boundary create real double-execution risk unless idempotency keys are enforced end-to-end.

## The Problem

A context window is finite (128K–1M tokens depending on model/provider), but an autonomous task — a multi-day coding effort, a standing operations agent, a research loop — is not. Two distinct sub-problems fall under "rotation":

1. **In-session degradation before exhaustion.** Chroma's controlled study across 18 frontier models (GPT-4.1, Claude Opus 4, Gemini 2.5) found *monotonic* accuracy decay as input length grows, well before the hard token limit — driven by "lost-in-the-middle" attention bias, quadratic attention dilution, and distractor interference from semantically similar but irrelevant content already in context ([Chroma, "Context Rot"](https://www.trychroma.com/research/context-rot)). This means agents should rotate *proactively*, not just when the window is literally full.
2. **Hard exhaustion / process handoff.** When the transcript can no longer grow, something must give: summarize it, externalize it, or start a new process that reconstructs equivalent state from durable storage.

Both sub-problems force the same design question: what must survive the transition, and what is safe to throw away?

## State of Practice: A Framework Survey

**Claude Code / Claude platform (Anthropic).** Anthropic ships two complementary, explicitly distinguished mechanisms. *Compaction* is client- or server-side: it takes a conversation nearing the limit, sends it to a summarization pass, and reinitializes the window with the condensed result — Claude Code's implementation is documented to preserve "architectural decisions, unresolved bugs, and implementation details" while discarding redundant tool outputs ([Anthropic, "Effective context engineering for AI agents"](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Observed real-world compaction ratios reduce ~132K tokens to ~2.3K, a roughly 98% reduction, per third-party analysis of Claude Code sessions. Auto-compaction fires at a configurable trigger (recent versions target ~83.5% of window utilization, tunable via `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`) ([ClaudeLog FAQ](https://claudelog.com/faqs/what-is-claude-code-auto-compact/); [okhlopkov.com, "Claude Code /compact"](https://okhlopkov.com/claude-code-compaction-explained/)). Separately, *context editing* (`clear_tool_uses_20250919`, `clear_thinking_20251015`) is a purely server-side, surgical mechanism that clears old tool results/thinking blocks and replaces them with placeholders rather than summarizing — Anthropic recommends it as the primary lever, with compaction as fallback for genuinely long-running tasks ([Anthropic, Context Editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)). Layered on top is the *memory tool*: a client-executed file interface (`/memories/*`) that Claude is instructed to check before starting any task, on the explicit assumption baked into the auto-injected system prompt that "your context window might be reset at any moment" ([Anthropic, Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)). Anthropic's guidance is explicit that memory and compaction are complementary, not substitutes: "compaction keeps the active context small without client-side bookkeeping, and memory preserves the information that must survive summarization."

**Anthropic's long-running-agent harness pattern.** For genuinely multi-day autonomous coding work, Anthropic's engineering team bypasses in-context tricks almost entirely in favor of filesystem/git state. An *initializer session* sets up `init.sh`, a `claude-progress.txt` log, and a JSON feature checklist (200+ items in their claude.ai-clone case study) where each subsequent session may only flip a `passes: true/false` boolean — explicitly forbidden from editing or removing test definitions, "because this could lead to missing or buggy functionality." Every new session runs a fixed startup ritual: `pwd`, read git log, read the progress file, pick the highest-priority unfinished feature, boot the dev server, run one verification test — before doing anything else ([Anthropic, "Effective harnesses for long-running agents"](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). Git commits function as the actual checkpoint boundary; the progress file is a human/agent-readable index into that history.

**LangGraph (LangChain).** Checkpointing is a first-class graph primitive: every superstep persists a full state snapshot keyed by `thread_id`, enabling resume after interruption, human-in-the-loop pauses, or crash recovery ([LangChain, Persistence docs](https://docs.langchain.com/oss/python/langgraph/persistence)). The default `InMemorySaver`/`MemorySaver` is explicitly non-durable — state vanishes on process restart — and production deployments are directed to `PostgresSaver`/`SqliteSaver`. A documented tradeoff: because a checkpoint is written per superstep, long-running agents accumulate large checkpoint volumes, requiring explicit pruning/retention policies. LangGraph separates *short-term memory* (checkpointer, thread-scoped) from *long-term memory* (a cross-thread store), mirroring the working-memory/episodic-memory split seen elsewhere.

**Letta (formerly MemGPT).** Pioneered the "LLM as OS" framing: a three-tier hierarchy of *core memory* (small, always in-context, agent-editable "RAM"), *recall memory* (searchable full history, "disk cache"), and *archival memory* (long-term store queried via tool calls) ([Letta, "Memory Blocks"](https://www.letta.com/blog/memory-blocks/)). Memory blocks are individually persisted with a stable `block_id`; the active context window is "compiled" from current DB block values on each request rather than replayed from a message log. Notably, Letta favors *explicit, tool-mediated* editing over automatic overflow summarization — the agent itself decides what to page in or out, rather than a framework-level trigger doing it silently.

**OpenAI Agents SDK.** Handoffs default to full transcript inheritance — "it's as though the new agent takes over the conversation, and gets to see the entire previous conversation history" — with `input_filter` and a beta `nest_handoff_history` mode available to compact prior turns into ordered summary segments while keeping recent items lossless ([OpenAI Agents SDK, Handoffs docs](https://openai.github.io/openai-agents-python/handoffs/)). Critically, application-level state (not just conversational context) must be threaded explicitly through `RunContextWrapper.context`; nothing carries over implicitly, which is a common source of dropped state in practice.

**AutoGen (Microsoft).** State handling is comparatively primitive: `save_state`/`load_state` serialize message threads and group-chat manager state to arbitrary JSON, with no native crash-recovery or automatic checkpointing layer — open GitHub issues have requested runtime-level checkpoint/rollback for years without being fully resolved ([AutoGen docs, Managing State](https://microsoft.github.io/autogen/stable//user-guide/agentchat-user-guide/tutorial/state.html); [autogen#3619](https://github.com/microsoft/autogen/issues/3619)).

**OpenHands.** Built around a single mutable `ConversationState` object as the source of truth, with a complete event log (user messages, agent actions, system events) persisted under a `persistence_dir` + `conversation_id`, restorable from a different process ([OpenHands SDK, Persistence docs](https://docs.openhands.dev/sdk/guides/convo-persistence)). A known gap: ACP-style conversations (wrapping Claude Code, Codex, Gemini CLI as sub-processes) currently cannot resume once a cloud sandbox is recycled, since the underlying tool's own session ID isn't persisted — an illustration of how handoff fidelity degrades at process boundaries that cross tool ownership.

**Durable-execution substrates (Temporal, Inngest, Restate).** Increasingly used as the reliability layer *underneath* agent frameworks. Temporal recovers workflows by replaying event history rather than snapshotting memory; each named step is cached so a restart resumes without re-executing completed work, and expensive/non-deterministic LLM calls are cached rather than reissued ([Inngest, "Durable Execution: The Key to Harnessing AI Agents"](https://www.inngest.com/blog/durable-execution-key-to-harnessing-ai-agents)). This model is orthogonal to context-window management but essential for the side-effect half of the problem: an idempotency key tied to workflow state must accompany any tool call that writes external state, or replay after a rotation can execute it twice.

## Handoff-Content Taxonomy: What to Carry, What to Drop

**Must survive:**

- Active task definition and success criteria (the equivalent of Anthropic's feature checklist)
- Pending obligations — outstanding tool calls awaiting results, unacknowledged user requests, scheduled follow-ups
- Irreversible-decision log — architectural choices, constraints already ruled out, and *why* (so they aren't silently re-litigated)
- Side-effect ledger — what external actions were already taken, with idempotency keys, to prevent re-execution
- Channel/conversation identity — which user, which thread, which reply path, so continuity is externally invisible

**Safe to drop or compress:**

- Raw tool outputs already synthesized into a conclusion (large file reads, search results, stack traces once diagnosed)
- Redundant back-and-forth that converged on a decision already recorded elsewhere
- Full reasoning/thinking traces once their conclusion is captured (Claude's `clear_thinking` edit targets exactly this)
- Exploratory dead ends, *provided* the fact that they were dead ends (not just their content) is preserved — dropping the content but losing the "already tried, failed" fact is a major source of repeated wasted work

The dividing line, per Anthropic's context-engineering guidance, is roughly: keep anything whose *absence* would be undetectable until it caused a wrong decision later; compress anything whose value was already fully extracted.

## Failure Modes

- **Lost pending items.** Summarization is lossy by construction; Anthropic itself warns "overly aggressive compaction can result in loss of subtle but critical context whose importance only becomes apparent later" ([Anthropic context-engineering blog](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). A rotation that summarizes away an open question or unconfirmed commitment silently drops it.
- **Double execution / non-idempotent replay.** When a handoff or crash-recovery replays a step whose side effect (an email sent, a record written, a payment) already fired, naive retry duplicates it. Distributed-systems practice — idempotency keys bound to workflow/step state — transfers directly, but many agent frameworks (AutoGen notably) still lack native support ([Temporal/Inngest analyses](https://www.inngest.com/blog/durable-execution-key-to-harnessing-ai-agents)).
- **Stale self-belief and memory confabulation.** Long-lived memory stores accumulate assertions that were true once but no longer are, and — worse — agents can write *confidently incorrect* accounts of what they did into memory, then act on that false record across resets. The STALE benchmark specifically probes whether agents can detect that a stored memory is invalidated by new evidence ([STALE, arXiv 2605.06527](https://arxiv.org/pdf/2605.06527)); separate work on memory confabulation shows these false beliefs can be self-reinforcing, since an agent that "concludes" a path always fails may never revisit it ([arXiv 2605.29463](https://arxiv.org/html/2605.29463)).
- **Premature victory / abandoned partial work.** Anthropic's harness postmortems name this explicitly: agents mistake partial progress for completion, or abandon a half-finished feature mid-session with no artifact marking it incomplete — solved only by structured, machine-checkable state (the `passes: true/false` checklist) rather than prose summaries.
- **Cross-process handoff loss at tool boundaries.** OpenHands' inability to resume ACP sub-agent sessions after sandbox recycling shows that handoff fidelity is only as strong as the *weakest* persisted layer — a wrapper framework can checkpoint its own state perfectly while the wrapped tool's session ID silently evaporates.

## Design Patterns and Recommendations

1. **Rotate before exhaustion, not at it.** Given context rot's monotonic degradation well below the hard limit, trigger summarization/handoff at a conservative utilization threshold (Claude Code's ~83.5% is a reasonable anchor) rather than waiting for a hard failure.
2. **Separate mechanism by content type.** Use surgical clearing (context editing) for bulky, already-synthesized tool output; reserve full summarization (compaction) for genuinely long-running conversational state; use externalized files/DB for anything that must survive process death, not just window rotation.
3. **Make state machine-checkable, not prose-summarized, wherever correctness matters.** A boolean checklist or structured JSON progress file is far harder to hallucinate past than a paragraph summary.
4. **Idempotency keys on every side-effecting call, always, tied to a stable run/step ID** — this is non-negotiable once an agent can act on the outside world across a rotation boundary.
5. **Record what was tried and failed, not just what succeeded** — the negative-result log is what prevents repeated wasted exploration after a reset.
6. **Treat sub-agents as a context-isolation primitive, not just a parallelism one.** Returning a 1–2K token distilled summary from a 50K-token sub-exploration is itself a rotation strategy, applied continuously rather than at a threshold.
7. **Verify on resume, don't just believe the checkpoint.** Anthropic's startup ritual (re-run a smoke test before continuing) guards against a checkpoint that was itself written from a stale or wrong belief.

## Open Questions

The field has converged on *mechanisms* faster than on *epistemics*. It remains unresolved how an agent should detect, at resume time, that its own carried-forward beliefs are stale rather than trusting its last checkpoint by default (STALE and confabulation research are early, not yet production-standard). There is no widely adopted cross-framework standard for a handoff envelope — every framework (LangGraph threads, OpenHands conversation state, Claude Code progress files, Letta memory blocks) uses an incompatible bespoke format, which blocks portability of a running agent between runtimes. And the idempotency story for *probabilistic* side effects — where a retried LLM call may legitimately produce a different, not-obviously-duplicate action — is still handled ad hoc rather than with a general primitive, unlike the settled case of deterministic workflow steps in systems like Temporal.
