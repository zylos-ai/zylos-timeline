## Executive Summary

Every job queue faces the same failure mode: a worker atomically claims an item — moving it from *pending* to *running* — and then dies before writing back a terminal state. The item is now orphaned: not pending (so nobody will retry it), not actually running (so it will never complete), just stuck. Every practical queue system needs an answer to "how do we notice, and what do we do about it?" This article surveys the two dominant answers.

The first family, **timeout/lease-based recovery**, is the default choice for systems where the claim itself carries no information about *who* holds it or whether they're still alive: Amazon SQS's [visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html) (30s default), beanstalkd's [TTR](https://github.com/beanstalkd/beanstalkd/blob/master/doc/protocol.txt) ("time to run"), Faktory's `reserve_for` (1800s default), Kafka's consumer-group `session.timeout.ms` (10s default), and Temporal's activity heartbeat/`start_to_close_timeout`. A claim is presumed orphaned once a clock expires, whether or not the claimer actually died — the timeout can't distinguish "crashed" from "just slow," so it trades false positives (duplicate delivery) for bounded recovery latency.

The second family, **process-lifecycle-anchored recovery**, is available only when the claimer is a *single writer whose own restart is proof of death*: if the claimant process is the only thing that could hold the claim, and the claim mechanism is itself tied to that process's lifetime (a session-scoped Postgres advisory lock, a private per-process Redis queue registered at boot), then a fresh start of that exact process is unambiguous evidence that any lingering claim under its name is orphaned — zero false positives, no clock needed. Sidekiq Pro's `super_fetch`, Postgres `SELECT ... FOR UPDATE SKIP LOCKED` workers, and que's session-level `pg_try_advisory_lock` all exploit this. RabbitMQ's unacked-message requeue on channel/connection close sits in between: connection-lifecycle-anchored, faster and more precise than a fixed timeout, but still probabilistic once TCP heartbeats and network partitions enter the picture.

The two families aren't interchangeable. Lifecycle-anchored recovery is a *shortcut* that only holds under single-writer or session-bound assumptions; the moment you scale out to multiple concurrent claimers (or restart-with-failover), the shortcut breaks and you need fencing tokens or leases again — which is exactly what SKIP LOCKED and advisory locks quietly reintroduce as their multi-worker safety mechanism. Understanding which family a queue design needs — and why — is one of the more consequential and under-discussed decisions in building a job dispatcher.

## The Orphaned-Claim Problem

The core hazard is a race between "claim" and "commit" with no atomicity spanning both. A typical claim operation looks like:

```
BEGIN
  SELECT item FROM queue WHERE state = 'pending' LIMIT 1 FOR UPDATE
  UPDATE queue SET state = 'running', claimed_by = worker_id, claimed_at = now()
COMMIT
```

Between that commit and the eventual `UPDATE queue SET state = 'done'`, the worker can be killed by an OOM reaper, a `kill -9`, a hardware fault, a deploy that doesn't drain in time, or a network partition that severs it from the coordinator. There is no way to make "claim it and finish it" a single atomic step, because "finish it" means doing real work (calling an API, writing a file, sending an email) that can take arbitrarily long and can't happen inside a lock-holding transaction.

So every queue design has to answer a detection question and a recovery question separately:

1. **Detection** — how do we know a claim is orphaned, as opposed to just slow?
2. **Recovery** — once detected, do we requeue it (at-least-once, possible duplicate execution), and if so, where does it go in line?

The rest of this article is a tour of how different systems answer both.

## Family A: Timeout and Lease-Based Recovery

The unifying idea: a claim carries an expiration. If the claimant hasn't renewed or completed it by the deadline, *anyone* is allowed to reclaim the item — no proof of death required, just proof of silence.

### Amazon SQS: visibility timeout

When a consumer calls `ReceiveMessage`, SQS doesn't delete the message; it makes it invisible to other consumers for the queue's [visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html), 30 seconds by default, tunable from 0 seconds to 12 hours. If the consumer doesn't call `DeleteMessage` before the timeout expires, the message becomes visible again and any consumer (including the original one, on a second poll) can receive it. A worker that's still alive but running long can call `ChangeMessageVisibility` to extend the window — effectively a heartbeat/lease-renewal call. Because standard SQS queues don't have a global concept of "the claimant is dead," the entire detection mechanism is the clock: a 45-second job with a 30-second timeout *will* be redelivered to a second worker while the first is still finishing, producing genuine concurrent duplicate execution. AWS's own guidance is blunt about this: [duplicate processing is "almost always a configuration problem, not a platform defect"](https://awsi.click/en/articles/sqs-at-least-once-delivery-internals/) — the timeout must be sized to worst-case processing time, not average. A [redrive policy](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html) with `maxReceiveCount` (default 10) caps how many times a message can be redelivered before it's shunted to a dead-letter queue, which is the safety valve for a message that's poison rather than merely slow.

### Beanstalkd: TTR (time to run)

Beanstalkd's [protocol](https://github.com/beanstalkd/beanstalkd/blob/master/doc/protocol.txt) makes the lease explicit in the verb names. A worker calls `reserve` (optionally `reserve-with-timeout <seconds>` to bound the wait for a job to appear) and gets a job with a **TTR** — the number of seconds the worker is allowed to run it. The TTR timer starts the moment the job is reserved. If it expires before the worker calls `delete`, `release`, or `bury`, the job silently reverts to the ready queue for another consumer. A worker can call `touch` to reset the countdown mid-job, and the server holds back roughly one second of "safety margin" before expiry, signaled by a `DEADLINE_SOON` response, so a well-behaved long-running worker gets an explicit warning rather than being surprised by expiry. This is architecturally identical to SQS's model — timer-based, no crash detection, false positives possible if TTR is undersized.

### Faktory: reservations

Contribsys's [Faktory](https://github.com/contribsys/faktory/wiki/Worker-Lifecycle) uses the same pattern under the name "reservation." `FETCH` reserves a job for `reserve_for` seconds (default 1800 = 30 minutes); the worker must `ACK` or `FAIL` within that window or the job is released for re-execution, "treated identical to a FAIL." Faktory bounds the configurable range (a maximum of 24 hours) precisely because operators kept setting it too high or too low; the reservation timeout is the single dial that trades detection latency against false-positive redelivery risk.

### Kafka: consumer-group session timeout and rebalancing

Kafka's mechanism is aimed at a different unit — not a single message, but ownership of a whole partition — but the shape is the same. Each consumer in a group sends periodic heartbeats to the group coordinator; if none arrive within `session.timeout.ms` (default 10 seconds on modern brokers), [the coordinator declares the consumer dead and triggers a rebalance](https://www.confluent.io/learn/kafka-rebalancing/), reassigning its partitions to surviving group members. `heartbeat.interval.ms` is conventionally set to about a third of the session timeout so multiple heartbeats can be missed before the group gives up on a member. The practical tuning tension is explicit in Kafka's own docs: `session.timeout.ms` must exceed the worst-case time between polls (including `max.poll.interval.ms` for processing-bound stalls), or a slow-but-alive consumer gets evicted and its partitions rebalanced away mid-processing — the rebalance-storm failure mode many teams hit in production.

### Temporal: activity heartbeats and task timeouts

Temporal generalizes the lease idea to long-running, potentially hours-long units of work. An activity has a `start_to_close_timeout` and, for anything long-running, a `heartbeat_timeout` — the activity implementation must call back periodically or the server considers it dead and reschedules it (subject to the activity's retry policy) even though `start_to_close_timeout` hasn't elapsed. If a worker process crashes outright, [running activities on its task queue simply time out via heartbeat or start-to-close expiry](https://community.temporal.io/t/handling-workflow-task-timeout-due-to-sticky-queue-task-timeout/16443), and pending/retried activities wait for another worker to poll the same task queue. Temporal's sticky workflow-task queues add a wrinkle worth naming as a caution: because a workflow's next task is directed back to the worker that cached its history (for replay efficiency), a worker that restarts without cleanly evicting its sticky affinity can produce a `Workflow Task Timed Out` until the `schedule_to_start_timeout` on the *normal* (non-sticky) task queue kicks in and lets another worker pick it up — a reminder that even lease-based systems accumulate special-case timeouts as they add optimizations.

### The shared trade-off in Family A

All five systems above share the same fundamental exchange: **bounded detection latency in exchange for unavoidable false positives.** Set the timeout short, and you detect real crashes fast but risk reclaiming a claim that's simply slow — producing duplicate, concurrent execution of the same logical unit of work (SQS's classic failure mode). Set it long, and false positives vanish but a genuinely crashed worker's item sits orphaned-but-undetected for the full window (Faktory's 30-minute default, if unconfigured, means a crashed worker's job doesn't even *reappear* for half an hour). None of these systems can tell the difference between "the process died" and "the process is just running behind" — the timeout is a heuristic standing in for a fact they can't observe directly. This is why all of them push toward **idempotent job handlers** as a design requirement, not an optional nicety: at-least-once delivery under a timeout model is a structural property, not an edge case.

## Family B: Process-Lifecycle-Anchored Recovery

The alternative approach becomes available under a specific and fairly narrow condition: the claim is held by exactly one process (a single-writer dispatcher, or a per-worker private structure), and the *mechanism* that represents the claim is itself bound to that process's — or that process's connection's — lifetime. Under that condition, the claimant's own restart is not a heuristic signal; it's a logical proof. If the process that held claim X has just started fresh, and claim X is still marked held by that process's old identity, then X is unambiguously orphaned — there is no other explanation, no clock required, and no false-positive case, because "the claimant restarted" and "the claim is orphaned" are the same fact observed twice.

### Sidekiq: from BRPOP to super_fetch

Sidekiq's original ("basic") fetcher used Redis `BRPOP` to pull a job directly off the queue list — simple, but if the process died between `BRPOP` and finishing the job, the job was just gone; there was no record it had ever been claimed. Sidekiq Pro's [`super_fetch`](https://github.com/sidekiq/sidekiq/wiki/Reliability) fixes this with a per-process private queue: at startup, each Sidekiq process registers a uniquely named private queue in Redis and fetches jobs with an atomic pop-and-push (`RPOPLPUSH`, or `BLMOVE` on modern Redis) that moves a job from the public queue straight into that process's private in-progress queue. When the job finishes, Sidekiq removes it from the private queue. If the process dies mid-job, the job is left sitting in a private queue whose owning process no longer exists.

The recovery mechanism is exactly the process-lifecycle argument: [when a Sidekiq process starts up, or when another process notices via heartbeat expiry that a peer is gone, `super_fetch` scans for private queues belonging to processes that are no longer registered and re-queues their contents](https://www.bigbinary.com/blog/increase-reliability-of-background-job-processing-using-super_fetch-of-sidekiq-pro). In practice Sidekiq Pro runs this check on every process boot (checking heartbeats that expire after ~60 seconds of silence, with a full `SCAN` sweep at most once an hour as a backstop), but the documentation is candid that the *sweep* half is still timing-dependent — "super_fetch might recover jobs in 5 minutes or in 3 hours; restarting a process is the best way to signal Sidekiq to look for orphans." That's the tell: the fast, precise path is startup-triggered reclamation of a known-dead peer's private queue; the slow, imprecise path (the periodic sweep) is really Family A's timeout-based sweeper bolted on as a backstop for the cases where nobody restarts.

### Postgres `SKIP LOCKED` workers: the claim *is* the lock

The cleanest embodiment of lifecycle-anchored recovery is a job queue built on `SELECT ... FOR UPDATE SKIP LOCKED`. A worker's claim transaction locks a row; the row lock, held inside a database transaction, is automatically released by Postgres the instant that transaction ends — commit, rollback, *or the connection dying*. There is no separate "claim record" that can drift out of sync with reality, because the claim and the lock are the same object. If the worker process is killed mid-job, the backend connection drops, Postgres notices at the TCP/connection level and rolls back the open transaction, and the row lock disappears — instantly making the row visible again to the next `SKIP LOCKED` scan. As one practical writeup on the pattern puts it, [the lock is tied to the transaction, so a worker crash guarantees the lock is released](https://www.netdata.cloud/academy/update-skip-locked/) — there's no timeout, no sweeper, no window of undetected orphanhood at all; detection is instantaneous because it's not really "detection," it's the database's own connection teardown.

### Postgres advisory locks: que and good_job

A closely related but subtly different mechanism is the **advisory lock** — a purely application-level, non-row-attached lock that Postgres tracks per-connection (or per-transaction). The Ruby queue [que](https://github.com/que-rb/que) claims jobs with `pg_try_advisory_lock`, a *session-level* advisory lock that is not tied to any transaction boundary; it persists across the whole job execution and is released explicitly when the job finishes — or automatically the moment the holding connection closes, which is exactly what happens when a worker process crashes. This is process-lifecycle anchoring again, just implemented at the connection layer instead of the row layer: `pg_locks` on the database shows exactly which backend holds which lock, and a crashed backend's locks vanish with it. [`good_job`](https://github.com/bensheldon/good_job), a similar Postgres-backed ActiveJob backend, defaults to the same session-advisory-lock strategy but explicitly supports switching to (or hybridizing with) `SELECT FOR UPDATE SKIP LOCKED`, because the two failure semantics aren't quite identical: a session-level advisory lock survives across multiple transactions within one connection (useful for holding a lock across retries or sub-steps) but, in the (rarer, pool-related) case where the connection itself doesn't actually close on crash — for example, behind a connection pooler that recycles rather than kills backends — the lock can leak in a way a transaction-scoped `SKIP LOCKED` row lock structurally cannot. That's a real, documented caveat: [session-level advisory locks are considered slightly riskier than transaction-scoped ones specifically because their release depends on the connection's actual teardown, not the transaction's](https://terrislinenbach.medium.com/why-for-update-skip-locked-isnt-enough-using-pg-advisory-xact-lock-d3eb9db46473), which is why some implementations now favor `pg_advisory_xact_lock` (transaction-scoped) instead — trading the ability to hold a lock across statement boundaries for a guarantee that's airtight even under connection pooling.

### Oban: startup rescue plus a named safety net

Elixir's [Oban](https://hexdocs.pm/oban/Oban.html) leans on the BEAM's own supervision model: because Oban jobs execute inside supervised processes on a node, [a node crash or restart lets Oban recover jobs that were `executing` almost immediately](https://elixirforum.com/t/oban-reliable-and-observable-job-processing/22449) — a fresh node boot is again treated as proof that anything still marked `executing` under its own name is stale. But Oban's maintainers also ship a `Lifeline` plugin with an explicit `rescue_after` timeout (commonly 30–60 minutes) as backstop for jobs that get "abandoned" without a clean restart signal — the documented failure case is a hot deploy where a node is torn down hard enough that its own graceful-shutdown rescue logic (a configurable shutdown grace period, 15 seconds by default) doesn't get to run, leaving rows stuck in `executing` with no lifecycle event to trigger a rescue. This is the same pattern as Sidekiq's sweep-as-backstop: pure lifecycle-anchored recovery is fast and precise when the lifecycle event actually fires cleanly, so every mature implementation of it keeps a timeout-based net underneath for the cases where it doesn't.

## The Middle Ground: Connection-Lifecycle Anchoring in RabbitMQ

RabbitMQ occupies an instructive middle position. With manual acknowledgements, a consumer that receives a message but never acks it leaves that message "unacked" — invisible to other consumers — indefinitely, with **no timeout at all** by default. [Detection is instead tied to the channel or connection dying](https://www.rabbitmq.com/docs/consumers): "any delivery... that was not acked is automatically requeued when the channel (or connection) on which the delivery happened is closed. This includes TCP connection loss, consumer application (process) failures, and channel-level protocol exceptions." That's process-lifecycle anchoring in spirit — a crashed consumer's dropped TCP connection is a strong, near-immediate signal, much closer to the Postgres `SKIP LOCKED` story than to a fixed SQS-style clock. But it's weaker than pure single-writer lifecycle anchoring in one respect: TCP connection death is not instantaneous or fully reliable as a liveness signal on its own — a half-open connection, a slow network partition, or a consumer that's alive but wedged (not crashed, just stuck in an infinite loop without disconnecting) will leave the message unacked *forever*, since nothing ever closes the channel. That's precisely why RabbitMQ layers **heartbeats** (a lightweight AMQP 0-9-1 keepalive, negotiated per-connection, commonly defaulting to 60 seconds in recent broker versions) on top of raw TCP: the heartbeat timeout is what turns a merely-unresponsive connection into a *closed* one, which is what actually triggers requeue. So RabbitMQ's real recovery signal is "connection closed," but getting to "connection closed" for a wedged (rather than crashed) consumer still depends on a timeout — making it a hybrid: lifecycle-anchored in the crash case, timeout-anchored in the hang case.

## Trade-Off Analysis

**False positives.** Family A always has a nonzero false-positive rate: any claim that's genuinely alive but slower than the timeout gets reclaimed, producing duplicate concurrent execution. Family B, done correctly (transaction-scoped locks, private per-process queues checked at boot), has zero false positives by construction — the "orphaned" determination is a proof, not an inference. The moment a Family B implementation adds a sweep-based backstop (Sidekiq's hourly `SCAN`, Oban's `Lifeline` `rescue_after`), that backstop reintroduces Family A's false-positive risk for the narrow set of cases the lifecycle signal missed.

**Recovery latency.** Family A's latency is bounded by the configured timeout — predictable, but exactly as slow as you configured it to be safe (Faktory's 30-minute default is a real production wait for a crashed job to reappear, if nobody tunes it down). Family B's primary path is near-instant (a session teardown, a process restart) but only fires when the *right event* actually happens; its backstop path inherits Family A's latency.

**Duplicate execution / semantics.** Both families are fundamentally at-least-once unless the job handler is idempotent — a reclaimed job may have partially executed before the crash. Family B does not grant exactly-once; it only reduces the *rate* of spurious reclamation caused by the detector guessing wrong, not the possibility of genuine crash-mid-execution duplication. "Effectively-once" in practice always comes from idempotent handlers plus a dedupe key, not from the detection mechanism itself.

**Threshold tuning burden.** Family A pushes an ongoing operational tax onto whoever owns the queue: visibility timeout vs. p99 processing time, TTR vs. worst-case job duration, `session.timeout.ms` vs. `max.poll.interval.ms`. Get it wrong in either direction and you get either duplicate work or slow crash detection — a dial that has to be revisited every time job characteristics change. Family B has comparatively little to tune, precisely because it doesn't need a threshold for its primary path — the tuning burden collapses to configuring the *backstop's* threshold, which is far more forgiving because it only has to catch what the lifecycle signal missed.

**Ordering on requeue.** Neither family guarantees FIFO re-sequencing for free. SQS standard queues explicitly warn that a message redelivered 3+ times gets moved toward the back of the queue rather than staying at its original position; beanstalkd and Faktory both put reclaimed jobs back at the head or tail of the ready queue depending on configuration, not at their original position in delivery order. Kafka is the exception: because ordering is a property of the partition log, not the individual message claim, a rebalance reassigns partition ownership but doesn't reorder the log itself — the new owner resumes from the last committed offset. Postgres-row-based queues can preserve original insertion order trivially (it's just a column to sort by) since the "claim" and the "queue" are the same table, but only if the application explicitly orders by an insertion timestamp or sequence rather than by claim time.

**What breaks at scale-out.** This is the sharpest boundary of Family B. The entire "restart is proof" argument depends on there being exactly one process (or exactly one connection) that could ever hold a given claim's lock — the moment you run multiple concurrent workers or multiple dispatcher replicas, "process X restarted" no longer implies "claim held under X's name is dead," because a *different* live process Y might have taken over the same logical role, or two processes could momentarily both believe they're the sole writer during a failover window. This is precisely why every real Family B implementation reintroduces a fencing mechanism once concurrency enters the picture: `SKIP LOCKED` workers rely on Postgres's own MVCC/lock manager as the fencing authority (only one backend can hold a given row lock regardless of how many workers race for it); que and good_job rely on Postgres's per-backend advisory lock table for the same reason; Sidekiq's `super_fetch` gives every process a *uniquely named* private queue precisely so N concurrent workers never collide on whose orphaned queue is whose. In other words, single-writer lifecycle anchoring doesn't disappear at scale — it gets pushed down a layer, from "the application process's identity" to "the database's own lock manager," which is a distributed-enough authority to arbitrate N concurrent claimants safely. Systems that skip this step — that try to use raw process restart as an orphan signal *and* run multiple workers — are the ones that produce real bugs (see the [Sidekiq rolling-restart issue](https://github.com/sidekiq/sidekiq/issues/4635) where overlapping deploys briefly confused which process's private queue was actually orphaned).

**Claim timestamp as observability, not action.** A pattern worth calling out explicitly: several of the systems above keep a `claimed_at` / `locked_at` timestamp column even when it plays no role in *recovery*. In a `SKIP LOCKED` or advisory-lock design, the lock's existence is the sole recovery signal — the timestamp is redundant for correctness. But it's exactly what an operator needs for alerting: "any row with `state = running` and `claimed_at` older than 10 minutes" is a legitimate, low-noise page, even though nothing in the recovery path actually acts on that timestamp. This is the healthy version of demoting a timeout from a control mechanism to a monitoring signal — it stops being the thing that *decides* an item is orphaned, and becomes the thing that tells a human an item is suspiciously old, which is a strictly safer role for a value that (as Family A shows) is inherently ambiguous between "dead" and "slow."

## When the Single-Writer Shortcut Applies — and When It Breaks

The design question to ask before choosing an orphan-recovery strategy: **is there an event, external to the claim record itself, that is logically equivalent to "the claimant is definitely dead"?**

- If the claimant is a single dedicated process (a cron-triggered batch dispatcher, a singleton coordinator, a leader-elected controller) and the claim mechanism is bound to that process's own connection or PID lifetime, then yes — anchor recovery to startup/session-teardown, and it will be both faster and strictly more precise than any timeout. Keep a coarse timeout-based sweep as an operability backstop, but don't let it be the primary path — the whole value of lifecycle anchoring is that the primary path has zero false positives.
- If there are, or will eventually be, multiple concurrent claimants — multiple worker replicas, horizontal scale-out, active-active failover — the single-writer shortcut is unsound as stated, but the underlying idea survives if you push the "identity that can be proven dead" down to something the concurrency control system itself can arbitrate: a database's row lock or advisory lock table (Postgres), a uniquely-named private per-worker structure (Sidekiq), or an explicit fencing token / generation number that invalidates stale claims even if the old claimant somehow wakes back up. This is functionally a lease again, just implemented with a much tighter, connection-bound expiry instead of an application-chosen timeout.
- If claimants and detectors run on different failure domains — different machines, different processes that can't observe each other's TCP state directly — you're back to Family A by necessity, and the design conversation shifts entirely to threshold tuning: size the timeout to worst-case processing time (not average), decide how many redeliveries constitute "poison" versus "slow" (SQS's `maxReceiveCount`, Faktory's retry ceiling), and make sure the job handler tolerates being run more than once.

## Design Checklist

- Does a claim have an unambiguous *terminal* recovery signal (connection close, process restart, transaction rollback) — or only a clock? Prefer the former when it's available.
- If using a timeout, is it sized to worst-case (not average) processing duration, with margin, and is there a heartbeat/renewal path (`ChangeMessageVisibility`, `touch`, activity heartbeats) for legitimately long jobs?
- If using lifecycle anchoring, is the claim mechanism actually bound 1:1 to the thing whose death you're inferring from — one process, one connection, one lock table entry — or could two things share an identity under scale-out?
- Is there a backstop sweep for the lifecycle-anchored path's blind spots (hard kills that skip graceful shutdown, connection poolers that mask a dead backend)? What's its own timeout, and is it generous enough to avoid becoming the primary false-positive source?
- Is the job handler idempotent, or is there a dedupe key? At-least-once is the default outcome of both families; don't design as if either one gives you exactly-once.
- Does requeue preserve, or explicitly not need to preserve, original ordering? If FIFO matters, verify the specific system's requeue placement rather than assuming it.
- Is the claim timestamp used anywhere as a *decision* input outside the primary lock/lease mechanism? If a timeout and a lifecycle signal are both wired to trigger recovery, that's usually a bug, not defense in depth — pick one as authoritative and demote the other to alerting.
