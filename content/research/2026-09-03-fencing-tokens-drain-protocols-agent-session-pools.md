## Executive Summary

Every distributed system that needs to retire a worker, a leader, or a connection eventually runs into the same problem: how do you make sure the thing you just told to stop has actually stopped, and that nothing it started keeps running unsupervised? The answer that has converged across three decades of infrastructure — ZooKeeper leader election, HDFS NameNode failover, Kafka transactional producers, Kubernetes node drain, load balancer connection draining, stream-processing watermarks — is a small set of reusable mechanisms: **monotonic fencing tokens** that let a shared resource reject stale writers, **two-phase drain sequences** that separate "stop accepting new work" from "wait for existing work to finish," and **explicit completeness markers** (watermarks, generation counts) instead of implicit assumptions about ordering.

AI agent runtimes are now hitting these same problems from a different angle. A pool of long-lived agent sessions — each holding conversation state, a prompt cache, maybe an open tool-use loop — is architecturally close to a pool of long-lived TCP connections or Temporal workflow executions. When you need to retire a session, migrate it, or cut traffic over to a new topology, you inherit every one of the classic failure modes: split-brain (two processes both think they own a channel), lost work (killing a process mid-task), and false completeness (believing a drain finished when a straggler request was still in flight). This piece surveys the prior art — fencing tokens, drain protocols, watermarks, and fail-closed handling of stale work — and distills the transferable design rules.

## Fencing Tokens: The Core Primitive

The clearest statement of the problem is Martin Kleppmann's 2016 critique of Redlock, [How to do distributed locking](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html). Kleppmann's argument isn't really about Redis — it's about what a lock *is for*. A lock is only useful if it prevents two clients from concurrently acting on a shared resource, and no lease-based lock can guarantee that on its own: a client can acquire a lock, then experience a GC pause or network delay long enough for its lease to expire, then resume and write to the resource believing it still holds the lock — after a second client has already acquired the lock and started its own work.

The fix is not a better lock, it's a fencing token: "a fencing token is simply a number that increases (e.g. incremented by the lock service) every time a client acquires the lock." The token by itself does nothing — the enforcement has to happen at the resource being protected. The storage service must "remember that it has already processed a write with a higher token number" and reject any write carrying a lower token. This is the crucial and often-missed part of the pattern: the lock service issuing tokens and the resource enforcing them are two different components, and the safety property lives entirely in the second one. Kleppmann's specific complaint about Redlock is structural: "Redlock does not have any facility for generating fencing tokens" — its lock value is a random string with no ordering guarantee, so even a theoretically perfect Redlock implementation gives you mutual exclusion under good conditions but no protection against a resumed zombie client.

This pattern — a monotonic counter checked at the point of write, not at the point of lock acquisition — recurs everywhere real systems need to fence off stale actors:

- **ZooKeeper zxid**: every ZooKeeper transaction id is a 64-bit value with the leader's epoch in the high 32 bits and a per-epoch counter in the low 32 bits. A new leader election bumps the epoch; a server only accepts a proposal if it doesn't know of a higher epoch, and ties are broken by the transaction counter. Because the epoch is embedded directly in the id space, comparing two zxids also compares "who was leader when." ([ZooKeeper Internals](https://zookeeper.apache.org/doc/current/zookeeperInternals.html); [ZooKeeper leader election and zxid overflow](https://www.alibabacloud.com/blog/zookeeper-practice-leader-election-caused-by-zxid-overflow_601677))
- **Kafka producer epochs (KIP-447 / transactions)**: transactional producers are fenced by an epoch tied to their `transactional.id`. When a producer calls `initTransactions()`, the transaction coordinator bumps the epoch for that id and completes or aborts any dangling transaction from the previous epoch. Any producer still writing under the old epoch — a "zombie" that paused or lost connectivity and is now catching up — has its writes rejected once the epoch has moved. ([KIP-447](https://cwiki.apache.org/confluence/display/KAFKA/KIP-447:+Producer+scalability+for+exactly+once+semantics); [How Kafka applies zombie fencing](https://blog.devgenius.io/how-kafka-applies-zombie-fencing-374b4e2f7a00))
- **Kafka consumer group generation / member epoch**: offset commits and `TxnOffsetCommitRequest`s carry a generation id (or, under KIP-848, a member epoch) that the group coordinator compares against its own bookkeeping. A commit from a member whose generation has been superseded — because the partition was already reassigned to someone else — is rejected with `ILLEGAL_GENERATION` or `STALE_MEMBER_EPOCH` rather than silently accepted. ([Transactions in Apache Kafka](https://www.confluent.io/blog/transactions-apache-kafka/))
- **HDFS NameNode fencing**: in HA HDFS, each NameNode that becomes active is assigned a unique, increasing epoch number, which it stamps on every write to the shared JournalNodes. JournalNodes reject writes from a NameNode whose epoch is lower than the highest epoch they've seen, which is what actually prevents a "zombie" formerly-active NameNode from corrupting the edit log after a failover — the STONITH power-off is a belt-and-suspenders backstop, not the real safety mechanism. ([HDFS High Availability](https://hadoop.apache.org/docs/stable/hadoop-project-dist/hadoop-hdfs/HDFSHighAvailabilityWithNFS.html))

The common shape across all four: a **monotonic generation/epoch number** issued by a single source of truth, carried on every subsequent request, and checked with a comparison (not just a presence check) at the point where the request would take effect. Losing the comparison — accepting any token, or accepting based on wall-clock recency instead of the token value — reopens exactly the race Kleppmann described.

## Drain and Quiesce in Production Infrastructure

Fencing answers "how do we stop a stale actor from acting." Draining answers a related but distinct question: "how do we stop routing *new* work to an actor while giving its *existing* work time to finish." Three well-documented implementations show the shape of the pattern.

**Kubernetes node drain.** `kubectl drain` is explicitly two steps performed in order: cordon, then evict. Cordoning marks the node unschedulable so the scheduler stops placing new pods there — pure intake control, no effect on what's already running. Only after that does drain begin evicting existing pods, one Eviction API request per pod, and each eviction request goes through the same admission path a normal delete would: PodDisruptionBudgets are evaluated (an eviction that would violate a PDB's `minAvailable` returns HTTP 429 and is retried, not silently dropped), then `terminationGracePeriodSeconds` is honored, and `preStop` lifecycle hooks run to completion *before* SIGTERM is even sent to the container. ([Safely Drain a Node](https://kubernetes.io/docs/tasks/administer-cluster/safely-drain-node/); [Container Lifecycle Hooks](https://kubernetes.io/docs/concepts/containers/container-lifecycle-hooks/)) The documentation is explicit that a successful `kubectl drain` return only means all pods (except excluded system pods) were evicted through this path — it is not, by itself, a guarantee that in-flight request-level work completed; that's delegated to whatever the pod does inside its own grace period.

**Load balancer connection draining.** AWS calls it "deregistration delay" on ALB/NLB target groups: when a target is deregistered or fails health checks, the load balancer immediately stops sending *new* connections to it but leaves existing connections open, moving the target into a `draining` state, configurable from 1 second up to 3,600 seconds (default 300s). If the backend itself closes a connection before the delay elapses, in-flight clients get a 500-level error — so the backend's own shutdown timeout has to be tuned to fit inside the load balancer's drain window, not the other way around. ([Target group attributes — deregistration delay](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-target-group-attributes.html)) Envoy generalizes this with an explicit admin action: POSTing to `/healthcheck/fail` forces Envoy to report unhealthy on its own health checks, which starts a graceful drain — Envoy "discourages" new requests for a configurable `--drain-time-s` window while still accepting connections, and staggers the actual connection closes (HTTP/1 `Connection: close`, HTTP/2 `GOAWAY`) across that window specifically to avoid a thundering-herd reconnect storm at the deadline. ([Envoy draining](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/operations/draining))

**Application-level graceful shutdown.** Go's `http.Server.Shutdown()` is the canonical minimal version of the same idea at the process level: it closes the listener first (stop accepting), then waits for active handlers to return before returning itself, bounded by whatever `context.Context` deadline the caller supplies — if the deadline expires first, `Shutdown` returns an error and some handlers may still be mid-flight, which is the caller's signal to escalate. nginx implements essentially the same sequence on reload: the old worker closes its listening sockets, stops accepting new connections, waits for existing connections to finish (optionally bounded by `worker_shutdown_timeout`), and only then exits — the classic failure mode being long-lived (WebSocket-style) connections that never close on their own and accumulate as "zombie workers" across repeated reloads unless the timeout is set explicitly.

The pattern across all three: **draining is stop-intake plus a bounded wait for existing work, and the two phases are never allowed to collapse into one step.** Cordon happens before evict. Health-check-fail happens before connection close. Listener close happens before handler wait. This ordering is what prevents the load balancer / scheduler from routing a fresh unit of work into a component that is simultaneously trying to empty out.

## Two-Phase Shutdown: Why "Stop Intake" Needs Its Own Acknowledged Handshake

A subtlety that's easy to underweight: in every example above, "stop accepting new work" is not a fact a shutting-down component can assert unilaterally and trust. Cordoning a Kubernetes node doesn't stop pods — it stops the *scheduler* from placing new ones, and the drain sequence only proceeds once that's true. Envoy's health-check-fail relies on whatever is doing traffic selection (a mesh, another Envoy, a client) actually honoring the 503 and stopping route. The component that *wants* to stop and the component that actually *controls the claim path* for new work are frequently different processes, and the shutdown protocol has to bridge that gap with an acknowledged signal, not a local flag.

This is the same principle formalized by the **Chandy-Lamport distributed snapshot algorithm**: to record a globally consistent cut of a distributed system without stopping it, you can't just have each process independently decide "I am now in the snapshot" — you need marker messages that propagate along every channel so that every process agrees on which messages are "before" and which are "after" the cut, producing a cut where every message received in the past of the cut was also sent in the past of it. ([A Deep Dive into the Chandy–Lamport Algorithm](https://risingwave.com/blog/a-deep-dive-into-the-chandy-lamport-algorithm/)) The general lesson transfers directly: a consistent stopping point is a property of an agreed *cut*, not a property any single node can declare into existence by itself.

**Epoch-based reclamation (EBR)** in lock-free concurrent programming is a narrower but structurally similar analogy. EBR lets threads defer freeing memory that other threads might still be reading, by tagging retired objects with the current global epoch and only reclaiming objects retired at least two epochs in the past — guaranteeing every thread has "quiesced" through the intervening epoch before reclamation happens. ([Lock-freedom without garbage collection](https://aturon.github.io/blog/2015/08/27/epoch/)) The transferable idea isn't the memory-reclamation mechanics, it's the *shape*: an epoch boundary only becomes safe to act on once every participant has provably crossed it, and that's established by an epoch counter everyone advances through together, not by a timeout.

This is also why staged fence *scope* escalation — first cut off one class of intake, confirm it, then cut off a second, broader class, then act — is a recognizable pattern rather than an ad hoc design. It mirrors the Kubernetes ordering (cordon confirmed before evict begins) and the Envoy ordering (health-check-fail propagated before connection close begins): each stage narrows what can still enter the system, and each stage is verified — not assumed — before the next, more destructive, stage proceeds.

## Watermarks: "Complete" Is a Frontier, Not a Counter

Stream processing systems solve an adjacent problem: not "has this component stopped," but "have I seen everything I'm going to see up to this point." Flink and Apache Beam both use **watermarks** — a watermark of time *T* asserts that no more events with event-time earlier than *T* are expected. Crucially, in Flink, when a stream is partitioned across multiple upstream sources, the operator's effective watermark is the *minimum* across all partition watermarks, because a single lagging partition can still deliver an "old" event at any moment — the frontier can only advance as fast as the slowest input. ([Timely Stream Processing](https://nightlies.apache.org/flink/flink-docs-master/docs/concepts/time/); [Understanding Apache Flink Event Time and Watermarks](https://www.decodable.co/blog/understanding-apache-flink-event-time-and-watermarks)) Beam frames it identically: "a watermark is a 'guessed' timestamp... [that] estimate[s] the completeness of your input," and a `PCollection`'s contents are only complete once the watermark advances to infinity. ([Basics of the Beam model](https://beam.apache.org/documentation/basics/))

The reason this matters for drain protocols specifically: **"last processed id" is not the same claim as "watermark."** A monotonically increasing sequence number tells you the highest id you've seen — it says nothing about whether every *lower* id has also been seen, and under any priority queue, retry, or out-of-order delivery scheme, it usually hasn't. A drain that waits for "no ids below N are still in flight" (a low watermark / completeness frontier) is a fundamentally stronger and different guarantee than a drain that waits for "the last id we dispatched was N" (a high-water mark on dispatch, not completion). Systems that conflate the two tend to declare drain complete while a lower-priority or delayed item is still outstanding — exactly the gap that watermark semantics exist to close. This is the formal version of "count/expire in-flight items explicitly instead of scanning for the newest one and assuming everything before it is done."

## Fail-Closed vs. Fail-Open for Orphaned In-Flight Work

Every drain protocol eventually has to answer: what happens to work that is still in flight when the drain deadline arrives, or to work the system discovers it lost track of? The fail-open/fail-closed framing — fail-open prioritizes availability by letting the system keep operating through the failure, fail-closed prioritizes control by stopping — is a general reliability-engineering choice, but it has a very specific, well-precedented answer for *drain* specifically, visible in every example above: **mature drain implementations fail closed on the ambiguous case, with an explicit, auditable expiry, rather than silently adopting or silently discarding stale work.**

- Kubernetes: an eviction blocked by a PodDisruptionBudget doesn't proceed and doesn't silently skip the pod — it returns 429 and the drain command retries until the budget allows it or the operator's timeout is hit, at which point the operator (not the cluster) has to decide to force it.
- Kafka transactions: a fenced-out zombie producer's writes aren't quietly ignored — they're actively rejected with a specific error, and the *previous* epoch's dangling transaction is explicitly aborted by the coordinator when the new epoch starts, not left ambiguous.
- ALB deregistration: a target that outlives its deregistration delay is forcibly removed and any request still in flight at that instant surfaces as a definite 500, not a silently dropped or silently retried request.

The unifying rule is: **the ambiguous window (deadline reached, work status unknown) resolves toward an explicit, recorded terminal state — expired, rejected, aborted — never toward quietly treating stale work as still valid or quietly forgetting it existed.** A system that fails open on drain (letting a straggler keep running past the fence, or silently re-adopting orphaned work without marking it) reintroduces exactly the split-brain risk fencing tokens exist to prevent.

## Mapping to AI Agent Session Pools

A pool of long-lived AI agent sessions shares the structural properties that make all of the above necessary: sessions are long-lived (not request-scoped), they hold state that's expensive to lose (conversation history, tool-call context, cached prompts), and — increasingly — they're managed by an orchestration layer distinct from the process that actually receives new messages for them, which is exactly the "who controls the claim path" problem from the two-phase section above.

Agent-orchestration frameworks are visibly re-deriving these patterns rather than inventing new ones:

- **Temporal Worker Versioning** treats a fleet of long-running workflow workers the same way Kubernetes treats nodes: new workflow executions are pinned only to the "Current" or "Ramping" deployment version, while older versions are left running only to finish workflows already pinned to them. Temporal explicitly reports a `DrainageInfo` status per version, and a version is only safe to sunset once that status confirms no workflows remain pinned to it — i.e., an explicit, queryable drain-completeness signal, not an inferred one from process uptime. Graceful worker shutdown itself follows the standard shape: stop polling for new tasks, then wait for in-progress activities to finish before exiting. ([Worker Versioning](https://docs.temporal.io/production-deployment/worker-deployments/worker-versioning); [Sunset and garbage collection](https://docs.temporal.io/production-deployment/worker-deployments/worker-versioning/sunset-and-gc))
- **LangGraph's durable execution** takes the checkpoint-and-resume path rather than the drain-and-wait path: because every superstep is checkpointed against a `thread_id`, a "graceful shutdown" can stop a running graph cooperatively after the current superstep and leave a resumable checkpoint behind, rather than needing to wait for the entire agent turn to finish. ([Durable execution](https://docs.langchain.com/oss/python/langgraph/durable-execution)) This is a different tradeoff than Temporal's drain-to-completion: it accepts mid-task interruption in exchange for not needing a bounded drain window at all, provided every side effect the agent takes is itself safely resumable or idempotent — the same idempotency question that governs whether "abort" or "let it finish" is the right choice for any in-flight LLM call.

Both are instances of the general pattern, not new mechanisms: Temporal's per-version drain status is a watermark ("no more work pinned to this generation"); its version pinning is a fencing scheme (new work is routed only to the current epoch, old-version workers are structurally prevented from receiving fresh assignments); LangGraph's checkpoint-per-superstep is the epoch-boundary idea applied at the granularity of a single agent turn rather than a whole session.

## Transferable Design Rules

1. **A token is only as good as the check on the other end.** Issuing a monotonically increasing generation/epoch number accomplishes nothing unless the component that actually performs the sensitive action — the write, the delivery, the process kill — compares the incoming token against the highest it has already accepted and rejects anything lower. The token-issuing service and the token-enforcing resource are different responsibilities; conflating them (or skipping the comparison) is exactly the gap that broke Redlock.

2. **Separate "stop intake" from "wait for existing work," and never assume the first without an acknowledgment from whoever controls the claim path.** Cordon before evict, health-check-fail before connection close, listener-close before handler-wait. If the component that receives new work is a different process from the one shutting down, the handshake needs an explicit ack (CAS'd against a known prior state), not a local flag that the intake-side process may not even be watching.

3. **Escalate fence scope in stages, verifying each stage before the next.** Stop the cheapest/most-reversible class of intake first (e.g., new conversation turns), confirm it took effect, then widen to the next, harder-to-reverse class (e.g., control messages, forced termination). Collapsing this into one step reintroduces the race the staging was meant to prevent.

4. **Completeness is a frontier, not a max-seen counter.** "Nothing below watermark W is still outstanding" is a strictly stronger and different claim than "the highest id we've dispatched is N." Any system with priority, retry, or out-of-order delivery needs the former; tracking only the latter will eventually declare a drain complete while a straggler is still running.

5. **Resolve ambiguous in-flight work toward an explicit, audited terminal state — never toward silent adoption or silent loss.** When a drain deadline is reached and an item's status is unknown, mark it expired/aborted/rejected with a record, the way Kafka aborts a dangling transaction on epoch bump or ALB returns a definite 500 past the deregistration delay. Fail-closed-with-audit beats both fail-open (risking split-brain) and silent fail-closed (losing the ability to reconcile afterward).

6. **Use narrow, purpose-built primitives for counting and expiring in-flight work, not table scans.** Every mature implementation above exposes a specific query for drain state — Kubernetes' eviction status, Temporal's `DrainageInfo`, watermark values — rather than requiring the operator to infer completeness by scanning all records for a pattern. A drain protocol that can only answer "is it done?" by re-deriving the answer from a full scan under load is a drain protocol that will eventually declare victory on stale data.

These rules are old — most of them predate Kubernetes, several predate ZooKeeper — but agent-session pools are hitting them for the first time because agent sessions are the first widely-deployed workload where "long-lived process holding expensive, hard-to-reconstruct state" meets "orchestration layer that wants to reshape the topology underneath it while it's running." That combination is precisely what fencing tokens and drain protocols were built for.
