## Executive Summary

Every conversational AI system that serves more than one user (or more than one conversation) eventually has to answer the same question: how much do concurrent conversations share, and how much must be kept apart? The answer sits on a spectrum. At one end, a single agent instance holds one context window and relies on prompt text (routing tags, channel metadata) to keep conversations straight — cheap, but fragile, because the model itself is the only thing enforcing the boundary. At the other end, every conversation gets its own process or microVM — airtight, but expensive and hard to share state across.

The industry has converged on a middle layer that most production systems now treat as the default: **thread- or session-level isolation with a shared backend**. LangGraph namespaces state by `thread_id` and offers a separate `Store` for cross-thread memory; OpenAI's Assistants API modeled the same split as "threads" backed by a persistent, per-thread message store; LangChain's Managed Deep Agents (MDA) go further and bind thread scope to a verified user identity rather than to anything present in the prompt text, explicitly to defeat prompt spoofing; AWS Bedrock AgentCore isolates at the microVM level for code-execution tools while keeping orchestration logic outside the sandbox. Underneath nearly all of these designs is the decades-old actor/mailbox pattern: one queue (or "session") per conversation, FIFO-processed by a single owner, so ordering and isolation are guaranteed without locks.

The harder, less-solved half of the problem is what to do with *memory*. Every serious framework distinguishes short-term, thread-scoped state (conversation history, scratch files) from long-term, cross-thread memory (user facts, preferences, shared knowledge) — and treats the boundary between them as a deliberate architectural seam, not an afterthought. LangGraph's `Store` is explicit and requires manual reads/writes, unlike the automatic checkpointer, "since conversation history is structural while long-term memory is a product decision full of complexity." Letta (formerly MemGPT) makes this most concrete with core memory blocks that can be explicitly shared across multiple agents/sessions, with a documented anti-pattern (concurrent full-block rewrites) and a working pattern (a single memory-owning "sleep-time" agent, others append-only). And LangChain's own production documentation states the security implication plainly: shared memory across users or sessions "is a vector for prompt injection... if one user can write to memory that another user's conversation reads, a malicious user could inject instructions into that shared state."

This note surveys the isolation spectrum, the concurrency mechanics that make session isolation cheap, the shared-memory design patterns that let isolated sessions still feel like "the same agent," the documented security failure modes, and what the strongest published designs converge on as good practice.

## 1. The Isolation Spectrum

Isolation for a conversational agent can be placed at roughly three altitudes, and almost every real system is a mix of these, applied to different subsystems.

### Prompt-level (tagged context in one window)

The weakest form: all conversations flow through a single context window, distinguished only by inline metadata ("[Channel: #general] [User: Alice]") that the model is expected to respect. This is common in early or simple bot integrations, where a single agent process holds one growing transcript and routing labels are the only separation mechanism. It costs nothing architecturally, but the isolation lives entirely in the model's ability to keep threads straight — which is also where it fails.

Documented failure modes of prompt-level separation map directly onto the "context failure modes" taxonomy popularized by David Breunig (June 2025) and echoed across subsequent agent-engineering literature:

- **Context poisoning** — a hallucination or error from one thread gets treated as ground truth and referenced in later turns, sometimes for a different conversation entirely. Breunig's canonical example is a Gemini agent playing Pokémon, where "misinformation about the game state... can often take a very long time to undo." ([dbreunig.com](https://www.dbreunig.com/2025/06/22/how-contexts-fail-and-how-to-fix-them.html))
- **Context distraction** — beyond roughly 100k tokens of shared history, models increasingly favor "repeating actions from its vast history rather than synthesizing novel plans," i.e., patterns from one conversation bleed into how the model handles another. ([dbreunig.com](https://www.dbreunig.com/2025/06/22/how-contexts-fail-and-how-to-fix-them.html))
- **Context confusion / clash** — irrelevant or contradictory material from a co-mingled context degrades tool selection and reasoning; sharded-prompt experiments referenced in the same piece showed a 39% average performance drop when related-but-distinct information arrived across turns instead of up front.
- **Cross-app / cross-conversation context poisoning** — a more adversarial variant, where injected instructions persist in a shared session-scoped store and surface later through a different, co-resident consumer of that context. Academic work frames this explicitly as a confused-deputy attack pattern with "cross-principal reach." ([arxiv.org/html/2606.00485](https://arxiv.org/html/2606.00485))

The common thread: prompt-level separation is a *convention*, not a *boundary*. It degrades gracefully at first (occasional confusion) and catastrophically under adversarial input (instruction or data leakage across conversations that were never meant to interact).

### Session/thread-level (separate contexts, shared backend)

This is the dominant pattern in production frameworks today: each conversation gets its own addressable context — a distinct history, distinct scratch state, sometimes a distinct system prompt — while the underlying compute, model weights, tool registry, and (critically) long-term memory store are shared across all sessions.

- **LangGraph** keys every checkpoint row on `(thread_id, checkpoint_id)`. Two conversations with different `thread_id`s are "completely isolated even if they run on the same graph instance or the same database," making `thread_id` the primary namespace for multi-tenant chat applications. ([abstractalgorithms.dev](https://www.abstractalgorithms.dev/langgraph-memory-and-state-persistence), [reference.langchain.com](https://reference.langchain.com/python/langgraph.checkpoint))
- **OpenAI's Assistants API** modeled conversations as "Threads" — persistent, automatically managed containers of messages, with the platform explicitly recommending one thread per user and advising isolation at the Project level for separate applications. (Note: this API is deprecated, shutting down August 26, 2026, but the thread abstraction it popularized persists across the industry.) ([developers.openai.com](https://developers.openai.com/api/docs/assistants/deep-dive), [community.openai.com](https://community.openai.com/t/using-openai-threads-for-session-history-with-external-models/1369613))
- **LangChain's Managed Deep Agents (MDA)** scope threads "per end-user id from your OIDC provider," and explicitly frame this as a security decision, not just an organizational one: identity "gives your agent a trusted way to know who triggered the run without relying on prompt text or spoofable request fields." Message history and scratch files are scoped to the thread by default and don't carry over between threads. ([docs.langchain.com](https://docs.langchain.com/langsmith/managed-deep-agents-quickstart), [docs.langchain.com](https://docs.langchain.com/oss/python/deepagents/going-to-production))
- **Google's Agent Development Kit (ADK)** uses an event-driven Runner: every user message, tool call, and model reply is logged as a permanent Event, and Session Services commit `state_delta`s only through `append_event()`, which the docs describe as necessary for changes to be "tracked, persistence works correctly, and updates are thread-safe." ([google.github.io/adk-docs](https://google.github.io/adk-docs/events/), [adk.dev](https://adk.dev/sessions/state/))
- **Slack/Discord/Telegram bot frameworks** (e.g., Chat SDK, Mastra) map each platform thread 1:1 onto an internal conversation/session object, each with its own memory scope and message history, typically backed by shared Redis or database state across workers. ([mastra.ai](https://mastra.ai/blog/building-multi-user-multi-channel-agents))
- **Claude Code** treats sessions as fully isolated by design — "no ability to share context, findings, or coordinate work" between sessions unless the user explicitly bridges them (e.g., via worktrees or purpose-built coordination tools). This is a deliberate simplicity trade-off: isolation is the safe default, and cross-session coordination is opt-in tooling layered on top. ([github.com/anthropics/claude-code #21277](https://github.com/anthropics/claude-code/issues/21277), [dev.to](https://dev.to/sahil_kat/coordinate-multiple-claude-code-sessions-on-a-shared-repo-1dh4))
- **Companion/character apps** (Character.AI-style) historically leaned on short, per-session context windows (often 4–8K tokens) with session-level memory buffers that reset between interactions; persistent cross-session memory has been added as an explicit, separately-engineered feature precisely because it isn't free — "the architecture for persistent memory costs meaningfully more per session than a sliding window... at scale, even modest per-session overhead multiplies into a very large bill." ([blog.kinthai.ai](https://blog.kinthai.ai/why-character-ai-forgets-you-persistent-memory-architecture))

At this layer, isolation is enforced by *addressing* (distinct keys/namespaces) rather than by *hardware*. It's cheap and horizontally scalable, but its security depends entirely on the authorization layer around it — nothing stops a bug in routing logic from handing thread A's context to thread B.

### Instance-level (separate processes/containers/microVMs)

The strongest isolation: each conversation, or each tenant, gets a dedicated execution environment with its own kernel, filesystem, and network namespace.

- **AWS Bedrock AgentCore** implements "a strict one-session-one-microVM isolation model" using Firecracker: each session gets a dedicated microVM with isolated compute, memory, and filesystem; on completion "the entire microVM is terminated and memory is sanitized... eliminating cross-session contamination risks." ([docs.aws.amazon.com](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-sessions.html), [docs.aws.amazon.com](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/built-in-tools-how-it-works.html))
- A general multi-tenant-isolation write-up frames this as a tiered spectrum: containers give process-level separation but share a host kernel (vulnerable to kernel-exploit escapes); microVMs give each tenant a dedicated guest kernel via hardware virtualization (Firecracker: "less than five MiB of memory overhead per VM"); some products hybridize — trusted platform code runs in containers, untrusted AI-generated code runs in microVMs, classified by provenance at enqueue time. ([blaxel.ai](https://blaxel.ai/blog/multi-tenant-isolation-ai-agents))
- Isolation at this tier is also described as extending past compute — per-tenant network egress allowlists, per-tenant storage volumes with "no shared mounts," and proxy-based credential injection rather than shared environment variables, since the goal is to make cross-tenant access "physically impossible" rather than merely disallowed. ([blaxel.ai](https://blaxel.ai/blog/multi-tenant-isolation-ai-agents))
- Even at this tier, real deployments show the boundary isn't unconditionally solid: published exploits have bypassed AgentCore's network-isolation mode and sandboxed code interpreters via DNS-based side channels, a reminder that "instance-level" isolation is a strong default, not a mathematical guarantee. ([unit42.paloaltonetworks.com](https://unit42.paloaltonetworks.com/bypass-of-aws-sandbox-network-isolation-mode/), [beyondtrust.com](https://www.beyondtrust.com/blog/entry/pwning-aws-agentcore-code-interpreter))

Instance-level isolation is typically reserved for the highest-risk surface — arbitrary code execution, browser automation, untrusted tool calls — rather than applied uniformly to every conversation, because the cost (dedicated compute per session, no easy state sharing) is prohibitive for ordinary chat turns.

## 2. Concurrency Architectures for One Logical Agent, Many Conversations

Once conversations are split into addressable sessions, the question becomes how to process many of them concurrently without one session's processing corrupting another's, or without conversations racing on shared resources.

**The actor/mailbox pattern is the dominant mental model**, inherited from Erlang/OTP and generalized across modern frameworks:

- A mailbox is "a single-reader-many-writer queue... only the owning actor is allowed to dequeue a message," processed strictly FIFO, one message at a time. This is what removes the need for locks: "state can only be accessed or modified in a single thread of execution." ([petabridge.com](https://petabridge.com/blog/how-akkadotnet-actors-process-messages/))
- Erlang's own design goal was exactly this: lightweight processes (up to ~10⁶ concurrent on a single 8GB host) that communicate only by message passing, "eschewing shared memory as a method of coordination," so that applications are "naturally built in a style fostering fault isolation, scalability, and modularity." ([youngju.dev](https://www.youngju.dev/blog/culture/2026-04-15-actor-model-erlang-akka-orleans-elixir-deep-dive-guide-2025.en), [berb.github.io](https://berb.github.io/diploma-thesis/original/054_actors.html))
- The same idea appears productized as **message-broker sessions**: Azure Service Bus sessions "guarantee that messages within the same session are processed in FIFO order by a single consumer at a time," while allowing full parallelism *across* sessions. The underlying principle is generic: "guaranteeing order requires serialization — if message B must wait for message A, the system processes one message at a time," and the session/mailbox boundary is exactly where that serialization is scoped. ([oneuptime.com](https://oneuptime.com/blog/post/2026-02-16-how-to-use-azure-service-bus-sessions-for-ordered-message-processing/view))
- **Google ADK's Runner** operationalizes this for agents specifically: it "drives the loop, processing events yielded by your agents and coordinating state commits," appending every event to session history and committing state deltas through a single serialized path — explicitly to make updates thread-safe. ([google.github.io/adk-docs](https://google.github.io/adk-docs/events/))

**What breaks without this discipline**, per practitioner write-ups on production LLM-agent race conditions: calling synchronous/blocking LLM calls inside an async endpoint blocks the entire event loop for every other session; any shared mutable state (a shared cache, a shared agent instance) not protected by session-level serialization produces "structural race conditions" where two flows read the same state at the same version, generate independent deltas, and both commit without an intervening re-read — silently dropping one side's update. The consistent architectural fixes cited are: (a) push work into per-session queues so the queue itself is the serialization point, and (b) move from direct shared-state mutation to event-driven state changes, where a runner/coordinator is the sole writer. ([machinelearningmastery.com](https://machinelearningmastery.com/handling-race-conditions-in-multi-agent-orchestration/), [medium.com/@aktooall](https://medium.com/@aktooall/building-an-agent-architecture-how-sessions-state-events-context-and-runner-work-together-d8dbdb64d52b))

In short: **concurrency across sessions is "embarrassingly parallel" by design (no ordering constraint between unrelated conversations), while within a session it is strictly serialized (one active turn at a time, FIFO).** Nearly every framework surveyed — LangGraph, ADK, Service Bus–based bot backends, Erlang-style actor systems — reduces to this same shape.

## 3. The Shared-Memory Problem

Isolating conversation *state* is the easy half. The harder design problem is: how does a session-isolated agent still feel like a single, coherent agent with a unified memory and shared knowledge — without that shared substrate becoming the leak vector that defeats the isolation just built?

### Two explicit tiers, not one blended one

Every mature framework surveyed splits memory into (at least) two tiers with different lifecycles, and treats moving data between them as a deliberate operation rather than automatic propagation:

- **LangGraph**: a *checkpointer* persists thread-scoped state automatically at every step (conversation continuity, human-in-the-loop, time travel). A separate *Store* persists "application-defined data outside the graph state for long-term, cross-thread memory... namespaced by user identity, not by thread," and unlike the checkpointer, requires **explicit** read/write calls in node code. The docs frame this asymmetry as deliberate: "conversation history is structural while long-term memory is a product decision full of complexity." ([focused.io](https://focused.io/lab/persistent-agent-memory-in-langgraph), medium.com/@anil.jain.baba)
- **MemGPT/Letta**: models memory as an OS-style hierarchy. *Core memory* is always in-context (persona, key user facts, size-limited); *archival memory* is a vector-backed long-term store (Postgres + pgvector) the agent searches only when it decides it needs older information — "the agent decides what to move between them," analogous to a page fault pulling data from disk into RAM. ([medium.com/@piyush.jhamb4u](https://medium.com/@piyush.jhamb4u/stateful-ai-agents-a-deep-dive-into-letta-memgpt-memory-models-a2ffc01a7ea1), original MemGPT paper: [arxiv.org/abs/2310.08560](https://arxiv.org/abs/2310.08560))
- **ChatGPT** (as a widely-used reference point, reverse-engineered by third parties since OpenAI hasn't published full internals): session context holds the raw current transcript; a separate "Saved Memories" store holds stable, explicitly-saved facts; a third layer, "chat history reference," lets the model draw inferences from *other* past conversations. Notably, OpenAI added a **Project-level isolation boundary** on top of this: "with project-only memory enabled, ChatGPT can use other conversations inside that Project for context but will not use saved memories from outside the Project" — i.e., unified memory is itself made *scopeable*, not all-or-nothing. ([openai.com](https://openai.com/index/memory-and-new-controls-for-chatgpt/), [embracethered.com](https://embracethered.com/blog/posts/2025/chatgpt-how-does-chat-history-memory-preferences-work/))

### When do session learnings sync back to shared memory?

Two patterns recur, and they trade latency for consistency in opposite directions:

- **Write-through (synchronous)**: the agent writes to long-term memory inline, during the turn. Consistency is immediate but adds latency and computational overhead to every turn where a write occurs.
- **Batch/async consolidation**: writes are deferred — after a session ends, or on a schedule — and involve heavier processing (entity extraction, embedding, dedup/conflict resolution, knowledge-graph updates) run in a background worker so user-facing latency stays low. The trade-off is a **staleness window**: information from one session is not yet visible to a concurrently running session referencing the same memory. Consolidation triggers commonly cited: end of session, context-window pressure, or nightly batch jobs for high-volume systems. ([redis.io](https://redis.io/blog/long-term-memory-architectures-ai-agents/), general pattern discussion across agent-memory literature)

**Letta's "sleep-time agents"** are a concrete, published instance of the async-consolidation pattern applied specifically to *shared* memory across concurrent sessions: sleep-time agents run in the background and share memory blocks with the primary conversational agent(s), modifying them asynchronously. Documentation is explicit about the concurrency hazard this introduces and its mitigation: "multiple agents doing memory_rethink on the same block simultaneously leads to lost updates," so the recommended pattern designates **one owner** for heavy rewrites of a shared block while other agents/sessions only append (`memory_insert`) rather than overwrite. With `enable_sleeptime=True`, all agents in a managed group get a "real-time, consistent view of shared blocks" — i.e., consistency is achieved by restricting concurrent writers, not by general-purpose locking. ([docs.letta.com](https://docs.letta.com/guides/agents/multi-agent-shared-memory), [docs.letta.com](https://docs.letta.com/guides/agents/architectures/sleeptime/))

This "single owner, append-only elsewhere" pattern is worth calling out because it's the same solution the actor/mailbox model uses for conversation state, just applied one layer up, to the memory store itself.

## 4. Security and Privacy: Cross-Conversation and Cross-Tenant Leakage

Session isolation and shared memory create two structurally different attack surfaces, and the literature treats them somewhat separately.

**Cross-session/cross-tenant leakage** (isolation failing at the infrastructure layer): a documented taxonomy names three root causes — (1) *misconfigured caching*, where systems key cached outputs globally rather than per-tenant, letting one user's cached response surface for another; (2) *shared memory states*, where multiple users read/write overlapping context without enforced boundaries; (3) *improperly scoped context*, where the architecture never segregated user-specific context in the first place, so the model can reference material from a different session. A specific, technically distinct variant is **KV-cache sharing leakage** in multi-tenant LLM serving: because requests with identical prompt prefixes can share key-value caches for efficiency, this shared cache can itself become a side channel that lets one tenant's prompt influence or be inferred from another's. ([giskard.ai](https://www.giskard.ai/knowledge/cross-session-leak-when-your-ai-assistant-becomes-a-data-breach), KV-cache leakage: researchgate.net/publication/390110581)

Recommended mitigations converge on: complete session/context/cache isolation at both infrastructure and application layers; per-tenant cache keys (never global caching of generative output); output redaction for sensitive patterns before returning a response; strict authorization checks before any stored-session data is retrieved; anomaly detection for query patterns that resemble exfiltration attempts. A published academic proposal (Secure Multi-Tenant Architecture, "Burn-After-Use") takes this to its logical extreme: enforce fully ephemeral conversational contexts that are destroyed immediately after use, specifically to prevent cross-session or cross-user inference. ([arxiv.org/abs/2601.06627](https://arxiv.org/abs/2601.06627))

**Context/prompt poisoning across conversations** (isolation failing at the reasoning layer, even when infrastructure boundaries hold): the clearest published framing is "cross-app context poisoning," a confused-deputy attack where an injection persists in a session-scoped shared data store, is "consulted on every subsequent turn," and has "cross-principal reach" because a different, co-resident consumer of that shared context later acts on the poisoned material via documented first-party APIs. Distinct from classic prompt injection, this class specifically depends on shared, persistent context — which is exactly the surface a unified-memory design introduces. ([arxiv.org/html/2606.00485](https://arxiv.org/html/2606.00485))

**"Identity → per-user thread isolation, defeating prompt spoofing"** — the concept as concretely implemented by LangChain's Managed Deep Agents — means: identity used for scoping threads and memory comes from an authenticated source (an OIDC provider, resolved server-side) rather than from anything present in the prompt text or request body that a user could forge. The documentation is unusually direct that this specifically closes an injection vector: **shared memory scopes (assistant-, user-, or organization-level) are called out as "a vector for prompt injection" precisely because "if one user can write to memory that another user's conversation reads, a malicious user could inject instructions into that shared state."** The recommended default is therefore to namespace memory by verified `user_id` (private per-user memory) rather than by a broader shared scope, and where shared scopes are unavoidable, to enforce declarative write-deny policies or custom backend validation hooks on those paths. ([docs.langchain.com](https://docs.langchain.com/oss/python/deepagents/going-to-production))

This maps cleanly onto the **OWASP Agentic Security Initiative's Top 10 (2026)** categories of *Identity & Privilege Abuse* (ASI03) and identity spoofing more broadly: agents inheriting or reusing credentials/session tokens across contexts without re-verification, mitigated by short-lived credentials, task-scoped permissions, policy enforcement on every action, isolated per-agent identities, and — notably — "session isolation with strict memory wiping" as an explicit recommended control. ([nhimg.org](https://nhimg.org/complete-guide-to-the-2026-owasp-top-10-risks-for-agentic-applications), [descope.com](https://www.descope.com/blog/post/owasp-agentic-top-10-identity))

A related but architecturally distinct mitigation pattern is **context quarantine via subagents**: rather than trusting the primary conversational context to hold multiple concerns safely, a task is delegated to a subagent with its own fresh context, own tool set, and own (narrower) system prompt; only a final summary is returned to the parent. This reduces the blast radius of any poisoned or injected content picked up mid-task, and is now a common pattern in coding-agent harnesses specifically for this reason. ([arize.com](https://arize.com/blog/context-management-in-agent-harnesses/), Claude Code subagent docs)

## 5. Trade-offs and Design Recommendations

Synthesizing across the frameworks surveyed, a few patterns show up consistently enough to treat as converging best practice for a hybrid "session-isolated, memory-unified" design:

**1. Isolate conversation state by default; make memory sharing opt-in and explicit, never implicit.** Every framework that got this right (LangGraph, MDA, Letta) treats the checkpoint/thread layer as automatic and the cross-session memory layer as something code has to deliberately read from and write to. Implicit sharing (e.g., one growing context window, or memory keyed only by prompt-supplied identifiers) is exactly what produces the poisoning and leakage failure modes documented above.

**2. Derive identity from an authenticated layer, never from prompt text.** MDA's core insight — identity must come from something a user cannot forge (an OIDC-resolved user ID, a signed session token) rather than anything in the message body — is the single highest-leverage fix for both cross-conversation cross-talk and deliberate prompt spoofing. This is a precondition for safe memory namespacing, not an optional hardening step.

**3. Namespace shared memory narrowly, and treat any broader-than-per-user scope as a reviewed security decision.** Default to per-user (or per-tenant) private memory. Shared/organization-wide memory scopes should require an explicit design review, because they are the documented injection vector: one conversation's write becomes another conversation's trusted context.

**4. Use single-writer discipline for anything actually shared.** Whether it's a conversation's own state (mailbox/actor pattern: one consumer, FIFO) or a genuinely shared memory block (Letta's "one owner rewrites, others append"), the recurring solution to write contention is not fine-grained locking — it's restricting who is allowed to perform destructive writes, and pushing everyone else to additive, order-independent operations.

**5. Separate the latency-sensitive path from the consistency-sensitive path.** Conversation turns should never block on heavy memory consolidation (extraction, embedding, dedup, conflict resolution) — that work belongs in an async/background pass (Letta's sleep-time agents; generic "batch consolidation" patterns). Accept a bounded staleness window for cross-session memory visibility in exchange for turn latency; make the window small enough that it doesn't produce visibly stale or contradictory behavior, but don't chase synchronous consistency at the cost of blocking every session on every write.

**6. Match isolation strength to risk, not uniformly to the whole system.** Thread/session-level isolation is the right default for ordinary conversational state — cheap, horizontally scalable, sufficient when combined with strong identity. Reserve instance-level isolation (microVMs, dedicated containers) for genuinely high-risk surfaces: arbitrary code execution, browser automation, or any tool call operating on untrusted external content. Applying microVM-grade isolation to every chat turn is not what current production systems do, because the cost is prohibitive relative to the risk for that specific surface.

**7. Assume the isolation boundary will be tested, and design detectability in.** Even the strongest published isolation (Firecracker microVMs at AWS scale) has had documented bypasses via side channels like DNS. Treat "isolation" as risk reduction with monitoring, not a guarantee — anomaly detection on cross-session query patterns and output redaction as a last-line defense are recommended even in architectures with strong structural isolation.

**8. Let the memory boundary itself be user-scopeable, not just system-scoped.** ChatGPT's Project-level memory boundary — where memory sharing is opt-in per grouping of conversations rather than global by default — is a useful pattern for any system where "unified memory" doesn't mean "one global pool visible everywhere," but rather "memory scoped to whatever grouping the user or operator considers one coherent context."

Taken together, these patterns describe a specific shape: **conversations are isolated by default (thread/session-level, actor-style serialized processing, identity resolved outside the prompt), and the parts of the system that are genuinely meant to be unified — long-term memory, shared knowledge — are exposed through a narrow, explicit, single-writer-disciplined interface rather than by simply widening the isolation boundary.** That combination is what lets a single logical agent serve many concurrent conversations safely while still behaving, from the memory's point of view, like one continuous entity.
