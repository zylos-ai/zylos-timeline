## Executive Summary

Since Ubuntu 23.10, and by default in Ubuntu 24.04 LTS, an AppArmor-mediated kernel restriction called `kernel.apparmor_restrict_unprivileged_userns` has quietly broken a wide swath of Linux sandboxing tooling: bubblewrap (`bwrap`), Chrome/Chromium's `--sandbox`, Electron apps, Flatpak, Steam, and anything built on raw `unshare(CLONE_NEWUSER)`. The restriction is a genuinely good idea — unprivileged user namespaces have been a reliable ingredient in local kernel privilege-escalation chains — but its opt-in-by-profile design means any unconfined process that tries to create a user namespace now gets `EPERM` unless an AppArmor profile explicitly grants it the `userns` permission.

This collision has become newly urgent in 2026 because of a second, orthogonal trend: AI coding-agent CLIs — OpenAI's Codex CLI, Anthropic's Claude Code sandboxed Bash tool, and a growing list of copycats — increasingly sandbox their own model-issued shell commands using exactly the same primitive, bubblewrap, run unprivileged, inside a user namespace. When these agents run on a bare Ubuntu 24.04 desktop the fix is a one-line sysctl or a distro-shipped AppArmor profile. When they run *inside* a Docker container or a Kubernetes pod — increasingly the default deployment shape for hosted or CI-driven agent workloads — the host-level fix doesn't reach the container at all, and the "just add CAP_SYS_ADMIN" instinct trades a narrow, well-understood hole for a much larger one on precisely the workload (an LLM's own generated shell commands) you least want unconstrained. This article maps the mechanism, catalogs real breakage, and lays out a decision matrix for operators who now have to make this call deliberately.

## The Mechanism: What `apparmor_restrict_unprivileged_userns` Actually Restricts

Unprivileged user namespaces (`unshare(CLONE_NEWUSER)` without root) let a normal process mint a namespace in which it appears to be `root`, gaining an in-namespace set of capabilities it can use for tasks like building a `chroot`-style mount tree, remounting `/proc`, or setting up further nested namespaces — all without a setuid helper. It's the mechanism that lets Chrome sandbox its renderer processes and lets bubblewrap build Flatpak's confinement without root, and it's been in mainline Linux since kernel 3.8. It has also been, per Ubuntu's own tally cited in their announcement, an ingredient in roughly 44% of the Linux kernel privilege-escalation exploits Google's security team surveyed, because the namespace machinery exposes a large amount of rarely-exercised kernel code (netfilter, filesystem mount parsing, etc.) to unprivileged callers ([Ubuntu blog: Restricted unprivileged user namespaces are coming to Ubuntu 23.10](https://ubuntu.com/blog/ubuntu-23-10-restricted-unprivileged-user-namespaces)).

Rather than the blunt on/off sysctl that Debian (`kernel.unprivileged_userns_clone`) and some hardened kernels have long carried, Canonical implemented a finer-grained gate through AppArmor. With `kernel.apparmor_restrict_unprivileged_userns=1` (the Ubuntu 24.04 default), an unprivileged, AppArmor-*confined* process may only call `unshare(CLONE_NEWUSER)`/`clone(CLONE_NEWUSER)` if its active AppArmor profile contains the `userns,` rule — a new mediation class added specifically for this feature. A process that is AppArmor-*unconfined* (no profile attached at all) is, perhaps counterintuitively, still permitted to create user namespaces under the default policy, unless the companion sysctl `kernel.apparmor_restrict_unprivileged_unconfined=1` is also set, which closes that gap by preventing unconfined processes from using tools like `aa-exec` to transition into a permissive profile in the first place. A process with `CAP_SYS_ADMIN` (in its own or an ancestor's user namespace) always bypasses the restriction, since that capability already implies far broader kernel access ([Ubuntu Discourse spec thread](https://discourse.ubuntu.com/t/spec-unprivileged-user-namespace-restrictions-via-apparmor-in-ubuntu-23-10/37626); [Understanding AppArmor User Namespace Restriction](https://discourse.ubuntu.com/t/understanding-apparmor-user-namespace-restriction/58007)).

Concretely, an AppArmor profile that wants to opt an application back in looks like Ubuntu's shipped Chrome profile:

```
/opt/google/chrome/chrome flags=(default_allow) {
  userns,
  # site-specific additions and overrides
}
```

or, for a purely compatibility-oriented (non-confining) grant — the pattern most operators actually reach for — an `unconfined`-flagged profile that does nothing but flip the one bit on:

```
abi <abi/4.0>,
include <tunables/global>

profile bwrap /usr/bin/bwrap flags=(unconfined) {
  userns,
  include if exists <local/bwrap>
}
```

This is functionally a compatibility shim, not a confinement policy: `flags=(unconfined)` means AppArmor otherwise imposes no restrictions on the binary, it just satisfies the one new mediation check. Ubuntu ships this exact shape for `/etc/apparmor.d/bwrap-userns-restrict` (scoped to `/usr/bin/bwrap`), and equivalent per-path profiles for Chrome, Firefox, Flatpak's `bwrap` invocation, LXC, and a handful of others it surveyed as "impacted" before the rollout ([Launchpad bug #2046477](https://bugs.launchpad.net/ubuntu/+source/apparmor/+bug/2046477); [Launchpad FFe #2036128](https://bugs.launchpad.net/ubuntu/+source/apparmor/+bug/2036128)). AppArmor's path-based attachment is the crux of what breaks later in containers: the kernel decides which profile (if any) applies by matching the *executable's path on disk* against the loaded profile set, at exec time, mediated by the AppArmor LSM.

It's also worth noting the restriction is not airtight. Qualys's Threat Research Unit disclosed three practical bypasses in March 2025 — using `aa-exec` to relaunch under an already-permissive profile like `chrome` or `flatpak`, spawning the default-installed `busybox` (whose profile grants `userns`), and `LD_PRELOAD`-injecting a shell into a permissive-profiled binary such as Nautilus — each letting a local unprivileged user obtain a full-capability user namespace anyway ([Qualys: Three bypasses of Ubuntu's unprivileged user namespace restrictions](https://blog.qualys.com/vulnerabilities-threat-research/2025/03/27/qualys-tru-discovers-three-bypasses-of-ubuntu-unprivileged-user-namespace-restrictions); [LWN: Bypassing Ubuntu's user-namespace restrictions](https://lwn.net/Articles/1015649/); follow-up bypass work at [afflicted.sh](https://afflicted.sh/blog/posts/bypass-pwn.html)). Ubuntu's response was that these don't constitute a security *vulnerability* per se — the feature was never meant to be a hard boundary against a determined local attacker, only to raise the bar against remote/opportunistic exploit chains — but it underlines that this is defense-in-depth, not a capability model, and shouldn't be treated as a substitute for real isolation when agent-generated code is involved.

## Real-World Breakage Catalog

The rollout produced a long tail of "why did this suddenly stop working" reports across the desktop and developer-tooling ecosystem:

- **Chromium/Electron.** Chromium's own security documentation states plainly: "Our primary sandbox no longer works on developer builds on some Linux distributions, namely Ubuntu, due to a security feature that restricts access to a powerful kernel feature, user namespaces" ([Chromium docs: AppArmor User Namespace Restrictions vs. Chromium Developer Builds](https://chromium.googlesource.com/chromium/src/+/main/docs/security/apparmor-userns-restrictions.md)). Ubuntu's AppArmor policy only allowlists the stable, distro-packaged Chrome/Chromium binary path — a locally built Chromium, or any Electron app bundled as an AppImage/tarball at an arbitrary path, isn't covered, and crashes on launch or silently falls back to `--no-sandbox`. Chromium's public bug tracker has the canonical report at [issues.chromium.org/issues/333313925](https://issues.chromium.org/issues/333313925), and Electron tracked it as affecting *every* Electron app on Ubuntu 24.04+ in [electron/electron#41066](https://github.com/electron/electron/issues/41066) ("All versions of Electron fail to open on Ubuntu 24.04+ due to `kernel.apparmor_restrict_unprivileged_userns=1` by default"). Downstream, apps like Joplin ([laurent22/joplin#9137](https://github.com/laurent22/joplin/issues/9137)) and various AppImage-packaged tools hit the identical SIGTRAP/crash signature.
- **Bubblewrap directly.** The generic bwrap failure mode is `bwrap: setting up uid map: Permission denied` or, when only network namespace creation is blocked, `bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted`. Russell Coker documented the break in detail for Ubuntu 24.04 ([etbe.coker.com.au](https://etbe.coker.com.au/2024/04/24/ubuntu-24-04-bubblewrap/)), and it recurs across unrelated projects that vendor bwrap for build isolation, e.g. Chainguard's `melange` build tool ([chainguard-dev/melange#1508](https://github.com/chainguard-dev/melange/issues/1508)) and VS Code's own sandboxing work ([microsoft/vscode#316046](https://github.com/microsoft/vscode/issues/316046): "bwrap fails to create user namespace if apparmor profile is not loaded").
- **Flatpak and Steam.** Flatpak's runtime `bwrap` invocation is covered by Ubuntu's own shipped profile, but downstream packaging can drift: Valve's Ubuntu 24.04 Steam AppArmor profile shipped with `flags=(complain)` instead of `flags=(unconfined)`, which meant it still blocked userns creation despite intent, producing "Steam now requires user namespaces to be enabled" for users who had done nothing wrong ([ValveSoftware/steam-for-linux#12620](https://github.com/ValveSoftware/steam-for-linux/issues/12620)).
- **AI coding-agent CLIs, directly.** OpenAI's Codex CLI vendors its own copy of bubblewrap for its Linux filesystem sandbox; once Codex switched to invoking a vendored/internal `bwrap` binary rather than the system one at `/usr/bin/bwrap`, it fell outside the scope of Ubuntu's `bwrap-userns-restrict` profile (which is path-scoped to `/usr/bin/bwrap` specifically), reproducing the exact same `uid map: Permission denied` failure on hosts that were otherwise correctly configured. The fix landed as [openai/codex#14963](https://github.com/openai/codex/pull/14963), "prefer system `/usr/bin/bwrap` when available," with a follow-up specifically for containerized use in [openai/codex#17547](https://github.com/openai/codex/pull/17547), "Support bubblewrap in secure Docker devcontainer." Independent write-ups of the same failure and fix appeared at [jdhodges.com](https://www.jdhodges.com/blog/codex-sandbox-ubuntu-24-04-fix/) and [asepalazhari.com](https://asepalazhari.com/blog/fix-bwrap-ubuntu-24-docker-codex-cli/). Anthropic's own sandboxing project hit the identical class of bug: [anthropic-experimental/sandbox-runtime#74](https://github.com/anthropic-experimental/sandbox-runtime/issues/74) reports `bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted` on Ubuntu 24.04+, traced to the sandbox's `--unshare-net` flag trying to create a network namespace that AppArmor now gates identically to the user-namespace case; the discussion weighed a distro-shipped AppArmor profile grant against simply switching to `--share-net` on the theory that network isolation adds little when the host or container already firewalls the process. Claude Code's own sandboxed Bash tool documentation likewise flags Ubuntu 24.04+'s AppArmor default as a known prerequisite issue to resolve before its bubblewrap-based sandbox will initialize ([Claude Code docs: Configure the sandboxed Bash tool](https://code.claude.com/docs/en/sandboxing)), and community write-ups such as [claude-desktop-debian#542](https://github.com/aaddrick/claude-desktop-debian/issues/542) and [labs.esokia.com](https://labs.esokia.com/post/sandboxing-claude-code-cli-linux-bubblewrap/) document the same fix pattern independently converged on across the ecosystem.

The pattern across all of these: the *symptom* is generic (`Permission denied`, `Operation not permitted`, a silent crash, or a fallback to no sandboxing at all), the *cause* is always the same one sysctl, and the *fix* people converge on independently, over and over, is a hand-written AppArmor profile granting `userns,` to a specific binary path.

## The Container Twist: Why Host Policy Doesn't Reach Containerized Agents

The fixes above all assume you control the host's `/etc/apparmor.d/` and can `apparmor_parser -r` a new profile. That assumption collapses the moment the agent runtime runs inside a Docker container or Kubernetes pod, which is now the default shape for hosted coding-agent products, CI-triggered agent jobs, and multi-tenant "agent sandbox" platforms. Three things change at once:

**AppArmor profile attachment is path- and host-scoped.** The kernel LSM decides confinement by matching the executable's path against profiles loaded into the *host's* AppArmor policy cache when a process execs. A container's root filesystem is a private mount namespace layered from an image — `/usr/bin/bwrap` inside the container is a different inode, on a different filesystem, than any host path a distro-shipped profile like `bwrap-userns-restrict` was written to match, even though the string looks identical. In practice the profile that actually governs a containerized process is whichever one the container *runtime* attached at container-start time — normally Docker's or containerd's own generated `docker-default` profile — not any host per-application profile at all. `docker-default` does not grant `userns,` to arbitrary contained binaries, so an unprivileged `bwrap` inside a stock Docker container fails identically to (or worse than) the bare-metal case, and no host-side fix ("just load the Ubuntu chrome/bwrap profile on the host") reaches it.

**Docker's own defaults add a second, independent gate.** Even setting AppArmor aside, Docker's default seccomp profile blocks the `unshare`/`pivot_root`/mount syscalls bwrap needs unless the container is granted `CAP_SYS_ADMIN` *and* Docker's default AppArmor profile is loosened; teams building containerized Codex/agent images report needing `--security-opt seccomp=unconfined` (or a custom seccomp profile allowlisting the specific namespace syscalls) stacked on top of the AppArmor fix before an inner bubblewrap sandbox will build at all — full detail in the same Codex Docker devcontainer work ([openai/codex#17547](https://github.com/openai/codex/pull/17547); [Fix bwrap Error on Ubuntu 24.04 in Docker for Codex CLI](https://asepalazhari.com/blog/fix-bwrap-ubuntu-24-docker-codex-cli/)). This is two independent LSM/syscall-filter layers that both have to agree to let the *inner* sandbox construct itself, on top of whatever the host kernel's `apparmor_restrict_unprivileged_userns` sysctl already requires.

**Kubernetes' AppArmor API changed shape, and doesn't remove the underlying host requirement.** Before Kubernetes 1.30, AppArmor was configured via the beta `container.apparmor.security.beta.kubernetes.io/<container-name>` pod annotation; from 1.30 onward it's a first-class, GA field: `securityContext.appArmorProfile`, settable at pod or container level, with `type: RuntimeDefault`, `type: Unconfined`, or `type: Localhost` plus `localhostProfile: <name>` for a custom profile that must already be loaded on the node ([Kubernetes docs: AppArmor tutorial](https://kubernetes.io/docs/tutorials/security/apparmor/); [Configure a Security Context for a Pod or Container](https://kubernetes.io/docs/tasks/configure-pod-container/security-context/)). The `Localhost` mode is exactly the mechanism that lets a cluster operator ship the same minimal `profile bwrap … flags=(unconfined) { userns, }` shape described above as a node-level AppArmor profile (via a DaemonSet, node image bake, or `NodeInitContainer`) and reference it by name from the pod spec — but it still has to be pre-loaded onto every node, it's node-OS-dependent (only meaningful on AppArmor-enabled kernels like Ubuntu's, a no-op on SELinux-based nodes), and Kubernetes' own separate `securityContext.userns` / user-namespace-for-pods feature (stable-track since 1.30 for isolating the *pod's own* container root from host root) is an orthogonal concept — it namespaces the container's UID range, it doesn't grant that container's *processes* the right to create further nested user namespaces for their own sandboxing.

Given all that, why is granting `CAP_SYS_ADMIN` (or running `--privileged`) worse than shipping the narrow AppArmor grant? Because `CAP_SYS_ADMIN` isn't scoped to "may create a user namespace" — it's the kernel's historical catch-all bucket, covering mount/umount, quota control, `ioctl` privileges, BPF operations, and dozens of unrelated operations that were never given their own capability bit. Handing it to a container running an LLM-driven shell means that if the agent runtime's *own* inner sandbox has a bug, is bypassed by a crafted command, or the model is prompt-injected into emitting an unexpected command, the blast radius is "can do almost anything a namespace-scoped root can do" rather than "can call `unshare(CLONE_NEWUSER)` and nothing else." A scoped AppArmor `userns,` grant, by contrast, adds back exactly the one syscall class the sandbox tool needs and nothing else — the process is still fully mediated by the outer container's seccomp filter and (optionally) its own separate AppArmor profile for everything else. This is the textbook least-privilege trade Ubuntu's own design intended, and it's the pattern worth deliberately re-creating for agent container images rather than reaching for `--privileged` as the path of least resistance.

## Why This Matters Specifically for AI Coding Agents

Coding-agent CLIs are a qualitatively different consumer of `userns` than Chrome or Flatpak. A browser sandboxes a small number of well-known, developer-authored renderer/GPU processes. A coding agent sandboxes an open-ended stream of *model-generated* shell commands — `rm`, `curl`, `git`, arbitrary interpreters — where the entire safety argument rests on the sandbox boundary actually holding. Both OpenAI's Codex CLI and Anthropic's Claude Code have converged on the same architecture: use bubblewrap to build an unprivileged, per-command mount/network namespace around what the model wants to execute, so a single wayward or adversarial command can't touch files or network endpoints outside an explicit allowlist ([Claude Code docs: sandboxing](https://code.claude.com/docs/en/sandboxing)).

That design choice means these tools inherit bwrap's entire dependency on unprivileged user namespaces working — and unlike a desktop user clicking "run Chrome," an agent runtime is now routinely deployed inside a container by design: hosted agent products isolate each user's session in its own container, CI pipelines spin up an agent in a fresh container per job, and "agent sandbox" platforms exist specifically to give a coding agent a disposable, container-scoped Linux box to work in. Every one of those deployment shapes now needs someone to have made a deliberate userns policy decision at image-build or node-provisioning time — not discovered it as a runtime crash in production. The Codex and Claude Code sandbox-runtime issues cited above are effectively bug reports about exactly this gap being unaddressed by default.

The emerging convention, visible in how both vendors' own fixes and community write-ups converged, is: (1) prefer the system-installed `bwrap` binary over a vendored copy, so it stays covered by whatever host/node AppArmor profile already exists; (2) ship or document a minimal profile of the shape below for environments (containers, minimal server images) where no such profile exists; (3) detect the failure at startup and degrade — either falling back to a documented lower-isolation mode with a loud warning, or failing closed with an actionable error — rather than silently disabling the sandbox.

```
# /etc/apparmor.d/bwrap  (or a Kubernetes Localhost node profile of the same shape)
abi <abi/4.0>,
include <tunables/global>

profile bwrap /usr/bin/bwrap flags=(unconfined) {
  userns,
  include if exists <local/bwrap>
}
```

paired, in Kubernetes, with:

```yaml
securityContext:
  appArmorProfile:
    type: Localhost
    localhostProfile: bwrap   # pre-loaded on the node via DaemonSet/node image
```

## Mitigation Decision Matrix

| Approach | What it does | Blast radius if agent sandbox is compromised | Operational cost | When it's appropriate |
|---|---|---|---|---|
| **Sysctl off** (`kernel.apparmor_restrict_unprivileged_userns=0`) | Disables the restriction host- or node-wide for *every* process | High — re-opens userns to all local unprivileged processes, not just the agent; restores the pre-2023.10 kernel attack surface Ubuntu shipped this to close | Lowest (one sysctl, or a `sysctl.d` drop-in) | Single-tenant dev VM/sandboxed cloud instance you already trust broadly; never on a shared or multi-tenant host |
| **Privileged / `--cap-add=SYS_ADMIN`** | Grants the container (or `--privileged`, all capabilities) enough power to bypass the restriction entirely | Very high — `CAP_SYS_ADMIN` is a broad catch-all (mount, BPF, quota, more), effectively container-escape-adjacent for untrusted workloads | Low to set up, high hidden risk | Rarely justified for agent workloads; acceptable only for fully trusted, non-agent build infrastructure |
| **Scoped AppArmor `userns,` profile** (host `/etc/apparmor.d/` entry or k8s `Localhost` node profile) | Grants exactly the one permission bwrap needs, to exactly the binary path that needs it | Low — sandbox syscalls it needed anyway; everything else stays mediated by seccomp/AppArmor as normal | Medium — profile authoring, node provisioning/DaemonSet for k8s, path must match the actual binary in use | Recommended default for agent runtimes in containers/Kubernetes; matches Ubuntu's own least-privilege intent |
| **Sandboxless / engine opt-out** (`--no-sandbox`, `--share-net` instead of `--unshare-net`, disable the inner bwrap layer) | Removes the agent's *own* inner sandbox, relying entirely on the outer container/VM boundary | Depends entirely on outer isolation quality; for a shared multi-tenant container this is a real regression | Lowest engineering cost, but shifts all isolation responsibility outward | Acceptable only when the outer container/VM is already the real trust boundary (e.g., one container per user session, ephemeral, no cross-tenant secrets) |
| **Setuid bwrap fallback** | Reverts to bwrap's older setuid-root helper binary path, which doesn't need unprivileged userns at all | Medium — trades kernel-userns attack surface for classic setuid-binary attack surface; still needs careful mount/no-new-privs configuration | Medium — requires installing/enabling the setuid variant, which many distros now ship disabled by default | Legacy or locked-down hosts where AppArmor profile changes aren't permitted but a setuid binary is acceptable |

## Forward Outlook

Ubuntu's design is very likely a preview, not an outlier. Kernel discussion around unprivileged user namespaces as a durable exploit vector predates this feature by years (see the original 2016 LWN piece on [controlling access to user namespaces](https://lwn.net/Articles/673597/)), and Debian already carries its own coarser `unprivileged_userns_clone` sysctl; the direction of travel across distributions is toward *some* form of default restriction, with AppArmor-mediated per-application opt-in being the more usable of the models on the table precisely because it avoids Debian's all-or-nothing knob. Expect other AppArmor-using distributions and derivatives to pick up Ubuntu's same sysctl and profile set over time, and expect SELinux-based distributions (Fedora, RHEL) to eventually need an equivalent policy construct even though their enforcement mechanism differs entirely — meaning any fix an agent vendor ships today should be described in terms of the *capability being granted* ("this process needs to create unprivileged user namespaces"), not hard-coded to AppArmor syntax.

Qualys's 2025 bypass disclosures are also a signal worth taking seriously for anyone tempted to treat the sysctl as a strong isolation boundary rather than defense-in-depth: `aa-exec`, `busybox`, and `LD_PRELOAD` bypasses all still work against the unmodified default policy as of this writing, so the restriction narrows the field for opportunistic/remote exploitation without stopping a determined local attacker who already has code execution — which is exactly the threat model an under-sandboxed AI agent's shell tool represents.

For agent-runtime vendors, the practical shopping list is short: detect the failure mode explicitly at sandbox startup rather than surfacing a raw `bwrap` error string; document the minimal AppArmor profile and Kubernetes `Localhost` pattern as first-class deployment guidance, the way Codex's and Claude Code's own issue trackers are converging on; prefer the system `bwrap` binary so it stays covered by distro-shipped profiles; and treat "runs inside a container" as a deployment mode that needs its own tested, documented policy — not an edge case discovered by a confused user's bug report. The alternative — quietly falling back to `--no-sandbox` or nudging operators toward `--privileged` — trades a well-understood, narrow kernel hardening feature for exactly the kind of broad, silent privilege escalation surface it was built to close.
