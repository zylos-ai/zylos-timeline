## Executive Summary

AI agents don't run `--help` and read source to discover what a tool can do. They read whatever documentation was handed to them — a `SKILL.md` file, a CLI reference page, an MCP tool manifest — and treat it as ground truth. If a capability exists in the code but not in that document, the agent doesn't "not know about it" in some soft, correctable sense. It concludes the capability doesn't exist, and it builds a workaround. Undocumented features are, for an agent consumer, indistinguishable from missing features.

This is the opposite of how documentation drift has traditionally been treated — as a hygiene issue, a stale-docs complaint, something a reviewer should have caught. For agent-facing docs, drift is a capability outage, and outages get monitored, not hoped away. The fix looks like a coverage test, not a style guide: enumerate the tool's actual capabilities from its source of truth (a command registry, a route table, an MCP tool list) and assert, in CI, that every one of them appears in the docs the agent actually reads. This article walks through a real incident that forced this realization, surveys the prior art in docs-as-code and documentation testing that doc-coverage tests build on, examines what's specific to the agent-consumption case, and lays out a concrete, minimal pattern any team building agent-facing tools can adopt.

## The Incident: An Invisible Feature, Twice

The grounding case is unremarkable in the way that matters most — it's the kind of gap that happens constantly and rarely gets caught. A component that renders documents as web pages had a share-link feature in its web UI: publish a page, optionally protect it with a password, rotate that password later, remove it. The web UI supported all four operations. The CLI — the interface an agent actually drives when asked to publish or manage pages — did not. There was no `enable-password`, `rotate-password`, or `disable-password` subcommand.

An agent asked to password-protect a shared link did what any reasonable agent does when a CLI doesn't expose something: it looked for another way in. It found the component's internal modules, imported them directly, and wrote a one-off script that called internals never meant to be a stable interface. It worked, technically. It also meant the agent was now coupled to implementation details that could change on any refactor, bypassing whatever validation or side effects the CLI layer was supposed to provide.

The natural fix was to add the missing subcommands to the CLI — which happened. Then something more interesting happened in review: the first round of review caught that the CLI got its new subcommands, but the agent-facing docs — the `SKILL.md` describing the component's capabilities and the CLI reference doc — were not updated to mention them. The subcommands existed. The tests passed. And the feature was, for every agent that would ever read those docs to decide what the CLI could do, still invisible. The exact failure mode that motivated writing the feature in the first place would have quietly recurred, just one layer up: the CLI now had the capability, but the discovery surface agents actually use still said it didn't.

The fix that came out of that review round wasn't "remember to update the docs next time." It was a script: enumerate every subcommand the CLI actually registers, and assert that each one has a corresponding mention in the `SKILL.md` and CLI reference doc. Wire that into CI so a PR that adds a subcommand without touching the docs fails, not merges.

That test, run for the first time against the *existing* codebase, immediately found a second, unrelated gap: a keyring-related command that had been in the CLI for a while and had never been documented anywhere an agent would see it. Nobody had shipped that gap in the PR under review — it had been sitting there, silently making a real command invisible to every agent that used the tool, for as long as the command existed. That's the strongest evidence for treating this as a systemic problem rather than a one-off review miss: a small, mechanical coverage test found two independent instances of the same failure mode on its first run, one of which predated the incident that motivated writing the test.

The lesson generalizes cleanly: **"docs were updated" needs to be a property CI can check, not a property a reviewer needs to remember to check.** And for tools consumed primarily by agents, the cost of getting this wrong isn't a slightly-stale README — it's a capability that silently doesn't exist from the consumer's point of view, no matter how real it is in the source code.

## Prior Art: Documentation Has Been Tested Before

None of this is conceptually new — the software industry has been fighting doc-code drift for decades. What's new is *who reads the docs* and how unforgiving that reader is about gaps. It's worth surveying the existing toolbox, because doc-coverage tests for agents are best understood as one more point on a spectrum that already has well-understood instruments.

### Doctests: examples that must keep working

The oldest and most direct answer to "how do I know my docs are still true" is to make the examples in the docs executable. Python's [`doctest`](https://en.wikipedia.org/wiki/Doctest) module scans docstrings for interactive-shell-style examples and re-runs them, failing if the output no longer matches. Rust does the same thing at the language level: code fences in `///` doc comments are compiled and run as part of `cargo test`, specifically [to help keep documentation up to date with code](https://doc.rust-lang.org/rustdoc/lints.html). Elixir's [`ExUnit.DocTest`](https://hexdocs.pm/ex_unit/ExUnit.DocTest.html) extracts `iex>` examples from `@doc` attributes and runs them as real tests. The shared insight: an example that isn't executed isn't verified, and unverified examples rot at the same rate as any other unmaintained code — quietly and without an error message, until someone tries to actually run one.

Doctests are precise but narrow: they verify that a *specific worked example* still behaves as claimed. They say nothing about whether the docs are *complete* — whether every public function has an example at all. That completeness question is what coverage-style tools try to answer instead.

### CLI snapshot and command-tree testing

For command-line tools specifically, a cluster of tools test the *shape* of CLI output rather than executing narrative examples. [`cram`](https://bitheap.org/cram/) is a language-agnostic end-to-end tool that runs shell commands embedded in a test file and diffs actual output against expected output. Rust's [`trycmd`](https://github.com/assert-rs/snapbox) (and its sibling `snapbox`) does the same for CLI binaries and is explicitly designed to enumerate large batches of test cases rather than hand-write assertions one at a time — real crates like `clap` itself, `typos`, and `cargo-edit` use it to verify that the examples in their own README stay runnable, [as documented in the clap project's own discussion of the pattern](https://github.com/clap-rs/clap/discussions/4500). Simon Willison's [`cog`](https://til.simonwillison.net/python/cog-to-update-help-in-readme)-based workflow for Datasette and `sqlite-utils` takes a related but distinct approach: rather than snapshot-testing help output, it regenerates the `--help` block inside the README from the live CLI and fails CI (`cog --check`) if the committed README doesn't match what regeneration would produce. [`mdsh`](https://github.com/zimbatm/mdsh) generalizes this to arbitrary shell output embedded anywhere in a markdown file.

These tools solve a real problem — they'd have caught the *rotate-password* subcommand's help text drifting from its README example — but they still only check what's *already referenced* in the docs. If nobody ever wrote a doc block mentioning `rotate-password` in the first place, there's nothing for cog or trycmd to check against. This is the exact gap doc-coverage testing is built to close: it doesn't verify that documented things behave as documented, it verifies that *undocumented things don't exist*.

### Generate-from-source: eliminating drift by construction

A different strategy sidesteps the sync problem entirely: don't hand-write the doc, generate it from the same source of truth as the tool itself. Go's [Cobra](https://cobra.dev/) framework ships a `doc` package that walks the live command tree and emits Markdown, man pages, or ReST directly from each command's `Use`, `Short`, `Long`, and flag definitions — Cobra's own guidance on [writing LLM-ready CLI docs](https://cobra.dev/docs/how-to-guides/clis-for-llms/) frames this explicitly as a drift-prevention measure: "programmatic generation from command definitions ... inherently prevents drift between your CLI's actual behavior and its documentation." [`terraform-docs`](https://terraform-docs.io/) does the equivalent for Terraform modules, reading `.tf` files and injecting variable/output tables into READMEs; teams wire it into CI to fail the build if the generated block doesn't match what's committed, [as described in Terraform's own automation guides](https://github.com/terraform-docs/terraform-docs).

Generation-from-source is the strongest guarantee available — a generated doc *cannot* drift from its source, because it *is* its source, reformatted. Its weakness is narrative quality: generated reference docs tell you the shape of a command (flags, types, defaults) but not the judgment a human or agent needs — when to use it, what it's for, what the common footgun is. `SKILL.md` files in particular are meant to carry exactly that judgment; a fully generated version would just be a flag list.

### API-contract drift detection

At the API layer, a parallel discipline exists around OpenAPI specs. [`oasdiff`](https://github.com/oasdiff/oasdiff) diffs two versions of an OpenAPI spec and classifies each change as breaking or non-breaking against [a documented rule set of over 500 distinct change types](https://www.oasdiff.com/docs/breaking-changes), and teams run it as a GitHub Action that posts a commit status on every PR. (Optic, a longtime competitor in this space, was archived in January 2026 — [its GitHub repo shut down](https://specshield.io/blog/optic-is-dead-migration-guide) — leaving oasdiff as the dominant open-source option, a reminder that even the tooling for *fighting* drift needs maintenance or it drifts out of existence itself.) These tools check spec-to-spec drift, not spec-to-implementation drift, but the CI pattern — diff against a source of truth, fail the build on unreviewed change — is identical to what a doc-coverage test needs to do against a command registry.

### Coverage-as-a-lint: the closest existing analogue

The closest existing pattern to "fail CI if a public capability lacks documentation" is language-level missing-docs linting. Rust's `missing_docs` lint flags any public item without a doc comment; it ships **allow-by-default** but [the Rustdoc book documents it as intended for library authors to deny explicitly](https://doc.rust-lang.org/rustdoc/lints.html) via `#![deny(missing_docs)]` — a policy several practitioners describe adopting specifically because, past a certain project size, "it is much easier to maintain documentation coverage than to backfill it later." Kubernetes takes a related but more structured approach at the API level: its [API conventions](https://github.com/kubernetes/community/blob/main/contributors/devel/sig-architecture/api-conventions.md) require every field to carry an explicit `+optional` or `+required` godoc tag, and that godoc text is mechanically compiled into the OpenAPI schema surfaced by `kubectl explain` — so the human-facing comment and the machine-facing schema are, by construction, the same string.

This is the direct ancestor of doc-coverage testing for CLIs: not "generate the doc" and not "test the example," but "enumerate every public surface and assert a doc obligation was met." Doc-coverage tests for agent-facing docs are this pattern, ported from language-level public items to CLI-level subcommands (and, as the next section covers, to MCP tool manifests).

### Review-time enforcement: Danger and its limits

One more layer worth naming because it's the *default* most teams reach for first: PR-time checklist bots. [Danger](https://danger.systems/js/) runs arbitrary review rules during CI — flag a PR if the description is too short, if it touches a sensitive path without a specific reviewer, and so on — and teams commonly configure a rule like "if `cli/commands/` changed, warn unless `docs/` also changed." This catches the *should-touch-docs* case cheaply, but it's necessarily a blunt proxy: it can tell that *some* file in `docs/` changed, not that the *specific new subcommand* is mentioned anywhere in it. A PR that edits an unrelated typo in the docs directory satisfies a Danger rule like this while shipping the exact silent gap from the incident above. Danger-style rules are a reasonable first line of defense and a poor substitute for an actual coverage assertion.

## The Agent-Specific Angle: Docs Are Now the API

Everything above predates the current wave of LLM agents, and all of it still applies. What's changed is the *reader*. Historically, a human hitting a doc gap had recourse: skim the source, run `--help`, ask a colleague, infer from adjacent examples. Agents increasingly don't do any of that by default — not because they're incapable of it, but because the entire design point of structured agent-facing docs (MCP tool descriptions, `SKILL.md` files, `llms.txt`) is to give the agent a complete, bounded, cheap-to-load description of capabilities *so that it doesn't have to* go exploring. That's a feature when the description is accurate and a trap when it isn't.

**MCP tool descriptions are the sharpest version of this.** In the Model Context Protocol, a tool's description field isn't documentation *about* the API — it functionally *is* the API, in the sense that it's the only signal the model uses to decide whether and how to call the tool. Frameworks lean into this directly: [FastMCP auto-generates a tool's description straight from its Python docstring](https://gofastmcp.com/servers/tools), which is generation-from-source in its purest form and eliminates an entire class of drift by construction — but only for the specific server implementations that adopt that pattern, and only for the description text itself, not for whether every registered tool got a docstring in the first place.

Where MCP tool docs drift anyway, the consequences are qualitatively different from a stale README. A widely-cited account describes an MCP search tool whose parameter was renamed from `query` to `search_query`; the server kept silently accepting the old field name, defaulting to an empty string instead of erroring, and [the agent "confidently explained why the search found nothing" rather than surfacing a broken contract](https://dev.to/nesquikm/my-mcp-tools-broke-silently-schema-drift-is-the-new-dependency-hell-5c49) — a failure mode the author frames as worse than REST versioning precisely because an LLM rationalizes a bad response instead of raising an exception. Tooling has started to appear specifically for this: [Specmatic's MCP Auto-Test generates test calls directly from a server's declared tool schema and runs them in CI](https://specmatic.io/updates/testing-mcp-servers-how-specmatic-mcp-auto-test-catches-schema-drift-and-automates-regression/), and its own writeup cites a real case — Postman's MCP server's `update_mock` tool didn't declare a `collection` parameter as required in its schema, but the implementation demanded it anyway, a mismatch automated schema testing caught that manual testing had missed.

There's a security dimension layered on top of the pure-drift problem, worth naming because it inverts the incentive: [the original tool-poisoning-attack research from Invariant Labs](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks) showed that MCP's trust model assumes tool descriptions are benign, and demonstrated hidden instructions embedded in a description field that are invisible in the UI a human reviews but fully visible — and actionable — to the model consuming them. [OWASP catalogs this as its own attack class](https://owasp.org/www-community/attacks/MCP_Tool_Poisoning), including a "rug pull" variant where a server changes an already-approved tool's description after the fact. A doc-coverage test guards against *incompleteness* — capabilities that exist but aren't described. Tool-poisoning defenses guard against the opposite failure mode — descriptions that exist but lie, or change underneath an agent that already trusted them, defended by pinning tool definitions and hashing them for integrity checks rather than by coverage enumeration. Both problems live at the same interface — the text an agent trusts as its map of what a tool can do — and a mature agent platform needs answers to both, but they're not the same test.

Standards for making documentation itself agent-legible have also emerged fast. [`llms.txt`, proposed by Jeremy Howard in September 2024](https://llmstxt.org/), gives a site a root-level markdown index specifically scoped for LLM context windows, distinct from `robots.txt`'s crawler-permission scope. Anthropic's own [Agent Skills specification](https://agentskills.io/specification) formalizes `SKILL.md` as YAML frontmatter (`name`, `description`) plus a markdown body, explicitly loaded *progressively* — the `description` alone is loaded at session start for every skill, and the full body only once a skill is activated. That progressive-disclosure design is efficient, but it raises the stakes on the `description` field specifically: if a capability isn't reachable through that first ~100-token summary, the agent may never load the body that would have described it correctly, no matter how good that body is. None of these specs, as written, mandate a coverage check against the underlying tool's actual command or route list — that enforcement is left entirely to the implementer, which is exactly the gap doc-coverage tests are meant to fill.

## Patterns and Trade-offs

Laid side by side, the available strategies form a spectrum from "cheapest, weakest" to "strongest, most narrative-destroying":

- **Review checklists / Danger rules** ("did you touch `docs/`?") are cheap to add and catch nothing that a determined or distracted author can't route around. They rely on vigilance — the exact thing the incident showed doesn't scale, since the *first* review round on the password-CLI PR missed the gap despite an engaged reviewer looking right at the diff.
- **Snapshot/doctest-style testing** (trycmd, cog, doctest, ExUnit.DocTest) verifies that *what's written* stays true, cheaply and mechanically. Its blind spot is exactly the incident's failure mode: it has nothing to say about a capability that was never written about at all.
- **Generate-from-source** (Cobra's doc package, terraform-docs, FastMCP docstrings) eliminates drift by construction for the fields it covers, at the cost of the generated text having no room for the narrative judgment — "use this when," "the common mistake here is" — that agent-facing docs like `SKILL.md` are specifically designed to carry. A fully generated `SKILL.md` degrades into a flag list an agent still has to guess how to use.
- **Coverage assertion** (the pattern this incident converged on, plus its ancestors in `missing_docs` and Kubernetes' `+optional`/`+required` tags) is the narrowest fix for the narrowest failure: it doesn't check that descriptions are *accurate*, only that every registered capability has *some* corresponding entry. It's cheap to write, cheap to run, and — as the second, pre-existing gap it caught on first run demonstrates — effective specifically at the class of bug that checklists and snapshot tests both miss.
- **Runtime/behavioral testing** (Specmatic's MCP schema fuzzing, oasdiff's breaking-change classification) catches the deepest and hardest class of drift — where the doc's *claim* about behavior no longer matches actual behavior, not just where a doc entry is missing. It's also the most expensive to build and maintain, and it's the layer that catches things coverage tests structurally cannot: the `update_mock` parameter that was declared optional but was actually required was never a documentation-*presence* problem, so no coverage test would ever have flagged it.

No single layer subsumes the others. A coverage test would not have caught Postman's `update_mock` schema lie, and Specmatic-style behavioral testing would not by itself have caught the missing keyring command, because there was no schema mismatch to fuzz — there was no schema at all in the doc, just silence. They defend different failure modes at the same interface and are cheap enough, individually, that skipping one in favor of another isn't a real cost saving.

## Concrete Recommendations for Agent Platform Builders

A minimal, high-leverage doc-coverage test looks like this, and is worth building before reaching for anything heavier:

1. **Identify one source of truth per surface.** For a CLI, that's the command-registration code itself (`cobra.Command` tree, `argparse` subparsers, `click` group) — not a hand-maintained list. For an MCP server, it's the live `tools/list` response or the decorator-registered tool set. If the source of truth requires a second hand-maintained list to describe it, the drift problem has just moved one level, not disappeared.
2. **Enumerate mechanically.** Walk the registry in-process (Cobra and Cobra-alikes make this trivial via `Commands()`/`Walk`) rather than parsing `--help` text, which is itself a rendering of the same registry and adds a layer of string-parsing fragility for no benefit.
3. **Assert presence, not prose.** Check that each command/tool name (and, ideally, each of its subcommands and required flags) appears *somewhere* in the agent-facing doc set — `SKILL.md`, CLI reference, `llms.txt` entry, whatever the agent actually loads. Don't try to assert the prose is *good* in this pass; that's a different, harder, more subjective problem, and conflating the two is how these tests stop getting written.
4. **Run it in CI on every PR that touches the registry**, not as a periodic audit. The incident's second finding — a keyring command undocumented since it was added — is exactly what a periodic audit would eventually catch, at unknown cost in the meantime; a per-PR gate catches it at the moment of introduction instead.
5. **Layer, don't choose.** Pair the coverage test with a cheap generate-or-check step (cog-style `--check`, or Cobra's doc generator run in CI-diff mode) for the mechanical parts of reference docs, and treat behavioral/schema testing (Specmatic-style, or a hand-rolled smoke test per tool) as a separate, heavier investment reserved for tools where a silent behavioral mismatch is expensive — payment flows, credential rotation, destructive operations.
6. **Know what this doesn't catch, and say so out loud.** A coverage test proves a name exists in the docs; it says nothing about whether the description is *correct*, whether an example still runs, or whether the tool's actual behavior matches what's claimed. Treat a green coverage test as "no capability is invisible," not as "the docs are good." The former is the specific, narrow, cheap guarantee that stops agents from silently losing access to real functionality; the latter still needs a human editorial pass.

## Conclusion

The instinct to treat documentation as secondary — something reviewers keep an eye on, something that gets a pass in a slower sprint — was always a little optimistic. For agent-facing docs specifically, it's the wrong model entirely. An agent doesn't experience a documentation gap as friction to push through; it experiences a documented absence as fact, and acts accordingly — writing around internals, giving up, or telling a user a feature doesn't exist when it does. The incident here didn't need anything exotic to fix: a script that walks a command registry and greps for each name in a docs folder, wired into CI. It caught the gap under review immediately, and a gap nobody was even looking for on the very first run. That ratio — trivial to build, immediately productive against a bug class checklists structurally can't catch — is the strongest argument for building this before the next feature ships, not after the next agent quietly scripts around the one that already did.
