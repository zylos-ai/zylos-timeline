## Executive Summary

Every agent platform that lets an autonomous agent write to external systems eventually hits the same problem: a credential handed to an agent process is, by default, too broad and too durable for the work it authorizes. The fix converging across the industry — CI/CD, cloud IAM, service meshes, and now AI agent orchestration — is the same shape: mint a credential at the moment work is claimed, bind it cryptographically to *who* is acting and *what task* they are acting on, inject it only into that unit of work, derive identity server-side from the token rather than from client-asserted headers, and revoke or let it expire the instant the task reaches a terminal state.

This is not a new idea. OAuth Token Exchange (RFC 8693), SPIFFE/SPIRE workload identity, GitHub Actions' `GITHUB_TOKEN`, GitHub-to-AWS OIDC federation, and Kubernetes bound service account tokens all implement variants of it for machine-to-machine and CI workloads. What changed in 2025–2026 is that agent platforms started applying it to *agents*, where the unit of work is a "task" claimed by an LLM-driven process rather than a CI job, and where the attribution question — did the *agent*, the *task*, or the *human who dispatched it* do this? — has real consequences for confused-deputy attacks and self-trigger loops.

The Multica platform's `mat_` task-scoped tokens are a concrete, recent instance of this pattern: minted at task claim, injected as `MULTICA_TOKEN` into the spawned agent run, used by server middleware to derive actor + task binding while stripping client-forged headers, with certain endpoints (chat history) restricted to task-token actors specifically. Its rough edge — writes made with a long-lived member PAT land as the member actor and can re-trigger the same agent — is the same self-trigger-loop failure mode GitHub Actions solved years ago for `GITHUB_TOKEN`-authored commits, and it is why an integrating bridge had to hand-roll a per-task token store (0600 files, cleanup at terminal state) rather than relying on a single long-lived credential.

## The Pattern

The pattern has five components that recur across every implementation surveyed:

1. **Mint at claim, not at login.** A credential is issued when a discrete unit of work (job, task, request) begins, not once per session or per user login.
2. **Bind to (actor, unit-of-work).** The token encodes both *who* is acting (a service, an agent, an app installation) and *which* unit of work it is scoped to — not just a role or scope list.
3. **Inject narrowly.** The credential reaches only the process executing that unit of work (an environment variable in a spawned job, a projected volume in a pod, a header the CI runner sets), never a shared config file used across many jobs.
4. **Derive identity server-side from the token.** The relying party trusts the token's claims, not anything the client asserts out-of-band (headers, form fields). This is the load-bearing defense against confused-deputy and spoofing attacks.
5. **Expire or revoke at terminal state.** The credential dies with the unit of work — by short TTL, by explicit revocation when the task completes/fails/cancels, or both.

## Prior Art Across the Industry

**OAuth 2.0 Token Exchange (RFC 8693).** Defines a Security Token Service pattern where a client exchanges one token for another scoped to a specific downstream action. Its `act` claim expresses "this principal is acting on behalf of that principal," and `act` claims nest to represent delegation chains; a `may_act` claim in the subject token authorizes who is eligible to act for that subject. Critically, RFC 8693 distinguishes **delegation** (both `sub` and `act` are present, preserving an audit trail of who's really behind the action) from **impersonation** (the actor claim is omitted, so the exchanged token looks exactly as if the original principal issued it). The security baseline is that an exchanged token should never carry broader privilege than the token it was exchanged from. This vocabulary — delegation vs. impersonation, actor chains, downscoping — is the closest formal analogue to "task actor vs. member actor" in agent platforms. ([RFC 8693](https://www.rfc-editor.org/info/rfc8693/), [ZITADEL: Token Exchange](https://zitadel.com/docs/guides/integrate/token-exchange))

**SPIFFE/SPIRE workload identity.** Instead of a static secret, a workload gets a SPIFFE ID and a short-lived SVID (X.509 or JWT), typically valid ~1 hour and automatically rotated by the SPIRE agent before expiry, with no long-lived secret ever touching disk. This is orthogonal to task-scoping (it identifies *what process* is running, not *what task* it's doing) but is increasingly composed with task-scoping in agent deployments — several 2026 papers describe minting an ephemeral, task-bound SVID per spawned agent instance, encoding which orchestrator created it and which task it serves. ([SPIFFE Concepts](https://spiffe.io/docs/latest/spiffe-about/spiffe-concepts/), [aiAuthZ: Off-Host, Identity-Bound Authorization for AI Agents](https://arxiv.org/pdf/2607.05518))

**GitHub Actions `GITHUB_TOKEN`.** The canonical CI example of task-scoped tokens: Actions generates a fresh token per job, scoped to explicit `permissions:` (everything else defaults to no access), limited to the repository containing the workflow, and it expires when the job finishes or after a hard maximum (24 hours). Notably, GitHub built in loop prevention at the platform level: actions performed with the default `GITHUB_TOKEN` do **not** trigger further workflow runs, specifically to prevent infinite workflow loops — the direct precedent for the self-trigger problem Multica currently has with PAT-authored writes. ([GITHUB_TOKEN docs](https://docs.github.com/en/actions/concepts/security/github_token), [StepSecurity: How GITHUB_TOKEN works](https://www.stepsecurity.io/blog/github-token-how-it-works-and-how-to-secure-automatic-github-action-tokens))

**GitHub Actions → AWS OIDC federation.** Rather than storing a long-lived AWS access key as a repo secret, the workflow requests a short-lived OIDC token from GitHub's own OIDC provider and exchanges it with AWS STS for temporary credentials (15 minutes to 1 hour), scoped by a trust policy to the specific repo/branch/workflow. No static secret exists anywhere in the chain, and every issuance is logged with the exact repo, branch, workflow, and run ID — an audit trail static credentials structurally cannot provide. ([GitHub Docs: OIDC with AWS](https://docs.github.com/en/actions/deployment/security-hardening-your-deployments/configuring-openid-connect-in-amazon-web-services))

**Kubernetes bound service account tokens.** KEP-1205 replaced non-expiring, unbound legacy ServiceAccount secrets with tokens minted on-demand via the `TokenRequest` API: audience-scoped (via the `aud` claim, so a token minted for one workspace/API is useless against another), time-bound (default 1 hour), and optionally bound to the requesting pod so the token dies when the pod is deleted. This audience-binding is structurally identical to Multica restricting chat-history endpoints to task-token actors only. ([KEP-1205 Bound Service Account Tokens](https://github.com/kubernetes/enhancements/blob/master/keps/sig-auth/1205-bound-service-account-tokens/README.md))

## Agent-Platform Specifics (2025–2026)

**OWASP Top 10 for Agentic Applications (2026).** Published December 2025 as the first peer-reviewed taxonomy of agent-specific security risks, it names **ASI03: Identity and Privilege Abuse** as one of the most consistently reported failure modes across 2025–2026 deployments — agents receiving broad, long-lived credentials that accumulate excessive permission over time through delegation chains and shared API keys. Its recommended mitigation is explicit: short-lived credentials, agent identities isolated from user identities, and audit logging of every privileged action. ([Cycode: OWASP Top 10 for Agentic Applications 2026](https://cycode.com/blog/owasp-top-10-agentic-applications/))

**MCP authorization spec evolution.** The Model Context Protocol's June 2025 revision (2025-06-18) reclassified MCP servers as OAuth 2.1 **Resource Servers only** — they validate tokens issued by a separate authorization server rather than minting their own — and mandated Resource Indicators (RFC 8707) so a client must bind a token to the specific resource it's calling, closing a confused-deputy class of bug where a token issued for one MCP server could be replayed against another. The July 2026 release candidate goes further, adding stateless-transport support and an Enterprise-Managed Authorization (EMA) extension aligning MCP more tightly with mainstream OAuth/OIDC deployments. ([MCP 2026-07-28 Release Candidate](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/), [Auth0: MCP Spec Updates](https://auth0.com/blog/mcp-specs-update-all-about-auth/))

**Credential brokers for agents.** SANS's "confused deputy" framing (Kenneth Hartman) proposes splitting agent credentialing into a Policy Decision Point (evaluates whether a request should be granted, never touches credentials) and a Credential Delivery Point (mints the actual short-lived, narrowly scoped, DPoP-bound token) — recommending token lifetimes as short as 60 seconds for routine operations. Independently, 2026 commentary frames this as the "ephemeral credential broker model": an orchestrator requests a credential from a broker at task spawn time, the broker validates against a permission ceiling and mints a token scoped to exactly that task, and the token expires automatically at task completion — explicitly naming the mismatch of "2-minute agent tasks backed by 60-minute OAuth tokens" as a structural risk. This is functionally identical to what Multica does when it mints `mat_` tokens at task claim. ([SANS: Your AI Agent is an Easily Confused Deputy](https://www.sans.org/blog/your-ai-agent-easily-confused-deputy-why-cloud-security-needs-credential-broker), [CSA: AI Agent Identity Is Solved Backwards](https://cloudsecurityalliance.org/blog/2026/05/08/ai-agent-identity-is-being-solved-backwards-and-the-window-to-fix-it-is-now), [Securing AI Agents with Ephemeral, Task-Scoped Credentials](https://earezki.com/ai-news/2026-05-06-stop-credentialing-your-ai-agents-like-its-2019/))

**Attribution as a first-class design problem.** Multiple 2025–2026 sources converge on the same failure pattern Multica exhibits with PAT writes: when an agent runs under a human's or a shared service's credentials, the audit log either falsely implicates a human ("a person issued actions overnight" when no person did) or collapses many distinct agent decisions into one faceless identity. The remedy proposed across the industry is a credential that carries distinct identifiers for the human principal, the agent, and — increasingly — the task or delegation chain, so logs can answer "who authorized this" and "which agent instance did it" separately. ([WorkOS: Why AI agent audit logs are different](https://workos.com/blog/agent-audit-logs), [Auth0: Closing the Audit Gap in Human-to-Agent Delegation](https://auth0.com/blog/closing-audit-gap-human-to-agent-delegation/), [Kiteworks: AI Agents Are Still Logging In as Humans](https://www.kiteworks.com/cybersecurity-risk-management/ai-agents-identity-audit-trail/))

## Design Trade-offs

**Lifetime vs. task duration.** The tightest security posture ties TTL to the literal duration of the unit of work (GitHub's job-bound `GITHUB_TOKEN`, Kubernetes pod-bound tokens). Agent tasks are worse-behaved than CI jobs: duration is unpredictable (an LLM loop can run for seconds or hours), so a pure short-TTL approach forces a renewal protocol, and renewal without a cap just re-creates a long-lived credential by another name. The credential-broker literature's answer is renewal with a hard cap and re-attestation against the same task, not indefinite refresh — mirroring Multica's explicit terminal-state binding (issue at claim, live until the task is explicitly closed) rather than a floating TTL.

**Storage on the agent host.** Three tiers appear in practice: OS keychain (macOS Keychain, libsecret) — strongest, but unavailable to headless daemon processes and bridges running as services; 0600 file-per-task with explicit cleanup — the pragmatic middle tier used by CI runners and by the Multica-integrating bridge, adequate against other local users but not against host compromise; and pure in-memory — strongest against disk forensics but fragile across daemon restarts, which matters when a bridge must survive process crashes without losing track of which tasks still hold live tokens. There is no universally correct choice; the right tier depends on whether the process is long-running and restart-prone (favor file-backed for recoverability) or short-lived and disposable (favor memory-only).

**Revocation at terminal states.** Passive expiry (short TTL) and active revocation (explicit call/delete on task completion) are complementary, not substitutes — expiry bounds the worst case if revocation is missed (crash, bug), revocation bounds the common case tightly. Mature credential-broker designs support multi-level revocation: a single token, all tokens for an agent, all tokens for a task, or an entire delegation chain.

**Attribution semantics.** RFC 8693's `act`/`may_act` chain is the general-purpose answer to "who did this" when delegation can nest arbitrarily (human → orchestrator → agent → sub-agent). Most agent platforms, including Multica as described, implement a simpler binary instead: an action is attributed either to the task-bound actor or to whichever member's PAT performed it, with no delegation chain in between. That simplicity is cheaper to build but loses the audit precision RFC 8693 provides, and it's precisely the gap that produces attribution laundering (below).

**Loop prevention: platform suppression vs. application guards.** GitHub Actions suppresses further triggers *at the platform level* only for its own auto-issued `GITHUB_TOKEN`; anything authored by a GitHub App or a PAT does trigger downstream workflows and requires an explicit actor check in the workflow condition. Agent platforms face the identical choice: suppress retriggering based on actor type centrally (clean, but only covers tokens the platform itself issues) or require every consumer to add its own "don't act if the actor is me" guard (leaky, since every new integration has to remember to add it). Multica's self-trigger gap with member-PAT writes is this exact platform-suppression-doesn't-cover-PATs case.

## Failure Modes and Mitigations

- **Leaked task tokens.** Short TTL and sender-constraining (DPoP, RFC 9449) bound a leaked token's usable window and make it unreplayable from a different host even before expiry; secret-scanning on logs and artifacts catches accidental exposure (the tj-actions/changed-files and CodeQL Action CVEs both leaked CI secrets via build logs/artifacts in 2025).
- **Stale token files outliving tasks.** The generalized "orphaned credential" problem — a valid secret outliving the identity/system it supported. Explicit cleanup on terminal state (as the Multica-integrating bridge implements) handles the graceful-exit case; crash and force-kill cases need a separate reconciliation sweep, since cleanup-on-terminal-state code never runs if the process dies mid-task. Absolute expiry is the necessary backstop for exactly this scenario.
- **Tokens outliving the task without a lifetime cap.** If token lifetime is decoupled from task lifecycle (e.g., a fixed 1-hour TTL regardless of task length), a 2-minute task leaves a valid credential live for the remaining ~58 minutes — the "30x exposure gap" pattern called out in 2026 commentary. Binding expiry to task completion (not just issuance + fixed TTL) closes this.
- **Attribution laundering.** Any write path that bypasses the task-token derivation — a long-lived PAT, a forged header, an unscoped fallback credential — lets an action appear to come from whichever actor holds that alternate credential rather than the task that logically caused it. This is both a security bug (confused deputy) and a correctness bug (self-trigger loops, false audit attribution). The only durable fix is what Multica's middleware already does for headers: derive actor identity exclusively from the credential's own cryptographic claims, never from anything the client can independently assert, and treat every non-task-token write path as a distinct, explicitly-modeled actor rather than an implicit escape hatch.

## Implications for Zylos

Zylos agents routinely act as bridges between a task-dispatching platform (Multica, OpenMax) and external write targets (GitLab, C4 channels, Plane). Wherever a platform Zylos integrates with offers task-scoped tokens, the bridge should default to using them for every write in that task's lifecycle rather than falling back to a standing PAT for convenience — the PAT path is exactly what produces self-trigger loops and attribution ambiguity. Two concrete follow-ups worth doing, not as part of this research task but as future work: (1) audit existing Zylos bridges/components for any endpoint that derives actor identity from a client-supplied header or field rather than from the credential itself; (2) for any bridge that already builds a per-task credential store (file-based, as with the Multica integration), make terminal-state cleanup and a periodic reconciliation sweep for crash-orphaned files both explicit, since the crash case is the one graceful-shutdown cleanup code cannot catch.
