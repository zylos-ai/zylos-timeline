## Executive Summary

Every AI agent fleet eventually hits the same decision point: a new agent needs to *do something* in a third-party system, and someone has to decide what credential it gets. The reflexive answer is often wrong — grant the agent whatever access looks adjacent to its job (a repo checkout, an admin console, a broad service account) rather than the narrow API surface the job actually requires. Security research through 2025–2026 is converging on a clear counter-principle: scope AI agent access to the *operation*, not the *system*, give each agent a distinct identity wherever feasible, prefer short-lived credentials over static ones, and verify every grant works — and is bounded — before calling it done.

This article surveys what NIST, OWASP, the major identity platforms (Microsoft Entra Agent ID, Okta), and the fast-growing non-human identity (NHI) security vendor category (Astrix, Oasis Security, Entro, Aembit) currently recommend for agent access provisioning, examines the real trade-offs of shared static tokens versus per-agent credentials versus workload identity, and lays out a pragmatic maturity ladder for small, self-hosted agent fleets that can't yet afford enterprise IAM tooling.

## The Access-Surface Question: API, Code, or Infra?

The first and most consequential decision in provisioning an agent is *which layer* it touches. Three layers are commonly conflated:

- **API/service-level access** — the agent calls a defined set of endpoints exposed by an application (e.g., a recruiting ATS's REST API).
- **Code/repo-level access** — the agent can read or write source code, configuration, and build artifacts.
- **Infra-level access** — the agent can reach servers, databases, cloud consoles, or CI/CD pipelines directly.

These are not interchangeable, and granting a broader layer "to be safe" is precisely the anti-pattern security guidance now targets. Microsoft's Security Blog, in a July 2026 piece on least privilege for AI agents, frames the fix as treating agents as "first-class principals" and designing roles around discrete units of work — "read-only knowledge retrieval," "create draft ticket" — rather than team-level or system-level permissions, explicitly warning against "granting broad Owner/Admin roles to unblock pilots" that never get walked back later ([Microsoft Security Blog, Jul 2026](https://www.microsoft.com/en-us/security/blog/2026/07/16/least-privilege-for-ai-agents-identity-access-and-tool-binding/)). The same piece recommends constraining access along three independent axes — resource boundary (tenant/subscription/workspace), data boundary (collection/sensitivity label), and operation boundary (read/write/export/admin) — so that "the where and what of access [is] as explicit as the who."

This maps directly onto the code-vs-API question: a non-engineering role that operates a service exclusively through its product surface has no legitimate operation-boundary need for source code. Repo read access is not a lesser version of API access — it's a different, wider surface (full application logic, secrets in config, CI credentials, other services' integration code) that happens to *contain* the capability the agent actually needs, plus a great deal it doesn't. Analyses of AI agent access control make this point directly: agents are non-deterministic, "they reason about the task, infer which tools might be relevant, and call APIs that seem useful in context," so if a broader credential is reachable, it will eventually get used opportunistically, not maliciously ([Cequence, 2026](https://www.cequence.ai/blog/ai/ai-agent-least-privilege-access/)). The corollary is that scoping to a role's real *operations* — not its adjacent visibility — is the actual definition of least privilege for agents, echoing NIST's Zero Trust Architecture (SP 800-207), which extends "verify explicitly, use least privilege, assume breach" to non-person entities and treats service accounts and API keys as first-class subjects requiring minimal scope and rotation, not exceptions to the rule ([NIST SP 800-207](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-207.pdf)). NIST's newer NCCoE concept paper on AI Agent Identity and Authorization (February 2026) narrows this further for agents specifically, identifying identification, authorization, access delegation, and logging as the four elements of a minimum production security architecture ([CSA Lab Space summary, 2026](https://labs.cloudsecurityalliance.org/research/csa-research-note-nist-ai-agent-standards-initiative-2026040/)).

OWASP's contribution is the **Non-Human Identity Top 10 (2025)**, a risk-ranked catalog built from real breach and incident data. Two entries are directly on point: **NHI5:2025 Overprivileged NHI** and **NHI7:2025 Long-Lived Secrets**, alongside NHI1 Improper Offboarding, NHI2 Secret Leakage, and NHI9 NHI Reuse ([OWASP NHI Top 10, 2025](https://owasp.org/www-project-non-human-identities-top-10/2025/top-10-2025/)). The 2026 OWASP Top 10 for Agentic Applications extends this into agent-specific territory (identity and privilege abuse is its own category, ASI03), explicitly framing agents as amplifying pre-existing NHI risk rather than introducing a wholly new one ([Entro Security, 2026](https://entro.security/blog/the-owasp-agentic-top-10-2026-what-it-means-for-ai-agents-and-non-human-identities/)).

## Credential Models & Trade-offs

For a small fleet, the real decision isn't "best practice in the abstract" — it's which of a handful of concrete credential models fits the service in front of you, especially when that service's own API only supports one shape of token.

| Model | What it is | Blast radius on compromise | Revocation cost | Fits small fleets when… |
|---|---|---|---|---|
| **Shared static token** | One long-lived secret, same value for every holder | Full — every holder's access, indefinitely, until rotated | High: rotating requires redistributing to *every* holder simultaneously, with a coordinated cutover | The service literally supports only one token, the number of holders is small and known, and you compensate with verification + monitoring |
| **Named per-agent keys** | Each agent gets its own key/credential, same permission scope | Contained to one agent's scope; other agents unaffected | Low: revoke one key without touching others | The service supports multiple API keys/service accounts and you want per-agent audit trails |
| **OAuth client-credentials per agent** | Each agent is a registered OAuth client, exchanges its own secret for scoped, time-limited access tokens | Contained, and time-bound even if leaked | Low, plus tokens self-expire | You control (or can extend) the auth layer and want scope + expiry enforced centrally |
| **Workload identity (SPIFFE/SPIRE, cloud IAM roles)** | No standing secret at all; identity is attested cryptographically (mTLS/X.509-SVID) at connection time | Minimal — nothing to steal that outlives the session | Near-zero: identity issuance is policy-driven | You run infrastructure the agent can be attested *from* (a controlled runtime/host), and the target service supports token federation |

Static, shared, long-lived credentials are the *default* in practice today, not the aspiration: an analysis of the official MCP server registry found 91.5% of listed servers ship with no OAuth support at all, relying on static API keys, personal access tokens, or nothing ([Guild.ai, Jul 2026](https://www.guild.ai/blog/agent-governance/the-credential-crisis-is-already-here); corroborated by [Microsoft Community Hub](https://techcommunity.microsoft.com/blog/appsonazureblog/only-8-5-of-mcp-servers-use-oauth-%E2%80%94-heres-how-to-host-one-securely-on-app-servic/4530349)). This is the honest starting point for most small-fleet integrations: the *service*, not the agent operator, usually dictates what's possible, and many still-common SaaS and internal tools expose exactly one static token, full stop.

Industry guidance is consistent on the direction of travel, though. GitGuardian's practical trade-off guide on short-lived credentials in agentic systems argues the core problem with static keys isn't that they're long-lived in the abstract, but that the "credential exposure window" scales with agent concurrency and retry behavior — an agent task that completes in two minutes but holds a token valid for weeks creates an attack surface no human workflow would tolerate ([GitGuardian](https://blog.gitguardian.com/short-lived-credentials-in-agentic-systems-a-practical-trade-off-guide/)). OpenAI's own platform guidance is blunt about the sharing question specifically: API keys are not meant to be shared across users — new team members get their own key on invite, precisely so that per-identity revocation and audit remain possible ([OpenAI Help Center](https://help.openai.com/en/articles/5112595-best-practices-for-api-key-safety)).

Where a shared token is genuinely unavoidable, the mitigations converge on three things: (1) minimize and document the holder list explicitly, (2) treat the token as tier-1 secret material (vaulted, never logged, never pasted in shared channels), and (3) compensate for the coarse revocation granularity with verification and monitoring on the *grant*, since you can't get fine-grained revocation after the fact. That compensating control is the subject of the next section.

## Canary Verification Patterns: Prove the Grant Works and Is Bounded

Granting access is only half the job; security and IAM literature increasingly treats *verifying* a grant as a first-class step, not an afterthought. Two established traditions converge on the same practice a canary-based grant check embodies:

**Access certification / entitlement review.** In mature IAM programs, access is periodically re-validated — reviewers confirm each entitlement is still needed and actually usable, with remediation APIs frequently using "staged or canary revokes, pre-change impact analysis, and quick rollback mechanisms" so that changing access doesn't silently break something ([DevSecOps School, 2026](http://devsecopsschool.com/blog/access-certification/); [Palo Alto Networks Cyberpedia](https://www.paloaltonetworks.com/cyberpedia/what-is-access-certification)). The word "canary" appears in this literature specifically because certification and grant changes are treated as risky operations that need a bounded, observable test before being trusted at scale.

**Canary tokens / honeytokens.** Security teams already use synthetic, purpose-built credentials and records — fake AWS keys, decoy database rows, beacon documents — whose only property of interest is that any interaction with them is unambiguous signal, with zero legitimate false-positive path ([Huntress](https://www.huntress.com/cybersecurity-101/topic/what-is-honey-token); [CounterCraft](https://www.countercraftsec.com/blog/canary-tokens-honeytokens-explained/)). Applying the same logic in the *opposite* direction — deliberately writing a synthetic, clearly-marked record through a new grant, then reading it back and deleting it — gives you the same unambiguous signal for a *positive* claim: "this credential can read," "this credential can write," and, critically, "this is what it looks like when it does, so we know what to watch for and clean up afterward." This is the practical shape of a grant-verification canary: a read probe (does the token actually resolve real data, not just return 200 with an empty payload), a write probe using data that's obviously synthetic and tagged for cleanup (never real records), sanitized evidence capture (redact tokens/PII from screenshots or logs kept as proof-of-grant), and a cleanup step that removes the test artifact so it doesn't pollute the target system. This is the same discipline OWASP's NHI guidance gestures at when it stresses that offboarding and grant changes must be verifiable events, not assumed ones ([OWASP NHI Top 10](https://owasp.org/www-project-non-human-identities-top-10/2025/)).

## The Non-Human Identity Landscape, 2025–2026

NHI management has become a distinct, well-funded security category rather than a subset of general IAM. Machine identities — service accounts, API keys, bots, and now AI agents — already outnumber human identities by roughly 45:1 to 100:1 in enterprise environments, and the category has both fresh capital and consolidation activity: Oasis Security raised a $120M Series B in March 2026 (led by Craft Ventures, with Sequoia and Accel) specifically to build governance for machine and agent identities ([SecurityWeek](https://www.securityweek.com/oasis-security-raises-120-million-for-agentic-access-management/); [Bloomberg](https://www.bloomberg.com/news/articles/2026-03-19/startup-oasis-security-raises-120-million-from-craft-sequoia)), while Cisco has reportedly been in acquisition talks for Astrix ([BankInfoSecurity](https://www.bankinfosecurity.com/blogs/cisco-eyeing-buy-non-human-identity-startup-astrix-p-4105)). Astrix (discovery and posture across SaaS/cloud/code), Oasis (full lifecycle governance including rotation and decommissioning), and Entro (secrets-centric tracing) form the leading tier of dedicated NHI platforms, with Aembit positioning specifically around workload/agent identity via SPIFFE/SPIRE-style attestation rather than standing secrets.

The identity platform incumbents are also moving quickly. Microsoft's Entra Agent ID, now generally available, gives every AI agent created through Copilot Studio or Azure AI Foundry a unique object ID in a unified directory, extending the same Zero Trust constructs used for human identities — conditional access, governance workflows, lifecycle management — to agents ([Microsoft Learn](https://learn.microsoft.com/en-us/entra/agent-id/what-is-microsoft-entra-agent-id)). Okta introduced an "Identity Security Fabric" in late 2025 explicitly to "discover, provision, authorize and govern nonhuman identities at large scale," treating agents as a new identity class alongside human and service-account identities rather than bolting agent support onto existing service-account tooling ([Okta Newsroom](https://www.okta.com/newsroom/articles/identity-security-fabric-emerges-as-blueprint-for-securing-ai-agents/)). On the standards side, SPIFFE/SPIRE remains the reference architecture for cryptographic workload identity (production use at Uber, Stripe, Netflix), though practitioners note real friction applying it to agents: X.509 issuance latency doesn't suit ephemeral, per-task agent instantiation the way it suits long-running services ([Solo.io](https://www.solo.io/blog/agent-identity-and-access-management---can-spiffe-work); [MojoAuth](https://mojoauth.com/blog/workload-identity-for-agents-spiffe-spire-vs-oauth-client-credentials)).

The throughline across all of this tooling is the same principle stated more simply by NIST and OWASP: an agent should be a **distinguishable, governable identity**, not an anonymous holder of a shared secret — even when the practical reality (that 91.5% MCP-server statistic) is that most integrations today don't yet support that.

## A Pragmatic Maturity Ladder for Small Fleets

Enterprise NHI platforms and SPIFFE-grade workload identity are overkill for a five-agent, self-hosted fleet talking to a handful of SaaS APIs. A more useful framing is a ladder, climbed only when the next rung is actually reachable — a pattern consistent with published machine-identity maturity models that run from ad-hoc shared credentials through to dynamic, policy-issued identity ([NHIMG, Machine-to-Machine Identity Maturity Model](https://nhimg.org/machine-to-machine-identity-maturity-model)):

1. **Rung 0 — Shared static token, verified.** The target service only supports one token. Document every holder, vault the secret, verify the grant with a read + write canary and sanitized evidence, and accept that revocation means a coordinated rotation across all holders. This is a legitimate, deliberate choice for a small fleet against a single-token API — not a failure state — provided it's chosen consciously and the blast radius is written down, not discovered later.
2. **Rung 1 — Named per-agent keys.** The moment a service supports multiple API keys or service accounts, move each agent onto its own. This alone gets you per-agent audit trails and lets one compromised or retired agent's credential be revoked without touching the rest of the fleet.
3. **Rung 2 — Scoped, short-lived tokens (OAuth client-credentials or equivalent).** When the service or your own gateway can issue time-bound tokens, bind each agent to its own OAuth client and narrow scopes to the specific operations the role needs (read-only vs. write, specific endpoints), not blanket account access.
4. **Rung 3 — Workload/runtime identity.** Reserved for fleets running on infrastructure you control end-to-end, where agents can be cryptographically attested (SPIFFE/SPIRE, cloud IAM roles) and credentials are minted just-in-time per task rather than stored anywhere at rest.

The climb should be triggered by *capability*, not calendar: reassess the rung whenever a target service adds multi-key support, whenever the fleet's agent count grows enough that shared-token coordination becomes the actual bottleneck, or whenever an incident (even a near-miss) exposes how coarse the current revocation granularity really is.

## Key Takeaways

- **Scope to operations, not systems.** A role that consumes a service via its API has no legitimate need for source-code access, however "read-only and harmless" that access looks — repo access is a wider surface that happens to contain the needed capability plus a great deal more (Microsoft Security Blog, OWASP NHI Top 10).
- **Shared static tokens are a real, common, and sometimes correct choice** — not a violation of best practice by default — when a service genuinely supports only one credential and the fleet is small enough to track every holder explicitly. The honest cost is coarse revocation: rotating means rotating for everyone, every time.
- **Named-per-agent and short-lived credentials should be the default the moment the target service allows it.** Most don't yet (91.5% of MCP servers ship without OAuth), which is itself the biggest gap in the current agent ecosystem, not a justification for staying at rung 0 indefinitely.
- **Verify every grant with a bounded canary** — a read probe, a synthetic write probe, sanitized evidence, and cleanup — borrowing directly from established access-certification and honeytoken practice, so "the grant works" and "the grant is bounded" are both demonstrated, not assumed.
- **NHI is now a distinct, funded security category** (Astrix, Oasis, Entro, Aembit) and a first-class feature area for Microsoft Entra and Okta, signaling where enterprise tooling is headed even if small self-hosted fleets won't need that tooling for a while yet.
- **Treat the credential model as a ladder tied to service capability**, and revisit the rung deliberately rather than defaulting to whatever was easiest to wire up first.
